# 代码审查工作流

当用户要求对本次任务涉及的代码进行审查时，**必须严格按以下流程执行**。

## 职责划分（重要）

- **阶段一（收集信息）和阶段二（逐项审查）** 可以调用 CodeReview 子代理执行
- **阶段三（输出审查报告）始终由主代理执行**，子代理返回后主代理必须立即执行阶段三，不得遗漏

> ⚠️ **核心规则**：无论使用子代理还是主代理执行审查，阶段三（保存审查报告到文件）都是强制性的最终步骤，
> 不得以任何理由跳过。子代理完成后，主代理必须立刻执行阶段三，否则视为流程未完成。

---

## 阶段一：收集信息

**目标**：收集审查所需的全部上下文信息。

执行步骤：
1. **获取git diff**：运行 `git diff` 获取当前工作区的全部代码变更
   > ⚠️ 直接通过终端输出捕获 diff 内容，**禁止**创建临时文件（如 `review_diff.txt`）来存储 diff
2. **读取修改文件**：读取所有被修改文件的完整内容
3. **检查相关测试**：查找与被修改文件相关的测试文件
4. **补充上下文**：如有必要，搜索关联的调用方代码和被调用方代码

## 阶段二：逐项审查

**目标**：按四个维度逐项评估代码变更质量。

### 1. 核心逻辑
- 变更是否完整实现了预期目标？
- 路径匹配是否正确（AntPathMatcher/RequestMapping等）？
- 有没有遗漏的边界情况？

### 2. 安全合规（本项目的重点）
- JWT认证变更：公开路径放行是否合理？
- 涉及字符串/文件/网络处理时，是否显式指定了 UTF-8 编码？
- API入参是否有校验？
- 是否存在敏感数据泄露风险？

### 3. 代码整洁
- 命名是否达意？
- 有没有不必要的重复代码？
- 注释是否准确且必要？（过时的注释比没有注释更糟糕）
- 风格是否与项目既有代码一致？

### 4. 周边配套
- 是否需要同步更新配置、常量或文档？
- 是否需要补充单元测试？
- 知识库/项目记忆是否需要同步更新？

## 阶段三：输出审查报告（主代理执行，不得跳过）

**目标**：将审查结论保存到 `doc\代码审查` 目录。

**执行者**：主代理（不能委派给子代理）

**执行时机**：子代理返回审查结论后，**主代理立即执行本阶段**

执行步骤：
1. **获取最新 git diff**（阶段一完成后可能有新的修改，需重新获取以确保准确）
   > ⚠️ 直接通过终端输出捕获 diff 内容，**禁止**创建临时文件
2. **生成审查结论**：按下方输出格式，汇总四个维度的审查结果
3. **保存到文件**：将完整审查报告保存到 `med_ai_assistant_1.0_bs_backend\doc\代码审查\{yyyy-MM-dd}-{审查主题}.md`

## 注意事项

- **审查必须基于实际代码**：审查前先获取最新的 git diff，不得凭空审查
- **安全合规是重点**：本项目有 JWT 认证体系，涉及公开路径放行需格外审慎
- **结论明确**：必须给出「通过 / 有条件通过 / 不通过」的明确结论
- **问题可追溯**：问题清单中的文件路径应可被审查人直接定位
- **保存到文档**：审查报告必须保存到 `doc\代码审查` 目录，文件名包含日期和主题
- **检查标准为相对路径**：审查报告的文档路径基于 `med_ai_assistant_1.0_bs_backend` 的相对路径
- **主代理负责最终落地**：即使阶段一/二委托给子代理，阶段三的保存操作必须由主代理执行，不可委派
- **禁止创建临时文件**：捕获 git diff 时直接通过终端输出获取，不得创建 `review_diff.txt` 等临时文件，避免需要手动清理
