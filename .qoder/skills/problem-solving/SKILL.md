# 问题解决工作流

解决任何问题或bug时，**必须严格按顺序执行以下四个阶段**，禁止跳过任何阶段。

## 阶段一：调研问题原因

**目标**：深入分析问题的所有可能根因，建立完整的问题画像。

执行步骤：
1. **复现与确认**：明确问题的具体表现、触发条件、影响范围
2. **代码分析**：检查相关源码，追踪调用链路，定位可疑代码段
3. **日志与配置检查**：查看错误日志、应用配置、环境变量等
4. **依赖分析**：检查相关依赖版本、第三方库兼容性
5. **列出根因清单**：按可能性从高到低列出所有潜在原因

**输出格式**：
```markdown
### 问题调研报告
- **问题描述**：[具体表现]
- **影响范围**：[受影响的模块/功能/用户]
- **可能根因**：
  1. [最可能的原因] - 证据：[...]
  2. [次可能的原因] - 证据：[...]
  3. ...
```

## 阶段二：网络检索最佳实践

**目标**：搜索该类问题的业界最佳实践和已验证的解决方案。

执行步骤：
1. **关键词提炼**：从阶段一的调研结果中提取精准搜索关键词
2. **多维度检索**：
   - 搜索错误信息、异常类型的通用解决方案
   - 查找相关框架/库的官方文档和已知问题
   - 参考 Stack Overflow、GitHub Issues 等社区经验
   - 查阅相关技术博客和最佳实践文章
3. **方案收集**：整理搜索到的可行方案，记录来源和适用条件

**输出格式**：
```markdown
### 最佳实践检索结果
- **方案A**：[描述] - 来源：[URL/文档]
  - 优点：[...]
  - 局限：[...]
- **方案B**：[描述] - 来源：[URL/文档]
  - 优点：[...]
  - 局限：[...]
```

## 阶段三：拟定解决方案

**目标**：综合前两个阶段的成果，制定具体可执行的解决方案。

执行步骤：
1. **方案选型**：对比各候选方案，选择最适合当前项目的方案
2. **修改范围界定**：明确需要修改的文件和代码位置
3. **影响评估**：评估修改对其他模块的影响
4. **风险识别**：列出潜在风险和回退策略
5. **向用户确认**：将方案呈现给用户，获得确认后再执行

**输出格式**：
```markdown
### 解决方案
- **选定方案**：[方案描述]
- **选择理由**：[为什么选这个方案]
- **修改范围**：
  - [文件路径1]：[修改内容概述]
  - [文件路径2]：[修改内容概述]
- **影响评估**：[对其他模块的影响]
- **风险点**：
  1. [风险描述] - 缓解措施：[...]
- **回退策略**：[如果修改失败如何回退]
```

## 阶段四：执行代码修改

**目标**：按照方案精确执行修改，并验证修复效果。

执行步骤：
1. **按方案修改**：严格按照阶段三确认的方案进行代码修改
2. **增量验证**：每完成一个修改点，立即验证其正确性
3. **回归测试**：确保修改不会引入新问题
4. **修复确认**：验证原问题已被解决

## 注意事项

- **严禁跳步**：不可未调研就直接改代码，不可未检索就拟定方案
- **证据驱动**：每个阶段的结论都需要有具体证据支撑
- **用户确认**：阶段三完成后，必须等用户确认方案再执行阶段四
- **记录完整**：保留完整的调研和决策过程，便于后续追溯
