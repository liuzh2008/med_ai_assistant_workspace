# 方案文档感知审查

## 适用情形

当你有一个方案/计划，需要验证它是否与项目已有的**领域语言、架构设计、代码实现、历史决策**一致时使用。

典型场景：
- 新功能方案评审，检查用词是否和现有设计文档一致
- 重构计划审查，确认对现有架构的理解是否正确
- 接口设计审查，验证设计是否遵循项目已有的原则和模式

## 审查方式

**逐条追问**，每次只问一个问题，等待反馈后再继续。对于每个问题，先给出推荐的答案。

> 如果问题可以通过探索代码库来回答，优先探索代码库而不是提问。

---

## 审查维度

### 1. 领域文档感知

在审查过程中，同时参考以下项目文档进行交叉验证：

```
med_ai_assistant_1.0_bs_backend/doc/
├── 系统结构/          ← 系统架构、模块设计文档
│   ├── 后端系统整体架构.md
│   ├── DRG分析/
│   ├── 患者与病历管理/
│   └── ...
├── 原则/              ← 设计原则与规范
│   └── 500行以上代码重构原则.md
├── 接口/              ← API 接口规范
├── 迭代/              ← 迭代方案与 TDD 实施指南
├── 问题修复/          ← 历史问题修复记录
└── 更新日志/          ← 版本更新记录
```

### 2. 术语校准

当方案中使用的术语与现有文档中的定义冲突时，立即指出：

- "文档里把 X 定义为 Y，但你这里说的 X 似乎是 Z 的意思——到底是哪个？"
- 当使用模糊或过载的术语时，提出精确的规范术语

### 3. 具体场景推演

当讨论领域关系时，构造具体场景进行压力测试：
- 设想能触及边界情况的场景
- 迫使对概念之间的界限做出精确说明
- 异常流程和错误处理是否覆盖

### 4. 代码交叉验证

当方案描述某个功能的现有行为时，检查代码实际是否如此：

- 如果发现矛盾，指出："代码里是这样实现的，但你说的是那样——哪个是对的？"
- 检查现有 Repository、Service、Controller 的实际签名和行为

### 5. 决策记录

当以下三个条件**全部满足**时，建议创建决策记录（存入 `med_ai_assistant_1.0_bs_backend/doc/其他/` 或 `doc/原则/`）：

1. **难以逆转** — 以后改主意的成本很高
2. **无上下文难以理解** — 以后的人看代码会问"为什么这么做？"
3. **真正的权衡结果** — 存在多个可选方案，且有明确的选择理由

缺少任意一条，则跳过决策记录。

---

## 执行流程

### 步骤一：加载领域知识

审查开始前，加载以下项目知识：
1. `doc/系统结构/` 中相关模块的架构文档
2. `doc/原则/` 中的设计原则
3. `doc/接口/` 中相关 API 规范
4. 相关模块的源代码结构

### 步骤二：逐条追问

按设计树的分支逐一深入，一次一个决策点：

```
当前决策 → 子决策A → 子决策A.1 → 子决策A.2 → 回退 → 子决策B → ...
```

每步先给出推荐答案，等待用户反馈后再继续。

### 步骤三：实时更新

当以下情况发生时，立即更新文档（不批量积压）：
- **术语明确** → 更新 `doc/系统结构/` 中相关文档的术语定义
- **决策确定** → 判断是否符合 ADR 三原则，按需记录到 `doc/其他/`
- **架构变更** → 更新 `doc/系统结构/` 中的架构描述

### 步骤四：审查结论

```markdown
## 审查结论

### 术语一致性
- **与现有文档一致**：[全部一致/存在冲突]
- **冲突项**：[如有，列明]

### 代码一致性
- **与实际代码一致**：[全部一致/存在矛盾]
- **矛盾项**：[如有，列明]

### 文档更新
- [ ] 已更新术语定义
- [ ] 已记录决策（如符合 ADR 三原则）
- [ ] 已更新架构描述

### 方案成熟度
- **方案是否可执行**：[是/需调整后执行]
- **主要风险点**：[如有]
```
