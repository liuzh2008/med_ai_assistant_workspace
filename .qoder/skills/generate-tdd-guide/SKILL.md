# TDD 实施指南生成（Generate TDD Guide）

按敏捷开发和测试驱动开发（TDD）原则，为指定项目生成一份**专业、详细、可操作**的 TDD 实施指南文档。

## 调用方式

| 方式 | 触发条件 |
|------|---------|
| 斜杠手势（DSH Web） | 在 DSH Web 输入框直接输入 `/generate-tdd-guide`（输入 `/` 后会自动弹出技能建议菜单 "Trigger suggestions"，选择本技能即可），回车发送即自动注入技能指令并执行；可附加文本，如 `/generate-tdd-guide 为质控模块生成指南，覆盖率 80%`。此路径为 DSH 内置机制（`skill.list` + pre-step `/name` token 注入），无需额外注册 |
| 斜杠命令（qoder） | 用户输入 `/generate-tdd-guide`（qoder 编辑器，命令定义见 `.qoder\commands\generate_tdd_guide.md`） |
| 自然语言 | 用户说"编写 TDD 实施指南"、"生成测试驱动开发计划"、"写一份 TDD 文档"、"红绿重构计划"等 |
| 场景 | 新模块开工前制定开发计划、迭代规划、质量评审需要测试方案时 |

## 执行流程

### 第一步：收集项目信息（缺失时先询问用户）

| 信息 | 说明 |
|------|------|
| 项目名称 | 必填，用于文档命名与概述 |
| 项目描述 | 项目目标与核心功能，1~3 句 |
| 开发周期 | 预计时间范围。按 AI 编码节奏以**小时/半天**为单位预估（如 2026-08-13 上午，约 3 小时），不使用人周/人月口径 |
| 质量目标 | 如"核心模块单元测试覆盖率 ≥ 80%，总覆盖率 ≥ 70%" |
| 模块清单 | 通常 3 个模块，每个模块需可描述其核心功能 |

若用户未指定，默认以当前项目（医疗AI辅助系统 MedAiAssistant：Java 21 + Spring Boot 3.5.8 + Oracle 21c / Vue 3 + Element Plus）为对象生成。

### 第二步：按模板生成

严格按下方「文档模板」生成，**保留全部章节编号与层级**，将占位符替换为实际内容。模板中标注"示例"的片段（如 pytest.ini、Gherkin）为可直接落地的示例代码。

### 第三步：文档命名与保存

- **命名规则（必须完整、准确）**：`TDD实施指南-<项目名称>-<YYYYMMDD>.md`，例如 `TDD实施指南-医疗AI辅助系统-20260813.md`；同一项目的迭代更新追加版本号，如 `TDD实施指南-医疗AI辅助系统-20260813-v2.md`。若为英文环境可命名 `TDD-Implementation-Guide-<ProjectName>-<YYYYMMDD>.md`。
- **保存位置**：默认保存到 `doc\` 目录；用户指定位置时按指定保存。

## 生成要求

- **适用范围（系统级技能）**：本技能跨项目 / 跨系统使用，**不得把任何单一项目的口径当作通用规则**。文中出现的具体技术栈、配置文件（`pom.xml` / `package.json` / `vite.config.ts`）、测试框架、E2E 载体与规则文件（如 `.qoder/rules/*`）**一律只是"该项目的实测结论或示例"**；为目标项目生成前必须先实测该项目仓库，按实测结果替换。
- 每条用户故事必须包含：用户角色（作为…）、需求描述（我需要…以便…）、验收标准（Given-When-Then）。
- 每个开发任务必须三阶段齐备：红（失败测试清单）、绿（最小实现方案）、重构（优化方向）。
- 周期表、风险矩阵、质量门禁表、交付计划表等**必须完整填写**，不得留空或写"待补充"。
- **时间预估口径**：当前代码由 AI 辅助编写、速度极快，一般任务 30 分钟内完成，因此所有工期/耗时一律按 **分钟（单个周期）、小时或半天（整体）** 预估，不使用"人天/人周"口径；**周期 = 一个可独立验证的任务**（红-绿-重构三阶段齐备），按 AI 编码速度以分钟计耗时，常见 10~30 分钟。
- **AI 执行纪律（必须写进指南，供实施会话遵守）**：① **禁止修改或删除测试来让用例通过**（出现改/删测试、硬编码期望值等作弊迹象即停下说明）；② **禁止实现周期表未登记的功能**，超范围需求先补周期再实现；③ **同一问题连续修复 2 次仍未通过，停下重新规划**，不做第三次试错。
- **生成前必须实测核对**：测试框架、命令、脚本名、测试文件命名与目录约定一律以目标仓库实测为准（见 §4.3），**禁止沿用其他项目或同级文档的测试命令**。
- ATDD 场景一律使用 Gherkin 语法（Feature / As a / I want / So that / Scenario / Given / When / Then）。
- 若模块信息不足，按 3 个模块生成占位章节并明确提示用户补充，而不是跳过。

## 文档模板

### 1. 项目概述

- 项目名称：`<项目名称>`
- 项目描述：`<项目目标与核心功能，1~3 句>`
- 开发周期：`<预计时间范围，按 AI 编码节奏以小时/半天为单位，如"2026-08-13 上午，约 3 小时">`
- 质量目标：`<按仓库实际写，如"新增代码覆盖率 ≥ 80%"；不写不可达的全局覆盖率门禁（见 §5.1）>`

### 2. 用户故事拆分

为以下模块生成用户故事和验收标准（`<模块1名称>`、`<模块2名称>`、`<模块3名称>`，按实际模块列表展开）。

每个用户故事应包含：

- **用户角色**：作为`<角色>`
- **需求描述**：我需要`<功能>`，以便`<价值>`
- **验收标准**（使用 Given-When-Then 格式）：
  - Given `<前置条件>`
  - When `<操作>`
  - Then `<预期结果>`

### 3. TDD 实施计划

#### 3.1 任务分解

将每个用户故事分解为具体的开发任务，每个任务应包含：

**任务名称**：`<具体任务描述>`
- 红阶段：`<编写失败测试用例清单>`
- 绿阶段：`<最小实现方案>`
- 重构阶段：`<优化方向>`

#### 3.2 红-绿-重构周期表

创建周期跟踪表格：

| 周期 | 红（失败测试） | 绿（最小实现） | 重构 | 预估耗时（分钟） | 状态 |
|------|--------------|--------------|------|---------|------|
| 1 | `<失败测试名称>` | `<最小实现>` | `<重构动作>` | `<如 20（红 5 / 绿 10 / 重构 5）>` | 待开始 |

预估耗时按 AI 编码速度填写，单位为分钟（示例：`20`，可注"红 5 / 绿 10 / 重构 5"）。**周期以"一个可独立验证的任务"为界，不按分钟数硬切**：单个周期耗时明显超过 30 分钟时，仅提示"该任务偏大，建议评估是否拆分"，**不得为凑时长把一个完整任务拆碎成多个周期**。

### 4. 测试策略

#### 4.1 测试金字塔配置

- 单元测试（70%）：`<框架选择、覆盖范围>`
- 集成测试（20%）：`<集成点、测试场景>`
- E2E 测试（10%）：`<端到端流程>`

技术栈适配示例（本项目默认栈）：

- 后端单元测试：JUnit 5 + Mockito；前端单元测试：Vitest（Vue 组件）。
- 集成测试：Spring Boot Test + Testcontainers（Oracle 21c 容器）验证 DAO/Service 与数据库集成；前端接口联调用 MSW。
- E2E 测试：主项目（MedAiAssistant）用 Cypress，覆盖登录 → 主流程 → 结果落库的关键路径；教学项目（AiMedTeach）用 Playwright Core（`node e2e/*.spec.mjs`）。**按目标仓库实测选择，不得跨项目照搬**。

#### 4.2 测试环境配置

- 测试框架配置：**先按 §4.3 实测，再写本仓库的真实配置**，禁止照抄示例。示例（仅当目标仓库确为该栈时才保留）：Python 用 `pytest.ini`（`testpaths` / `addopts` / `markers`）；Java 用 `pom.xml` 的 surefire + failsafe 段；前端用 `vitest.config.ts` 或 `vite.config.ts` 的 test 段。

- 测试目录结构：

```
项目根/
├── src/                  # 生产代码
└── tests/
    ├── unit/             # 单元测试（70%）
    ├── integration/      # 集成测试（20%）
    └── e2e/              # E2E 测试（10%）
```

- 持续集成流水线配置：**先实测仓库是否已有跑测试的 CI**（本项目当前无：`.github/workflows/` 仅有发布/安全/文档类流水线）。写作口径：

  - 已有 → 引用真实 workflow 文件名与步骤；
  - 没有 → 写"CI 测试门禁：待建设（现状：无）"，**不得写成既有流程**；若指南要求接入 CI，须新增对应任务并标注为待建设，目标形态示例：

```yaml
# 目标形态（仅当指南含"接入 CI"任务时写；命令按 §4.3 实测替换）
jobs:
  test:
    steps:
      - run: mvn -B verify          # 单测 + failsafe 集成测试
      - run: npm run test:unit      # 按实测脚本名替换
```

#### 4.3 测试栈实测核对与假绿排查

生成指南前，必须对目标仓库**实测**以下各项，并把实测结论作为「工具现状」写进 §4.2 与 §5.1（**禁止照抄其他项目或同级文档**）：

| 核对项 | 实测位置 | 必须记录的结论 |
|-------|---------|--------------|
| 单元测试框架与命令 | `pom.xml` 的 surefire 段 / `package.json` 的 scripts | 命令与脚本名原文 |
| 集成测试承接 | 是否有 failsafe 承接 `**/*IT.java` | 无 failsafe → **禁止新增 `*IT.java`**（会静默不执行） |
| E2E 框架与载体 | `cypress/` 目录 / `e2e/*.spec.mjs` / playwright-core 依赖 | 究竟 Cypress 还是 Playwright，脚本原文 |
| 覆盖率工具与门禁 | jacoco 是否有 `check`、前端是否有 `coverage` script | 只有观测能力 → **不得写成门禁** |
| 测试 CI | `.github/workflows/` 是否含跑测试的流水线 | 没有 → 标注"待建设（现状：无）" |
| 测试文件命名与脚本 glob | 执行脚本匹配的模式 vs 计划新增的文件名 | 二者必须一致 |

**假绿排查（每条都要能在指南中验证）：**

- 运行后**必须出现 `Tests run:` 行且数量 > 0**；只有 `BUILD SUCCESS` 而无 `Tests run` = 测试根本没跑（多为包路径或命名不符）；
- **新增测试文件名必须落在执行脚本的 glob 内**（如脚本跑 `test/xxx/*.test.mjs`，则文件不得写成 `.spec.mjs`）；
- **标了 `*IT` / `*ITCase` 的类必须有 failsafe 或等价机制承接**，否则被 surefire 排除且静默不执行；
- **项目特定强制项（只在其所属项目内适用，换仓库必须先实测）**：以下条目出自 **MedAiAssistant 主项目**的 `.qoder/rules/06-testing.md`，**仅当目标仓库就是该主项目时**照写；目标仓库为其他项目（如 AiMedTeach）时，必须先实测该仓库既有的测试风格与命令再落笔——例如 `@MockitoBean` 与 `@MockBean` 在项目间并不一致，禁止跨项目套用。MedAiAssistant 口径：用 `@MockitoBean`（禁用 `@MockBean`）；**禁止 `mvn test` 全量**，用 `mvn test -Dtest=XxxTest`；测试命名 `{方法}_{场景}_{期望}`。

|---------|--------|----------|-------------------|----------|

## 输出示例（节选）

一份 3 模块的指南约 80~140 行正文（不含配置代码；含 §4.3 实测核对与假绿排查）。示例片段：

```gherkin
Scenario: 医生保存诊断结论成功
  Given 医生已登录并完成诊断录入
  When 医生点击"保存诊断结论"
  Then 系统提示保存成功且结论持久化到数据库
```

## 注意事项

- 文档语言：默认简体中文（代码标识符、框架名、命令保留原文）。
- 严格遵循 TDD：先写测试再实现，禁止在绿阶段之前编写生产代码。
- 生成后主动提醒用户：模块清单、覆盖率目标、工期/耗时预估（分钟·小时口径）等占位信息是否准确，便于修订。
