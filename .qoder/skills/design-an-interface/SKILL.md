# 接口多方案设计

## 概述

对一个模块的接口，同时生成多个**截然不同**的设计方案（而非微调），每个方案体现不同的设计哲学和权衡。通过方案对比，避免过早锁定单一设计方向。

## 执行步骤

### 步骤一：理解需求

明确接口设计的上下文：

1. **模块职责**：这个模块做什么？不做什么？（遵循关注点分离原则）
2. **调用方**：谁调用这个接口？期望的交互模式是什么？
3. **数据流**：输入是什么？输出是什么？数据如何流转？
4. **约束条件**：性能要求、安全要求、兼容性要求
5. **现有集成点**：需要与哪些现有模块/系统对接

### 步骤二：生成多个设计方案

为同一个接口生成 2-4 个**截然不同**的设计方案，每个方案遵循不同的设计哲学：

**设计方案差异化维度**：

| 维度 | 可选方向 |
|------|---------|
| **API 风格** | RESTful / RPC / GraphQL / 事件驱动 |
| **数据格式** | JSON / Protocol Buffers / 纯文本 / 二进制 |
| **同步/异步** | 同步阻塞 / 异步回调 / 消息队列 / WebSocket 流式 |
| **状态设计** | 有状态 / 无状态 / 混合 |
| **错误处理** | 异常码 / HTTP 状态码 / Result 封装 / 自定义错误类型 |
| **粒度** | 粗粒度（单接口完成复杂操作）/ 细粒度（多个原子接口） |

### 步骤三：方案对比

对每个方案进行多维度的对比评估：

| 评估维度 | 方案A | 方案B | 方案C |
|---------|------|------|------|
| 实现复杂度 | [高/中/低] | [高/中/低] | [高/中/低] |
| 调用方体验 | [好/中/差] | [好/中/差] | [好/中/差] |
| 性能表现 | [高/中/低] | [高/中/低] | [高/中/低] |
| 可维护性 | [高/中/低] | [高/中/低] | [高/中/低] |
| 扩展性 | [高/中/低] | [高/中/低] | [高/中/低] |
| 与现有架构一致性 | [高/中/低] | [高/中/低] | [高/中/低] |

### 步骤四：推荐方案

向用户推荐最优方案，说明选择理由。

## 输出

```markdown
## 设计方案对比

### 需求概要
[一句话描述需求]

### 方案A：[设计哲学]
[方案描述 / 接口定义 / 数据流]

### 方案B：[设计哲学]
[方案描述 / 接口定义 / 数据流]

### 方案C：[设计哲学]
[方案描述 / 接口定义 / 数据流]

### 推荐方案
**推荐**：方案[A/B/C]
**理由**：[选择理由]
```
