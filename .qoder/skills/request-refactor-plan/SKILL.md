# 重构计划生成

## 概述

通过与用户访谈了解代码现状，生成结构化重构计划。强调**小提交粒度**（每个提交只做一个重构点），确保每次重构可独立验证和回退。

## 执行步骤

### 步骤一：访谈调研

通过以下问题了解待重构代码的现状：

**目标与范围**：
- "需要重构的模块是哪个？它负责什么功能？"
- "为什么需要重构？当前代码有什么问题？"
- "重构的范围有多大？是整个模块还是某个子功能？"

**现状诊断**：
- "当前代码的核心复杂度在哪里？"
- "是否存在重复代码、过长的类/方法？"
- "是否有循环依赖或不合理的依赖关系？"
- "当前的测试覆盖情况如何？"

**约束条件**：
- "重构有截止时间吗？"
- "重构期间是否可以中断服务？"
- "有哪些不可改变的约束（API 签名、数据库结构等）？"

### 步骤二：确定方向

基于访谈结果，确定重构方向：

| 重构类别 | 说明 | 示例 |
|---------|------|------|
| **关注点分离** | 拆分类/方法，明确边界 | 将数据访问、业务逻辑、协议处理分离 |
| **消除重复** | 提取公共代码 | 抽取工具类、公共父类 |
| **简化复杂度** | 简化过长方法/类 | 拆分为多个小方法/类 |
| **改进命名** | 使代码自文档化 | 方法名、变量名反映意图 |
| **引入设计模式** | 用模式解决结构问题 | 策略模式替代if-else链 |
| **测试补全** | 为重构中的代码补充测试 | 先写测试后重构 |

### 步骤三：生成重构计划

按小提交粒度（每个提交只做一个重构点）生成计划：

```markdown
## 重构计划：[模块名称]

### 前置条件
- [ ] 已有足够的测试覆盖（没有则先补充）
- [ ] 当前分支已提交或备份
- [ ] [其他前置条件]

### 提交清单

#### 提交 1：[重构操作描述]
- **目标**：[为什么要做]
- **修改文件**：
  - [文件路径]：[修改内容]
- **验证方法**：[如何验证]
- **回退方式**：[如果出问题怎么回退]

#### 提交 2：[重构操作描述]
- **目标**：[为什么要做]
- **修改文件**：
  - [文件路径]：[修改内容]
- **验证方法**：[如何验证]
- **回退方式**：[如果出问题怎么回退]

### 不动点（明确不修改的内容）
- [什么保持不变]
```

### 步骤四：确认与执行

1. 将重构计划呈现给用户确认
2. 获得确认后，按提交顺序逐一执行
3. 每完成一个提交，立即验证
4. 全部完成后，运行完整测试套件确认无回归

## 输出

```markdown
## 重构计划

### 模块：[名称]

### 当前问题
[描述现状问题]

### 目标
[期望达到的状态]

### 提交计划
| 序号 | 操作 | 文件数 | 风险 | 预估工时 |
|------|------|-------|------|---------|
| 1 | [操作] | [数量] | [低/中/高] | [时间] |
| 2 | [操作] | [数量] | [低/中/高] | [时间] |

### 用户确认
[✅ 已确认 / 待确认]
```
