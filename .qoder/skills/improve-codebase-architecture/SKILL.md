# 改善代码库架构

## 适用情形

当代码库逐渐变成"泥球"时使用：
- 模块越来越多，每个都很"浅"（接口几乎和实现一样复杂）
- 理解一个概念需要在多个小模块之间来回跳转
- 测试难以编写，因为被测单元的接口太大
- 想找人帮你系统性地扫描一遍代码库，找出架构问题

**建议定期运行**，在代码腐化积累到难以收拾之前及时发现。

---

## 架构术语体系

使用以下统一术语描述所有建议，保持输出一致性：

| 术语 | 含义 |
|------|------|
| **模块（Module）** | 任何有接口和实现的东西（函数、类、包、垂直切片） |
| **接口（Interface）** | 调用者需要知道的全部：类型、前置条件、错误模式、调用顺序、配置——**不止是方法签名** |
| **深度（Depth）** | 接口的杠杆率：小接口背后的大行为。**深 = 高杠杆**，**浅 = 接口几乎和实现一样复杂** |
| **接缝（Seam）** | 接口所在的位置；可以在不原地编辑代码的情况下改变行为的地方 |
| **适配器（Adapter）** | 在接缝处满足接口的具体实现 |
| **杠杆（Leverage）** | 调用者从深度中获得的价值——用很少的知识做很多事 |
| **局部性（Locality）** | 维护者从深度中获得的价值——变更、缺陷、知识都集中在一处 |

### 关键原则

- **删除测试**：想象一下删除这个模块。如果复杂度消失了，那它只是一个透传；如果复杂度散到了 N 个调用者身上，那它就在发挥作用
- **一个适配器 = 假设的接缝，两个适配器 = 真实的接缝**
- **接口就是测试面**——测试通过公共接口验证行为

### 不用的词

- ❌ 不用 "组件/Component" — 用 "模块/Module"
- ❌ 不用 "服务/Service" — 用模块的功能描述
- ❌ 不用 "边界/Boundary" — 用 "接缝/Seam"
- ❌ 不用 "API" — 用 "接口/Interface"

## 执行流程

### 步骤一：了解上下文

查阅相关架构文档，了解当前模块的设计意图和已有的决策约束：

- `med_ai_assistant_1.0_bs_backend/doc/系统结构/` — 模块职责和架构描述
- `med_ai_assistant_1.0_bs_backend/doc/原则/` — 设计原则
- `med_ai_assistant_1.0_bs_backend/doc/问题修复/` — 历史问题和已知陷阱

使用这些文档中的术语来描述代码——例如，"病人管理模块"而不是"patient-service"。

### 步骤二：探索代码

使用子智能体遍历代码库。不需要遵循僵化的启发式规则，而是**有机地探索**，在遇到以下"摩擦感"的地方停下来：

1. **理解一个概念需要在多个小模块之间来回跳转** → 可能是模块分得太碎
2. **模块很"浅"** → 接口几乎和实现一样复杂，调用者需要了解太多内部细节
3. **纯函数被提取出来只是为了可测试性** → 但真正的 bug 隐藏在调用方式中（缺乏局部性）
4. **紧耦合模块跨接缝泄漏** → 一个模块的变化导致多个模块跟着改
5. **代码难以通过当前接口测试** → 要么接口太粗，要么测试依赖内部实现

对任何怀疑是"浅"的模块应用**删除测试**：把它删掉——复杂度会集中（好信号）还是散开（浅模块的信号）？

### 步骤三：提出候选

列出编号的**加深机会**。每个候选包含：

```
## 候选 N：[标题]

**涉及文件**：[文件/模块路径]

**问题**：当前架构为什么造成摩擦？

**解决方案**：用自然语言描述要改变什么

**收益**：
- **杠杆**：调用者得到什么简化的接口？
- **局部性**：维护者得到什么集中度？
- **可测试性**：测试会如何变好？
```

> **与已有决策冲突**：如果某个候选与 `doc/原则/` 或历史方案中的决策矛盾，只在矛盾足够严重时才提出来。标记为"与 [某决策] 矛盾——但值得重新审视，因为…"

**不要直接提接口方案**。先问用户："你想深入看哪个？"

### 步骤四：追问循环

用户选定后，进入追问式对话。按设计树的分支逐一深入。

过程中随决策明确**实时执行**以下操作：

1. **术语明确** → 更新 `doc/系统结构/` 中相关模块的文档
2. **模糊概念澄清** → 立即用精确术语替换模糊说法
3. **用户有充分理由拒绝某个候选** → 询问"是否需要在 `doc/其他/` 中记录这个决策，避免以后架构审查重新提出来？"
4. **需要探索不同接口方案** → 使用 [design-an-interface](skill:../skills/design-an-interface/SKILL.md)

## 输出示例

```
## 候选 1：诊断分析查询逻辑散落在三处

**涉及文件**：
- `DiagnosisQueryService.java`（基础查询）
- `DiagnosisFilterService.java`（过滤逻辑）
- `DrgAnalysisService.java`（DRG 专用查询，内部又重写了一遍过滤）

**问题**：同样的按病人+日期范围查询诊断的逻辑在三个类中各写了一遍。
每个类提供的是"浅"接口——调用者需要自己去组合过滤条件。
诊断相关的变更需要同时改三处。

**解决方案**：将诊断查询逻辑收拢到 `DiagnosisQueryService` 中，
提供深接口：`findDiagnoses(patientId, filter, pageable)`。
`DiagnosisFilterService` 合并进来，`DrgAnalysisService` 直接调用。

**收益**：
- **杠杆**：调用者只需知道一个方法和一个 Filter 对象
- **局部性**：查询逻辑变更只需改一处
- **可测试性**：一个测试类覆盖所有查询场景，而不是三个类测同样的边界
```
