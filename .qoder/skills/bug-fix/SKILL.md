# Bug 修复九步法

解决任何 Bug 时**必须严格按顺序执行以下九个步骤**，禁止跳过任何步骤。

> **前提**：修复问题前，先查阅 `med_ai_assistant_1.0_bs_backend/doc/问题修复/` 目录下的历史问题修复文档，确认是否有类似的已记录案例。

---

## 步骤一：复现确认

**目标**：获取完整的错误信息，确认问题可复现。

执行要求：
1. 收集完整的错误日志、错误码、报错信息
2. **明确问题的具体表现、触发条件、影响范围**
3. 对比正常环境/正常情况下的行为差异
4. **代码分析**：检查相关源码，追踪调用链路，定位可疑代码段
5. **依赖分析**：检查相关依赖版本、第三方库兼容性

```
输出格式：
- **问题描述**：[具体错误现象]
- **触发条件**：[什么操作/条件下出现]
- **影响范围**：[哪些用户/功能受影响]
- **正常对比**：[正常环境下是什么表现]
- **可能根因**（初步）：
  1. [最可能的原因] - 证据：[...]
  2. [次可能的原因] - 证据：[...]
```

---

## 步骤二：隔离问题层

**目标**：将问题归类到具体的层面，不确定根因时不改代码。

执行要求：
1. 判断问题属于哪一层：**代码 / 配置 / 网络 / 环境**
2. 如果无法确定根因，**优先排查环境和配置**，而不是改代码
3. 通过排除法缩小范围
4. **日志与配置检查**：查看错误日志、应用配置、环境变量等

```
输出格式：
- **问题归类**：[代码/配置/网络/环境]
- **已排除**：[已确认正常的层面]
- **锁定范围**：[疑似有问题的层面]
```

---

## 步骤三：逐层诊断

**目标**：由内到外逐层排查，一次只查一个点，记录每步结果。

执行要求：
1. 按照 **由内到外** 的顺序排查（如：应用本身 → 容器 → 操作系统 → 网络 → 防火墙 → 外部依赖）
2. **一次只查一个点**，记录每一步的排查结果
3. 不要同时修改多个配置或多个环节

常见诊断链路示例（网络类问题）：
```
DNS解析 → IP转发 → 防火墙规则 → nftables/iptables → 抓包验证 → hosts映射 → 容器网络模式
```

```
输出格式：
### 逐层诊断记录
| 诊断层 | 排查命令/方法 | 结果 | 结论 |
|-------|-------------|------|------|
| [层名] | [命令] | [正常/异常] | [是否排除] |
```

---

## 步骤四：定位根因

**目标**：因果链必须能解释所有已观察到的现象。

执行要求：
1. **列出根因清单**：按可能性从高到低列出所有潜在原因
2. 根因必须能**完整解释**步骤一中观察到的所有异常现象
3. 如果存在多个因素，说明它们是如何叠加导致问题的
4. 确认根因后，再进入后续步骤

```
输出格式：
### 根因分析
- **根因**：[一句话说明]
- **因果链**：[A导致B，B导致C...]
- **涉及因素**：[如：因素1 + 因素2 + 因素3 叠加导致]
- **证据清单**：
  - [证据1]
  - [证据2]
```

---

## 步骤五：网络检索最佳实践

**目标**：搜索该类问题的业界最佳实践和已验证的解决方案。

执行要求：
1. **关键词提炼**：从步骤四的根因中提取精准搜索关键词
2. **多维度检索**：
   - 搜索错误信息、异常类型的通用解决方案
   - 查找相关框架/库的官方文档和已知问题
   - 参考 Stack Overflow、GitHub Issues 等社区经验
   - 查阅相关技术博客和最佳实践文章
3. **方案收集**：整理搜索到的可行方案，记录来源和适用条件

```
输出格式：
### 最佳实践检索结果
- **方案A**：[描述] - 来源：[URL/文档]
  - 优点：[...]
  - 局限：[...]
- **方案B**：[描述] - 来源：[URL/文档]
  - 优点：[...]
  - 局限：[...]
```

---

## 步骤六：拟定解决方案

**目标**：综合前序步骤的成果，制定具体的解决方案。

执行要求：
1. **方案选型**：对比各候选方案，选择最适合当前项目的方案
2. **修改范围界定**：明确需要修改的文件和配置位置
3. **影响评估**：评估修改对其他模块的影响
4. **风险识别**：列出潜在风险和回退策略
5. **向用户确认**：将方案呈现给用户，获得确认后再执行

```
输出格式：
### 解决方案
- **选定方案**：[方案描述]
- **选择理由**：[为什么选这个方案]
- **修改范围**：
  - [文件/配置路径1]：[修改内容概述]
  - [文件/配置路径2]：[修改内容概述]
- **影响评估**：[对其他模块的影响]
- **风险点**：
  1. [风险描述] - 缓解措施：[...]
- **回退策略**：[如果修改失败如何回退]
```

---

## 步骤七：最小化修复

**目标**：影响面最小，一次只修一个问题。

执行要求：
1. 选择**影响范围最小**的修复方案
2. **一次只修一个问题**，不连带修改无关内容
3. 明确每项修改的目标和方式
4. **增量验证**：每完成一个修改点，立即验证其正确性

```
输出格式：
### 修复方案
- **方案描述**：[具体修改内容]
- **影响范围**：[仅影响xxx]
- **修改项**：
  1. [修改点1] - [目的]
  2. [修改点2] - [目的]
```

---

## 步骤八：验证

**目标**：逐层验证修复效果，确认无副作用。

执行要求：
1. **连通性验证** → **功能验证** → **持久性验证（reload后）** → **副作用检查**
2. 按此顺序逐步确认
3. **回归测试**：确保修改不会引入新问题
4. 重启/reload 后再次验证，确保修复持久有效
5. 检查其他相关功能是否受影响

```
输出格式：
### 验证结果
| 验证项 | 方法 | 结果 |
|-------|------|------|
| 连通性 | [方法] | ✅/❌ |
| 功能正常 | [方法] | ✅/❌ |
| 重启持久性 | [reload后验证] | ✅/❌ |
| 副作用检查 | [检查其他功能] | ✅/❌ |
```

---

## 步骤九：文档化

**目标**：记录问题修复过程，形成可复用的知识。

执行要求：
1. 记录到 `med_ai_assistant_1.0_bs_backend/doc/问题修复/` 目录
2. 包含：问题描述、根因、修复方案、可复用的诊断命令
3. 文档命名格式：`yyyy-MM-dd-简短描述.md`
4. **保留完整的调研和决策过程**，便于后续追溯

---

## 三条铁律

> **铁律一：不确认根因，不改代码**
> 必须先排查环境和配置，确认根因后再修改，禁止猜测式修改。不可未调研就直接改代码。

> **铁律二：一次只改一个变量**
> 改一个验证一个，否则无法确定哪个修改生效。

> **铁律三：禁止大范围变更**
> 大范围变更（如 `network_mode: host`）往往引发全面故障，一旦失败需要全量回滚，风险极高。
