## 二、系统架构与技术实现方式

### 2.1 整体架构

系统采用**前后端分离 + 双服务器分离**架构，由以下组件构成：

```
┌─────────────────────────────────────────────────────────────────┐
│                         前端应用层                                │
│              Vue 3 + Element Plus（运行于浏览器）                  │
└──────────────────────────┬──────────────────────────────────────┘
                           │ Nginx反向代理（HTTPS）
                           ▼
┌─────────────────────────────────────────────────────────────────┐
│                       主服务器（Main Server）                      │
│                    Spring Boot 3.5.x + Java 21                    │
│   • 接收HTTP请求，业务逻辑编排                                   │
│   • JWT令牌认证、用户权限管理                                     │
│   • 创建AI执行任务、结果查询                                       │
│   • 健康检查、系统监控、审计日志                                   │
└──────────┬──────────────────────────────────────┬────────────────┘
           │                                      │
           ▼                                      ▼
┌──────────────────┐                  ┌──────────────────────────┐
│   主数据源        │                  │   执行数据源              │
│   Oracle 21c     │                  │   Oracle 21c             │
│   (业务数据)      │                  │   ENCRYPTED_DATA_TEMP表  │
└──────────────────┘                  └──────────┬───────────────┘
                                                 │ 轮询机制
                                                 ▼
┌─────────────────────────────────────────────────────────────────┐
│                    执行服务器（Execution Server）                   │
│                    Spring Boot 3.5.x + Java 21                    │
│   • 轮询加密数据临时表                                             │
│   • 解密敏感数据 → 调用AI模型 → 加密结果                           │
│   • 异步处理，与主服务器解耦                                       │
└─────────────────────────────────────────────────────────────────┘
```

## 三、数据走向（安全视角）

### 3.1 数据来源

- 系统仅从**医院内网Oracle数据库**读取在院患者的医疗数据（患者基本信息、诊断、病历、检验检查、医嘱），不做写回HIS/EMR操作
- 所有数据通过**内网专线**传输，不经过公网

### 3.2 数据加密流转

```
主服务器 ──AES-256加密──→ ENCRYPTED_DATA_TEMP表（密文）──轮询读取──→ 执行服务器
                                                                         │
                                                   内存中AES-256解密 → 调用AI模型
                                                                         │
                                                   返回结果AES-256加密 ←────────┘
执行服务器 ──写回密文──→ ENCRYPTED_DATA_TEMP表──主服务器轮询解密──→ 结果存入业务库
```

**关键安全措施**：
- 敏感数据全程以AES-256-CBC密文形式存储在临时表中，**明文永不落地**
- 解密仅在进程内存中完成，处理完毕后立即清理
- 主服务器与执行服务器通过临时表异步解耦，不直接网络互通
- 每次加密使用随机IV（初始化向量），确保相同数据每次密文不同

### 3.3 网络安全边界

- 前端 → Nginx：HTTPS加密传输
- Nginx → 主服务器：内网HTTP，Nginx终止SSL
- 主服务器 → Oracle数据库：内网Oracle Net协议
- 执行服务器 → AI模型API：仅出站HTTPS，可配置IP白名单
- 所有服务部署于**医院内网**，对外不暴露端口（AI调用除外）

## 四、数据安全与隐私保护

### 4.1 安全架构分层

| 安全层 | 措施 |
|--------|------|
| **网络层** | HTTPS/TLS加密传输、防火墙配置、内网部署隔离 |
| **应用层** | Spring Security、JWT令牌认证（HMAC-SHA256）、会话无状态管理 |
| **数据层** | AES-256-CBC加密（敏感数据）、Argon2密码哈希、PBKDF2密钥派生 |
| **接口层** | Jakarta Bean Validation参数校验、限流控制、错误码规范化 |
| **审计层** | 完整操作日志审计、数据变更追踪 |

### 4.2 数据加密机制

- **传输加密**：全程采用AES-256-CBC算法，随机IV（初始化向量），PKCS5Padding填充
- **密钥管理**：密钥与盐值存储于数据库配置表，不同环境隔离，支持密钥轮换
- **加密流程**：主服务器加密 → 写入临时表（密文）→ 执行服务器读取解密 → 调用AI → 结果加密写回 → 主服务器解密读取
- **明文不落地**：敏感数据在整个流转过程中以密文形式存储于数据库，仅在服务进程内存中解密，处理完成后立即清理

### 4.3 认证与授权

- 采用JWT（JSON Web Token）无状态认证方案
- 令牌默认24小时过期，HMAC-SHA256签名
- 基于角色的访问控制（RBAC）
- 登录密码采用Argon2安全哈希算法存储
- 支持用户激活/停用状态管理

### 4.4 数据隔离

- 系统仅读取患者医疗数据（在院患者），不做写回HIS/EMR操作
- 所有AI分析结果以辅助参考形式呈现，最终临床决策权在医生
- 不与外部互联网直接互通，通过内网专线/VPN与医院信息系统对接

## 五、系统可靠性与容错机制

| 机制 | 说明 |
|------|------|
| **双服务器解耦** | 主服务器与执行服务器分离，AI调用故障不影响主业务流程 |
| **异步轮询** | 主-执间通过数据库临时表异步通信，避免同步阻塞 |
| **连接池管理** | HikariCP连接池（最大5连接），HttpClient连接池（最大200连接） |
| **超时控制** | HTTP连接超时3s、Socket超时5min、请求超时10s |
| **自动恢复** | 内置AutoRecoveryEngine自动故障恢复机制 |
| **健康检查** | 数据库连接、网络状态、系统资源实时监控 |
| **重试机制** | AI调用支持指数退避重试、熔断保护 |
| **限流保护** | 请求频率限制和队列管理 |
| **日志追溯** | 请求ID贯穿全链路，支持问题定位 |

│  医生工作站   │────▶│             医院内网核心交换机                    │
│  (浏览器)     │     └────┬────────────┬────────────┬─────────────────┘
└──────────────┘          │            │            │
                          ▼            ▼            ▼
                   ┌──────────┐ ┌──────────┐ ┌──────────┐

                   │ 代理服务  │ │ :8081    │ │ :8082    │
                   └──────────┘ └──────────┘ └──────────┘
                          │            │            │
                          ▼            ▼            ▼
                   ┌──────────────────────────────────────┐

### 6.2 硬件配置建议

| 服务器角色 | CPU | 内存 | 硬盘 | 数量 |
|-----------|-----|------|------|------|
| **主服务器** | 4核+ | 8GB+ | 100GB SSD | 1台 |
| **执行服务器** | 4核+ | 16GB+ | 100GB SSD | 1台 |
| **Oracle数据库** | 8核+ | 16GB+ | 500GB+ | 由医院现有环境提供 |

## 七、风险分析与应对措施

### 7.1 数据安全风险

| 风险项 | 风险等级 | 应对措施 |
|--------|---------|----------|
| 患者隐私数据泄露 | 高 | AES-256全链路加密，明文不落地，最小权限原则 |
| 数据库未授权访问 | 高 | 仅限内网访问，绑定IP白名单，最小权限数据库账户 |
| JWT令牌劫持 | 中 | HMAC-SHA256签名，24小时过期，HTTPS传输 |
| AI模型输出敏感信息 | 中 | AI返回结果经过脱敏后存储，不包含明文患者标识 |

### 7.2 系统可靠性与业务连续性风险

| 风险项 | 风险等级 | 应对措施 |
|--------|---------|----------|
| 主服务器单点故障 | 中 | 支持水平扩展部署，Docker容器化快速恢复 |
| AI模型外部服务不可用 | 中 | 异步解耦，AI调用失败不影响主业务，支持重试与降级 |
| 数据库连接异常 | 中 | HikariCP健康检查、自动重连、自动恢复引擎 |
| 网络中断 | 中 | 重试机制、状态机确保数据一致性、幂等性设计 |

### 7.3 临床使用风险

| 风险项 | 风险等级 | 应对措施 |
|--------|---------|----------|
| AI建议误导诊疗 | 中 | AI结果仅作辅助参考，不替代医生决策，前端明确标注"AI建议仅供参考" |
| 数据同步延迟 | 低 | 定时任务轮询同步，状态可追溯，医生可手动刷新 |
| 误操作导致数据问题 | 低 | 操作审计日志完整记录，支持数据回溯 |
