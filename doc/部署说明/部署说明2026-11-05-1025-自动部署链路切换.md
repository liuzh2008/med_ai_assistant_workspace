### 0.1 本次上线与常规部署的**顺序差异（必须遵守）**

常规顺序是"后端 → 前端"。本次因为**主服务器要从执行服务器的制品库拉文件**，所以：

```
执行服务器先升级（提供 /api/build-files/* 新端点 + 写制品库）
        ↓
主服务器再升级（从 8082 拉 jar / zip）
        ↓
前端最后（从 8082 拉 zip）
```

顺序颠倒会出现：主服务器下载 `404`（执行服务器还是旧代码，没有 `/artifact/**` 端点）。

### 0.2 生产现用手动部署方式（基线，自动链路出问题时用它兜底）

> 自动链路本质上就是把下面三件事自动化；手动方式永远保留，作为回退手段。
> **路径以本节为准**（2026-11-05 与现场核对）。

**后端**

```bash
cd /opt/medai/backend
chmod +x ./deploy.sh
./deploy.sh
```

**前端**

```bash
cd /opt/medai/frontend
chmod +x ./deploy-from-package.sh
./deploy-from-package.sh
```

前置：把构建好的文件复制到生产服务器：
- 前端包 → `/opt/medai/frontend/docker/med_ai_assistant_1.0_bs_vue.zip`（`deploy-from-package.sh` 解压到 `/opt/medai/frontend/docker/med_ai_assistant_1.0_bs_vue/`，并要求包内含 `medai-images.tar`）
- 后端包 → `/opt/medai/backend/`（含 `deploy.sh`、`med-ai-main.tar`、compose、config）

**执行服务器**

```bash
# 备份原 execution-linux 目录（如果存在）
\mv /opt/medai/execution /opt/medai/execution-backup
# 解压 zip 到 /opt/，覆盖写入
unzip -o /tmp/execution-linux.zip -d /opt/

cd /opt/medai/execution
chmod +x deploy.sh
./deploy.sh
```

> 注意：`\mv` 之前先确认 `/opt/medai/execution-backup` 是否已被上一次备份占用（重复执行会覆盖旧备份）。

### 0.3 自动链路与手动方式的对应关系

| 端 | 手动方式 | 自动方式（本次上线） | 生产路径 |
|---|---|---|---|
| 主服务器 | `cd /opt/medai/backend && ./deploy.sh` | `auto-deploy-backend.sh`（拉 jar + 本地构建后调同一个 `deploy.sh`） | `/opt/medai/backend` |
| 前端 | `cd /root && ./deploy-from-package.sh` | `auto-deploy-frontend.sh`（下载 zip；包内含 `medai-images.tar` 时调同一个脚本，不含时退化为 `deploy-linux.sh --build`） | `/root` + `/root/docker/` |
| 执行服务器 | 解压 zip 到 `/opt/medai/execution` 后 `./deploy.sh` | `gitee-pull-release.sh`（拉 jar + 离线构建后调同一个 `deploy.sh`） | `/opt/medai/execution` |

> 三条自动链路最终都调用**同一个 `deploy.sh` / `deploy-from-package.sh`**，所以自动与手动部署结果一致。

## 7. 风险与注意事项

1. **顺序不可颠倒**：执行服务器未升级前，主服务器的 `/api/build-files/artifact/**` 会 404。
2. **基座镜像必须先导入两端**：否则两端的 `docker build` 会失败（`FROM med-ai-jre-base:21` 找不到）。
3. **不要覆盖 `.env` / `config`**：脚本只增缺失键，部署时不要手工替换这两个文件。
4. **首次手工执行要绕过安全窗口**：`auto-deploy-backend.sh` / `auto-deploy-frontend.sh` 默认只在 02:30–03:30 执行，手工执行需 `DEPLOY_ALLOW_OUTSIDE_WINDOW=true`。
5. **`gitee-pull-release.sh` 无安全窗口限制**：手工执行会立即部署，请避开业务高峰。
6. **前端包可能不含镜像 tar**：若开发机发布时 Docker 未启动，包为 8.9MB，`deploy-linux.sh` 会走 `--build`，依赖生产已有 `nginx:1.25-alpine`。
7. **Gitee token 不落盘**：`publish-release.ps1` 从测试服容器读取；生产脚本不需要 token（执行服务器从 Gitee 拉取时由 `GITEE_ACCESS_TOKEN` 提供）。

## 9. 预演结论

- **链路可用**：执行服务器 → 主服务器 → 前端 三端均通过新产物链路升级到 0.9.304；
- **自动化程度**：除首次导入基座镜像、安装 timer 外，日常升级只需开发机一条发布命令；
- **生产差异**：预演用 `DEPLOY_DIR` 覆盖了生产路径；生产路径 `/root/docker/...` 与脚本默认值一致，无需覆盖；

## 附录 B 常见报错对照

| 现象 | 原因 | 处置 |
|---|---|---|
| `artifact http=404` | 执行服务器仍是旧镜像（无 `/artifact/**` 端点） | 先完成 3.2 执行服务器升级 |
| `docker build` 报 `FROM med-ai-jre-base:21` 找不到 | 基座镜像未导入 | 两端执行 `publish-base-image.sh` / `import-base-image.sh` |
| `下载失败（第 N 次）` 连续 4 次 | Gitee 不可达或 token 失效 | 检查 `GITEE_ACCESS_TOKEN`、`curl -sI https://gitee.com` |
| `分卷校验失败` | 下载不完整 | 加 `FORCE_DEPLOY=true` 重跑；Gitee 不支持断点续传，脚本会整卷重下 |
| `健康检查超时，回滚` | 新版本启动失败 | 看 `docker logs med-ai-execution-server -n 200`，常见 `ORA-` / `BeanCreationException` |
| `缺少基座镜像`（timer 安装时） | 未导入基座 | 先执行第 3 步的基座镜像步骤 |
| 主服务器 `latest.json` 一直为空 | 执行服务器 `cache-dir` 配置未生效 | 确认 `application-execution.properties` 含 `github.release.cache-dir=/medai/build-files`，重启容器 |
| 部署后端时在**前端目录**找 `deploy.sh`（`chmod: 无法访问 './deploy.sh'`） | 队列 service 里设了全局 `DEPLOY_DIR`（前端目录），后端脚本继承了这个变量 | worker 按 `component` 选目录：`BACKEND_DEPLOY_DIR` / `FRONTEND_DEPLOY_DIR`；**不要把全局 `DEPLOY_DIR` 写进 service** |
| `project has been loaded without an explicit name from a symlink. Using name "backend"` + `container name "/med-ai-main-redis" is already in use` | 从 `/opt/medai/backend`（软链接）进入部署目录，compose 项目名被推断成 `backend`，与既有项目 `main-linux-testserver` 冲突 | `BACKEND_DEPLOY_DIR` 指向**真实目录**（非软链接）；或给 compose 显式加 `-p <既有项目名>` |
| 后端部署报 `sha256 校验失败`（换过制品库包之后） | 制品库里的 `deploy` 包换了，但 `manifest` 里的 `deployPackage.sha256/size` 还是旧值 | 重算并更新 manifest 的 `artifacts.deployPackage`；换 jar/分卷时同理 |
| 部署“成功”但功能回退（页面刷新 404 / 前端没有 apply 逻辑 / 镜像里没有 `/app/version.txt`） | **版本号没变但代码改了**：制品库/Gitee 上仍是旧包。部署链路只认版本号，不会感知代码变化 | 改代码后必须**重新发布**：推荐 `bump-version.ps1` 升版本号；若要复用同版本号，必须同时更新**该版本的全部产物**（jar / deploy 包 / 前端 zip）并**同步 manifest 的 sha256/size**，否则部署会拉回旧包 |
