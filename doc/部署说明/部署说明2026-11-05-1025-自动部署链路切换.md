### 0.1 本次上线与常规部署的**顺序差异（必须遵守）**

常规顺序是"后端 → 前端"。本次因为**主服务器要从执行服务器的制品库拉文件**，所以：

```
执行服务器先升级（提供 /api/build-files/* 新端点 + 写制品库）
        ↓
主服务器再升级（从 8082 拉 jar / zip）
        ↓
前端最后（从 8082 拉 zip）
```

顺序颠倒会出现：主服务器下载 `404`（执行服务器还是旧代码，没有 `/artifact/**` 端点）。

## 7. 风险与注意事项

1. **顺序不可颠倒**：执行服务器未升级前，主服务器的 `/api/build-files/artifact/**` 会 404。
2. **基座镜像必须先导入两端**：否则两端的 `docker build` 会失败（`FROM med-ai-jre-base:21` 找不到）。
3. **不要覆盖 `.env` / `config`**：脚本只增缺失键，部署时不要手工替换这两个文件。
4. **首次手工执行要绕过安全窗口**：`auto-deploy-backend.sh` / `auto-deploy-frontend.sh` 默认只在 02:30–03:30 执行，手工执行需 `DEPLOY_ALLOW_OUTSIDE_WINDOW=true`。
5. **`gitee-pull-release.sh` 无安全窗口限制**：手工执行会立即部署，请避开业务高峰。
6. **前端包可能不含镜像 tar**：若开发机发布时 Docker 未启动，包为 8.9MB，`deploy-linux.sh` 会走 `--build`，依赖生产已有 `nginx:1.25-alpine`。
7. **Gitee token 不落盘**：`publish-release.ps1` 从测试服容器读取；生产脚本不需要 token（执行服务器从 Gitee 拉取时由 `GITEE_ACCESS_TOKEN` 提供）。

## 附录 B 常见报错对照

| 现象 | 原因 | 处置 |
|---|---|---|
| `artifact http=404` | 执行服务器仍是旧镜像（无 `/artifact/**` 端点） | 先完成 3.2 执行服务器升级 |
| `docker build` 报 `FROM med-ai-jre-base:21` 找不到 | 基座镜像未导入 | 两端执行 `publish-base-image.sh` / `import-base-image.sh` |
| `下载失败（第 N 次）` 连续 4 次 | Gitee 不可达或 token 失效 | 检查 `GITEE_ACCESS_TOKEN`、`curl -sI https://gitee.com` |
| `分卷校验失败` | 下载不完整 | 加 `FORCE_DEPLOY=true` 重跑；Gitee 不支持断点续传，脚本会整卷重下 |
| `健康检查超时，回滚` | 新版本启动失败 | 看 `docker logs med-ai-execution-server -n 200`，常见 `ORA-` / `BeanCreationException` |
| `缺少基座镜像`（timer 安装时） | 未导入基座 | 先执行第 3 步的基座镜像步骤 |
| 主服务器 `latest.json` 一直为空 | 执行服务器 `cache-dir` 配置未生效 | 确认 `application-execution.properties` 含 `github.release.cache-dir=/medai/build-files`，重启容器 |
