# 成熟软件更新策略调研（面向 MedAI 内外网双节点场景）

> 调研时间：2026-11-04
> 目的：为 MedAI（Vue 前端 + Spring Boot 主服务器 + 执行服务器）的更新流程选型，明确「哪些是行业共识、哪些不适合本院环境、哪些可以立刻落地」。
> 结论优先：本项目**不需要也不应该上 K8s/GitOps**，真正缺的是**制品不可变化、优雅停机、前端缓存策略、数据库 expand-contract** 四件事。

---

## 一、策略谱系总览

| 策略 | 做法 | 切换粒度 | 回滚速度 | 资源成本 | 适用场景 | 对本项目 |
|---|---|---|---|---|---|---|
| **Recreate（重建）** | 停旧 → 起新 | 全量 | 分钟级（重新起旧镜像） | 1 份 | 内网单机、非 7×24 | ✅ 当前做法，可保留 |
| **RollingUpdate（滚动）** | 逐个替换实例 | 实例 | 秒级 | N+1 | 多副本、K8s | ⚠️ 双节点可做，但无副本概念 |
| **Blue-Green（蓝绿）** | 两套环境并存，路由切换 | 全量原子切换 | **秒级（切回路由）** | 2 份 | 需要快速回滚、可接受双倍资源 | ⭐ 最契合本项目 |
| **Canary（金丝雀）** | 小比例流量先看新版 | 按比例/特征 | 秒级（摘流量） | 1.1~1.5 份 | 用户量大、可观测完善 | ⚠️ 医院用户按科室可做简化版 |
| **A/B 测试** | 两版并行做业务对比 | 按分组 | — | 2 份 | 验证产品假设 | ❌ 与发布无关，别混用 |
| **Feature Flag（功能开关）** | 代码合并但开关控制可见性 | 按开关 | 秒级 | 0 | 功能级灰度 | ✅ 前端已有部分开关雏形 |
| **Shadow（影子流量）** | 复制流量到新版不返回结果 | 全量 | — | 2 份 | 高风险的算法/模型升级 | ❌ 成本高，收益有限 |

参考：[Martin Fowler: BlueGreenDeployment](https://martinfowler.com/bliki/BlueGreenDeployment.html)、[CanaryRelease](https://martinfowler.com/bliki/CanaryRelease.html)。

**蓝绿的关键细节**（Fowler 原文）：
- 两套环境要「尽量一致但独立」，切的是**路由器**而不是重启服务；
- 蓝绿天然是**热备**，等于每次发布都演练一次容灾；
- **数据库是最大难点**：正确顺序是「先做 schema 变更（同时兼容新旧）→ 部署 → 验证 → 再部署新应用 → 稳定后清理旧结构」，而不是应用和 schema 一起切。

## 二、零停机的四个必要条件（无论哪种策略）

来自 Spring Boot 官方与阿里云 ACK 的实践，四条缺一不可：

1. **优雅停机**：Spring Boot 2.3+ 默认开启，SIGTERM 后进入「宽限期」，已有请求继续处理、新请求被拒（网络层直接不接）。宽限期由 `spring.lifecycle.timeout-per-shutdown-phase` 控制（默认 30s，建议按最长请求调大）。
   [Spring Boot: Graceful Shutdown](https://docs.spring.io/spring-boot/reference/web/graceful-shutdown.html)
2. **就绪探针（readiness）**：新实例必须「能接流量」才加入负载均衡——Spring Boot 的 `/actuator/health/readiness` 就是干这个的。
3. **连接排空（draining）**：K8s 用 `preStop` + `terminationGracePeriodSeconds`；Compose 用 `stop_grace_period`。没有排空，正在跑的 LLM 长请求会被硬断。
4. **先加后减**：新实例就绪后才摘旧实例（滚动更新 `maxSurge`/`maxUnavailable` 的本质）。
   参考：[阿里云 ACK 零停机滚动更新](https://www.alibabacloud.com/help/en/ack/ack-managed-and-ack-dedicated/user-guide/achieve-zero-downtime-rolling-deployments)、[Qovery: zero downtime on k8s](https://www.qovery.com/blog/how-to-achieve-zero-downtime-application-with-kubernetes)

> 注意：本项目有**长耗时请求**（LLM 生成 30~60s、批量 Prompt 轮询），宽限期必须大于最长请求时间，否则「优雅停机」形同虚设。

## 三、数据库变更：expand-contract（行业标准做法）

核心思想：**把 schema 变更拆成两次发布**，让新旧应用版本可以共存。

```
Expand（扩展）  → 加新列/新表，双写，旧代码照常跑
Backfill（回填）→ 把旧数据迁到新结构
Contract（收缩）→ 新代码只读新结构，确认稳定后删旧列
```

参考：[xata: expand-contract with pgroll](https://xata.io/blog/pgroll-expand-contract)；Fowler 蓝绿文中的「先 schema 后应用」也是同一原则。

**对本项目的直接含义**（Oracle、当前 SQL 手工执行、无 Flyway）：
- 加列可以随时做（向下兼容）；**删列/改类型必须等应用稳定后单独发一次**；
- SQL 脚本必须**幂等**（可重复执行不报错），并在 `doc/部署清单.md` 登记执行顺序；
- 不要在发布窗口里「一把梭」执行大字段变更（Oracle DDL 会锁表）。

## 四、前端发布：内容哈希 + 短缓存（当前最缺的一环）

成熟做法（[阿里云开发者社区：CDN 缓存键、灰度刷新与回源策略](https://developer.aliyun.com/article/1763184)）：

| 资源 | 缓存策略 | 原因 |
|---|---|---|
| `index.html` | `Cache-Control: no-cache` 或 `max-age=60, must-revalidate` | 它是入口，必须尽快指向新资源 |
| `app.<hash>.js` / `*.css` | `max-age=31536000, immutable` | 文件名带内容哈希，内容变了文件名就变 |
| API 响应 | 不缓存 | — |

配套三条经验：
1. **灰度时缓存键要带版本维度**，否则新旧版本共用一个缓存键会串味；
2. 刷新 CDN 要**分批 + 预热**，一次性 purge 会打爆源站；
3. 「用户看到旧页面」先分层定位（浏览器 / CDN / 源站 Nginx / 应用缓存），别只刷一层。

> 本项目现状：`index.html` 与静态资源同一套缓存头，用户经常需要「强刷」。这是前端更新的第一痛点。

## 五、内网/离线（air-gapped）环境的交付实践

行业做法（[Semaphore: Air-Gapped Deployments](https://semaphore.io/blog/air-gapped-deployments-how-to-deploy-to-servers-without-internet-access-complete-guide)）：

1. **交付制品而非源码**：镜像 tar / zip + 清单（manifest），版本号不可变；
2. **完整性校验**：发布包带 SHA256，落地后先校验再部署（本项目 `auto-deploy-backend.sh` 已有 manifest 校验，是加分项）；
3. **私有制品库**：Harbor / Nexus 或**内网文件服务器**（本项目用执行服务器 `/medai/build-files` 承担这个角色）；
4. **变更单 + 介质传递**：离线环境没有「pull」，只有「搬运」，所以每次发布要有可追溯的包与版本记录；
5. **可重复构建**：同一个 commit 能构建出同一个产物，便于回滚与审计。

> 结论：本项目已有的「构建 tar → 投放 → 校验 → 备份 → 部署 → 失败回滚」骨架是对的，缺的是**生成这些制品的脚本化**和**命名统一**。

## 六、多副本/多实例与定时任务（本项目的高风险点）

行业共识：**有状态定时任务在多实例下必须互斥**，否则新旧实例并存期间任务会跑两遍（本项目 `@Scheduled` 不少：Prompt 轮询、EMR 质控、模板同步、规则同步）。

可选方案（按侵入性排序）：
1. **ShedLock**（Spring 生态标准做法）：数据库表当锁，`@SchedulerLock` 注解，多实例只有一个执行；
2. `@Profile` / 配置开关：只让一个节点跑定时任务（本项目已有 profile 区分，最简单）；
3. 部署序列控制：先停旧、再起新（Recreate 天然规避，蓝绿不规避）。

参考：[ShedLock 与 Spring 指南](https://baeldung.cn/shedlock-spring)

## 七、对本项目的落地建议（按投入产出排序）

### P0：立刻能做，1~3 天

| # | 事项 | 依据 | 收益 |
|---|---|---|---|
| 1 | 补齐**制品打包脚本**：统一命名 `med_ai_assistant_{backend,execution,frontend}-<ver>.tar/zip` + manifest(SHA256) | §五 | 自动部署链路不再靠手工放包 |
| 2 | 部署脚本加 **stop_grace_period** 与 `spring.lifecycle.timeout-per-shutdown-phase=120s` | §二 | 发布不再硬断 LLM 长请求 |
| 3 | 前端 nginx：`index.html` 短缓存 + 带 hash 资源长缓存 | §四 | 用户不用强刷 |
| 4 | 发布前**自动健康检查 + 失败自动回滚**（现有 auto-deploy 已有，补到手动 deploy.sh） | §二 | 手工发布也安全 |

### P1：1~2 周

| # | 事项 | 依据 | 收益 |
|---|---|---|---|
| 5 | 数据库变更遵循 **expand-contract**，SQL 幂等 + 版本化目录 | §三 | 回滚不再依赖「反向 SQL」 |
| 6 | 定时任务加 **ShedLock** 或明确「只在一个节点启用」 | §六 | 杜绝双实例重复执行 |
| 7 | 蓝绿简化版：主服务器保留 `med-ai-main-blue/green` 两个 compose 项目，nginx upstream 切换 | §一 | 回滚从分钟级降到秒级 |

### P2：有余力再做

| # | 事项 | 说明 |
|---|---|---|
| 8 | 按科室灰度（Canary 简化版） | 前端/网关按 `HOSPITAL_DEFAULT_ID` 或科室白名单分流 |
| 9 | 内网 Harbor/Nexus | 当前 `/medai/build-files` 已够用，上 Harbor 主要是为了签名与权限 |
| 10 | 可观测性（发布后 5 分钟看错误率/延迟） | 决定自动回滚的触发条件 |

### 明确不建议

- **K8s / GitOps（Argo CD、Flux）**：本院无 K8s，且引入一套控制面带来的运维成本远超收益；
- **Shadow 流量**：LLM 调用有成本，影子流量等于双倍计费；
- **A/B 测试当发布手段**：统计显著性需要天级数据，发布需要分钟级收敛，两者目标不同。

---

## 八、一句话总结

> 成熟更新策略的核心不是「蓝绿/金丝雀」这些名词，而是四件底层能力：**制品不可变且可校验、实例优雅停机、流量先加后减、数据库变更有兼容窗口**。本项目在「备份 + 回滚 + manifest 校验」上已经有基础，补齐这四件即可达到行业主流水平，不需要引入 K8s。
