# R9700 单卡 400 tok/s 可行性验证报告

**日期**：2026-11-03
**目标**：在「R9700 单卡 + 64 GB 内存」约束下，验证能否达到 **400 tok/s 总产能**
**结论**：**不能。** 在全部可获得的引擎/模型组合下，单卡 R9700 的聚合吞吐上限约 **161 tok/s**（Strata + 125B MoE，Windows）；Linux 上最优只有 **121 tok/s**。400 tok/s 需要 4 张卡或 HBM 级显卡。

---

## 一、测试目标与验收口径

| 项 | 内容 |
|---|---|
| 硬件约束 | R9700 32 GB 单卡 + 62 GiB 内存 |
| 目标 | **400 tok/s**（单服务器聚合产能） |
| 判定 | 聚合吞吐能否达到 400 tok/s；单流吞吐作为参考 |
| 环境 | 2026-11-03 由 Windows 切换到 Ubuntu 24.04 |

## 三、测试过程

### 阶段 1：环境验证（00:31–00:45）

**结论：硬件与内核驱动就绪。**

```bash
# KFD 已识别设备
kfd kfd: amdgpu: added device 1002:7551
kfd kfd: amdgpu: Total number of KFD nodes to be created: 1

# VRAM
/sys/class/drm/card1/device/mem_info_vram_total = 34208743424 (31.86 GiB)
```

容器内验证（`rocm/rocm-terminal`，ROCm 6.4）：

```
Agent 2
  Name:  gfx1201
  Marketing Name:  AMD Radeon Graphics
```

### 阶段 2：磁盘规划（00:37–00:45）

根分区 24 GB，先做隔离：

```bash
# /opt/rocm 绑到 /data（后来发现 ROCm 库主要落在 /usr，此措施无效）
/data/rocm /opt/rocm none bind 0 0
```

**事故**：原生安装 ROCm（`amdgpu-install --usecase=rocm`）时**根分区写满**，`dpkg` 中断：

```
dpkg: 处理归档 ... 时出错： 写入失败 (设备上没有空间)
dpkg: 无法恢复的致命错误，中止
```

**后果**：`/tmp` 无法创建临时目录，所有 shell 类工具（bash/glob/grep）连续三轮启动失败：

```
ENOSPC: no space left on device, mkdtemp '/tmp/dsh-subprocess-launch-XXXXXX'
```

**恢复**：清理 apt 缓存、`/tmp/apt-dpkg-install-*`、`/var/lib/dpkg/updates/tmp.i` 后修复 `dpkg --configure -a`，根分区回到 12 GB 可用。

**结论：放弃原生 ROCm，改容器路线。**

### 阶段 3：Docker 与存储迁移（00:50–01:05）

```bash
apt install -y docker.io
# daemon.json: {"data-root": "/data/docker", "registry-mirrors": ["https://docker.m.daocloud.io"]}
```

**发现**：Ubuntu 的 docker.io 29.x 使用 **containerd snapshotter**（`driver-type: io.containerd.snapshotter.v1`），镜像层实际写 `/var/lib/containerd`，**无视 `data-root`**。首次拉 `rocm-terminal`（4.16 GB）时系统盘被占 9.5 GB。

**修复**：

```bash
containerd config default > /etc/containerd/config.toml
# root = '/data/containerd'
rm -rf /var/lib/containerd
```

验证：拉 `rocm-terminal` 后 `/data/containerd` = 3973 MB，`/var/lib/containerd` = 1 MB，**根分区不变**。

### 阶段 4：模型下载（01:17–01:24，09:16–09:24）

| 模型 | 大小 | 用途 | 结果 |
|---|---|---|---|
| `unsloth/Qwen3.8-27B-GGUF` Q4_K_M | 16 GB | llama.cpp | ✅ |
| `Qwen/Qwen3.8-27B-FP8` | 29 GB | vLLM | ❌ 后删 |
| `amd/Qwen3.8-27B-Quark-AWQ-MXFP4` | 19 GB | vLLM | ✅ 保留 |
| `cyankiwi/Qwen3.8-27B-AWQ-INT4` | 20 GB | vLLM | ❌ 后删 |
| `Launch80/Qwen3.8-27B-PARO-MXFP4` | 18 GB | radiance 配套 | ✅ |

**踩坑**：
1. HuggingFace 直连不通，必须 `HF_ENDPOINT=https://hf-mirror.com`
2. hf-mirror **不支持 Xet 存储**，需 `HF_HUB_DISABLE_XET=1`，否则报 `401 Unauthorized ... cas-server.xethub.hf.co`
3. 用容器内 Python 下载会以 root 写文件，后续 `rm` 需 `sudo`

### 阶段 5：vLLM 路线（02:00–02:15）—— **三种量化全部失败**

镜像：`vllm/vllm-openai-rocm:latest`（46.8 GB，vLLM 0.32.0，torch 2.13.0）

#### 5.1 FP8（28.75 GiB）→ 显存不足

```
torch.OutOfMemoryError: CUDA out of memory. Tried to allocate 288.00 MiB.
GPU 0 has a total capacity of 31.86 GiB of which 32.00 MiB is free.
```

权重加载完只剩 32 MB，装不下 KV。

#### 5.2 Quark MXFP4（18.4 GiB）→ 不支持原生 MXFP4

```
WARNING [quark_ocp_mx.py:91] The current platform does not support native MXFP4/MXFP6
computation. Simulated weight dequantization and activation QDQ will be used,
with the linear layers computed in high precision.
WARNING [emulation.py:91] Using EmulationMxfp4LinearKernel
→ torch.OutOfMemoryError: Tried to allocate 768.00 MiB（权重被展开成高精度）
```

**关键**：官方 vLLM 镜像**没有 RDNA4 的原生 MXFP4/FP8 WMMA kernel**，只能模拟反量化，导致显存爆炸。

#### 5.3 AWQ INT4（19.44 GiB）→ GPU kernel 崩溃

```
Memory access fault by GPU node-1 (Agent handle: 0x5eb78420) on address 0x7aae2a20f000.
Reason: Page not present or supervisor privilege.
```

崩溃点在 `RDNAHybridW4A16LinearKernel`——这是 kernel bug，不是显存问题。调 `gpu-memory-utilization 0.85` + `--enforce-eager` 无法规避。

### 阶段 6：radiance 定制镜像（07:39–08:30）—— **未能拉取**

第三方 385.8 tok/s 依赖 `stilldeadcode/vllm-radiance:0.9.3`（Dockerfile 是四阶段源码构建：torch 2.11 + triton 3.6 + vLLM 0.27.1 + aiter 0.1.17 + 20 多个 gfx1201 补丁 + libr4d 手写 HIP kernel）。

| 源 | 结果 |
|---|---|
| `dockerproxy.net` | 能下但**不支持 Range 续传**，2.6 GB 大层必断：`failed to discard to offset: unexpected EOF`；后 502 |
| `docker.m.daocloud.io` | `403 Forbidden` |
| `docker.1ms.run` | `magic number mismatch`（层损坏） |
| `docker.xuanyuan.me` | `403 Forbidden` |
| Docker Hub 直连 | 超时 |

用 `skopeo copy` 重试同样卡在同一处：

```
fatal: unexpected EOF (after reconnecting, server did not process a Range: header, status 200)
```

**结论**：镜像不可得（需要代理）。配套模型 PARO-MXFP4 已下好备用。

### 阶段 7：llama.cpp（09:30–10:00）—— **实测基准**

镜像：`ghcr.io/ggml-org/llama.cpp:server-rocm`（30.7 GB，自带 ROCm 运行时与编译好的二进制）

模型：`Qwen3.8-27B-UD-Q4_K_M.gguf`（16 GB，全层上 GPU）

| 配置 | 每路 tok/s | 聚合 tok/s |
|---|---|---|
| 单流 | **30.1** | 30.1 |
| 4 路并发 | 22.2 | **85.1** |
| 8 路并发 | 13.9 | **105.2** |

prompt 处理：28 token / 202 ms ≈ 138 tok/s。

**分析**：27B Q4 每 token 需读约 16 GB 权重，640 GB/s ÷ 16 GB = **40 tok/s 理论上限**，实测 30.1 = **75% 效率**。并发扩展性差（8 路仅 3.5 倍），与第三方同卡数据（峰值 95.7 @ n=2）吻合。

### 阶段 8：Strata + Flash-Next 125B/6B MoE（10:45–11:19）—— **Linux 比 Windows 慢 40%**

#### 8.1 安装

```bash
STRATA_DATA_DIR=/data/strata STRATA_BIN_DIR=/data/strata/bin sh install-strata.sh
# Terminal 0.1.56（95 MB，签名校验通过）
strata update --backend hip --no-control
# Engine 0.1.56 linux-x86_64-hip-rx9070（test-start 通过）
```

模型用 Windows 分区上的（只读挂载）：
- `/mnt/win-data/Strata/Models/models/Q2_0/`（36 GB + 27 GB）
- `/mnt/win-data/Strata/Models/mtp/rt`
- `/mnt/win-data/Strata/Models/packs/q2_0`

NTFS 只读读取实测 **920 MB/s**。

#### 8.2 关键卡点：`hipErrorNoDevice`

首次启动报：

```
strata generate: native embedding: cannot pin 260 MiB: no ROCm-capable device is detected
hipGetDeviceCount: Returned hipErrorNoDevice
```

用 `strace` 定位到**真正原因不是版本，是权限**：

```
openat(AT_FDCWD, "/dev/kfd", O_RDWR|O_CLOEXEC) = -1 EACCES (权限不够)
```

当前 shell 会话的组未刷新（`usermod -aG render,video` 只对新登录生效）。用 `sg render -c '<命令>'` 包裹后引擎正常：

```
strata generate: opened 2 GPU queues in a fixed order
strata generate: PCIe probe: 47.0 GB/s host->device
strata: gfx12 (RDNA4): 12 exact speed switches on by default
```

#### 8.3 基准结果

| 配置 | 单流 tok/s | 8 路聚合 tok/s | expert cache |
|---|---|---|---|
| Linux 原版（ctx 131072 / ple direct） | **79–84** | **121.0**（每路 15.1） | 6406 slots / 8.25 GiB |
| Linux 调优（ctx 65536 / `--ple-io mmap`） | **76–78** | 未测 | 6492 slots / 8.36 GiB |
| **Windows**（参照） | **140** | **161** | 16384 slots / **21.6 GiB** |

#### 8.4 调优实验（均无效）

| 调优 | 预期 | 实测 |
|---|---|---|
| `--ple-io mmap`（针对 `PLE direct 4904 rows/s` 警告） | 加载/prompt 提速 | 单流无提升 |
| `--max-context 131072 → 65536` | 省 KV 给 expert cache | cache 仅 6406 → 6492（**几乎没变**） |

**结论**：KV 不是挤占 expert cache 的原因；`--ple-io` 也不是瓶颈。命中率已达 96.5–97%，但 cache 只有 8.36 GiB（Windows 21.6 GiB），差距来自**引擎的显存分配策略**。

显存账对不上：cache 8.36 + prompt borrow 2.7 + free 1.7 + projections 2 + MTP 0.2 ≈ **15 GiB**，卡有 31.86 GiB，**约 16 GiB 闲置未用**。

## 四、汇总结果

| 引擎 / 平台 | 模型 | 单流 tok/s | 聚合 tok/s | 结论 |
|---|---|---|---|---|
| **Strata / Windows** | Flash-Next 125B/6B MoE Q2_0 | **140** | **161**（8 路） | **最优** |
| Strata / Linux | 同上 | 79–84 | 121（8 路） | 比 Windows 慢 40% |
| llama.cpp / Linux | Qwen3.8-27B dense Q4 | 30.1 | 105.2（8 路） | 远低于目标 |
| vLLM 官方 / Linux | 27B（FP8 / Quark / AWQ） | — | — | **三种量化全部启动失败** |
| vLLM radiance / Linux | 27B MXFP4 | ~20 | 385.8（n=24，第三方） | 差 4%，镜像不可得 |

**400 tok/s 目标：全部组合未达成。** 最接近的是第三方 radiance 的 385.8，但它差 4%、复现门槛极高（源码级定制 + 镜像不可得），且每路仅 16 tok/s。

---

## 五、关键发现

1. **硬件无短板**：KFD、gfx1201、PCIe 47 GB/s、VRAM 31.86 GiB 全部正常；ROCm 在容器内可完整工作。
2. **Linux 不是升级**：同一张卡、同一引擎逻辑，Linux 版只给 8.36 GiB expert cache，Windows 给 21.6 GiB，单流 78 vs 140。
3. **官方 vLLM 镜像不支持 RDNA4 原生低比特**：MXFP4 走模拟反量化、AWQ kernel 崩溃，这是官方镜像的空白区。
4. **llama.cpp 的天花板由带宽决定**：27B Q4 单流理论上限 40 tok/s，实测 30（75% 效率），不能靠调参突破。
5. **385.8 的真实性**：数据内部自洽（16.08 × 24 = 386，KV 池与带宽利用率可解释），但依赖不可得的定制栈，**不可复现**。
6. **磁盘是隐藏雷区**：24 GB 根分区装不下 ROCm；docker.io 29.x 的 containerd snapshotter 绕过 `data-root`；GPU 崩溃报告会写 `/var/lib/apport`（本次 2.1 GB）。

## 六、建议

### 6.1 立即

- **保留 Windows + Strata 作为生产环境**（单流 140 / 8 路 161，实测最优）。
- 删除本次未用上的模型与镜像，`/data` 可回收约 165 GB。

### 6.2 若要 400 tok/s

| 方案 | 产能 | 成本 | 风险 |
|---|---|---|---|
| **4 × R9700 跑副本** | **560 tok/s**（4 × 140） | 约 6.4 万 | 最低，模型与质量零改动 |
| 1 × H200 级 | 1500+ tok/s | 约 25 万 | 需重做整个栈 |
| 27B + radiance | 385.8（差 4%） | 时间成本极高 | 镜像不可得、单请求延迟放大 8 倍 |

**推荐 4 卡副本**。

### 6.3 可反馈给 Strata 的问题（带证据）

1. Linux 版引擎给 8.36 GiB expert cache，Windows 给 21.6 GiB，**约 16 GiB 显存闲置**，单流因此 78 vs 140。
2. `--ple-io direct` 在本机 NTFS 上只有 4904 rows/s（20 MB/s），引擎自身警告可能触发 stall watchdog。
3. Windows + AMD 组合官方未测（0.2.9 release notes 明示）。

  rocm/rocm-terminal:latest rocminfo | grep -E 'gfx|Marketing'
