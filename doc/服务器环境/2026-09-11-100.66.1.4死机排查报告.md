# 100.66.1.4 死机事件排查报告（2026-09-11）

> **事件**：测试服务器 100.66.1.4 于 2026-09-11 22:03 起服务不可达，22:35:49 后系统完全无响应，
> **22:58:50 重启**（无正常关机记录，判定为强制重启）后恢复。
> **排查方式**：`journalctl -b -1`（上一次启动日志）+ 内核日志 + apt/unattended 记录 + `last -x`。
> **结论**：**物理内存耗尽（global OOM）叠加 swap 耗尽**，系统进入内存抖动后完全卡死。
> **配套**：硬件配置见同目录《100.66.1.4-硬件配置.md》

## 三、根因判定

### 3.1 直接原因：物理内存耗尽（global OOM）

关键证据（内核日志原文）：

```
9月 11 22:33:39 kernel: systemd-resolve invoked oom-killer: gfp_mask=0x140cca(GFP_HIGHUSER_MOVABLE|__GFP_COMP), order=0, oom_score_adj=0
9月 11 22:33:43 kernel: oom-kill:constraint=CONSTRAINT_NONE,nodemask=(null),cpuset=systemd-resolved.service,
                         mems_allowed=0,global_oom,task_memcg=/user.slice/.../xdg-desktop-portal-gnome.service,
                         task=xdg-desktop-por,pid=3472,uid=1000
9月 11 22:33:43 kernel: Out of memory: Killed process 3472 (xdg-desktop-por) total-vm:1510168kB, anon-rss:1664kB, ...
```

- `global_oom`（非 cgroup 局部限制）表示**整机物理内存 + swap 全部耗尽**；
- 被杀对象是桌面组件，说明连 GUI 会话都在争抢内存；
- 同一时刻内核打印了完整进程快照，主体为**大量 Oracle XE 进程**。

### 3.2 加剧因素

| 因素 | 说明 |
|---|---|
| **swap 早已耗尽** | 4 GiB `/swap.img` 在故障前已接近 100% 占用（2026-09-07 实测记录：swap 99.98%、`Committed_AS` 超卖 25.6 G vs CommitLimit 12.2 G） |
| **4.5 个月未重启** | 自 2026-04-25 起连续运行，页缓存/内存碎片持续累积 |
| **Oracle XE 多进程常驻** | OOM 快照中数十个 `oracle_*`、`ora_m00x_xe`、`ora_j00x_xe` 进程，单个虚拟内存 ≈ 512 MB |
| **7 个 Docker 容器** | `med-ai-main`(Java+容器未限内存)、`med-ai-execution-server`、`medteach-backend`、3 个前端、Redis、Oracle — Java 服务堆内存叠加 |
| **GNOME 桌面环境** | 服务器为笔记本且带图形界面（`xdg-desktop-portal-gnome`、`update-manager` 等），额外占用数百 MB |
| **本次构建任务** | 21:45 启动的 `npm run build`（Node 堆上限 2 GB）在 15.3 GiB 整机上加压；OOM 快照中仅见 `node` 27 MB，说明构建进程此时已结束或已被回收，**属诱因/加速因素而非唯一原因** |
| **suspend 反复失败** | 22:03 起 `systemd-logind` 持续尝试挂起并失败（`suspend.target is masked`），反复重试消耗资源，且与"22:03:51 服务全面不可达"时间吻合 |

### 3.3 死机形态

22:35:49 后日志完全静止 23 分钟、`last -x` 无 shutdown 记录、重启后内核发生大版本切换 →
判定为**系统在内存抖动中彻底失去响应（未完成正常关机流程）**，由人工**强制断电/长按电源键重启**恢复。

### 3.4 死机时的 7 个 Docker 容器与内存配额

| # | 容器名 | 镜像 | 内存上限 | 重启前运行时长 | 说明 |
|---|---|---|---|---|---|
| 1 | `med-ai-oracle` | `gvenzl/oracle-xe:21-slim-faststart` | **3 GiB** | 4 个月 | Oracle XE 数据库；OOM 快照中数十个 `ora_m00x_xe` / `oracle_*` 进程（UID 54321）即其子进程 |
| 2 | `med-ai-main` | `med-ai-main:latest`（容器内跑 0.9.281） | **无限制（0）** | 9 天 | MedAi 主后端 Java 服务；**无内存上限，可涨至整机上限** |
| 3 | `med-ai-execution-server` | `med-ai-execution:latest` | **8 GiB** | 3 天 | MedAi 执行服务 Java；单容器限额已超整机内存一半 |
| 4 | `med-ai-main-redis` | `redis:7.2` | 无限制 | 12 天 | 主后端依赖的 Redis；**重启后当前状态为 `Exited (255)`** |
| 5 | `med-ai-assistant-frontend` | `med-ai-assistant-frontend:latest` | 无限制 | 2 周 | MedAi 前端 Nginx（8080/8443） |
| 6 | `medteach-backend` | `medteach-backend:latest` | **1 GiB** | 3 天 | AIMedTeach 教学后端（8083） |
| 7 | `medteach-frontend` | `medteach-frontend:latest` | 无限制 | 2 天 | AIMedTeach 教学前端 Nginx（8085） |

> 数量核对：`docker ps -aq | wc -l` = **7**；OOM 时刻内核快照中亦有 6 个 `containerd-shim`（+容器内进程）与之对应。

**配额风险（关键）**：仅显式设置的内存上限之和即 **3 + 8 + 1 = 12 GiB**，
而 `med-ai-main` 与 3 个前端容器**均无限制**，可继续增长 —— 在 15.3 GiB 整机上属**严重超卖**：
分配给容器的上限已接近物理内存总量，宿主机、GNOME 桌面与任何构建任务都只能挤占剩余空间，
**OOM 属结构性必然，而非偶发事故**。

## 四、结论

1. **死机根因是内存耗尽（global OOM）**：15.3 GiB 物理内存 + 4 GiB swap 被 Oracle XE、7 个 Docker 容器、GNOME 桌面长期占满，本次构建任务成为压垮内存的最后一根稻草。
2. **22:03 的服务不可达**与 `logind` 反复挂起失败同步出现，早于 OOM 判定 30 分钟——系统在 OOM 前已进入异常状态（疑似合盖/挂起事件触发、失败后未能恢复）。
3. **本次部署操作（在服务器上跑 2 GB 堆的 `npm run build`）是重要诱因**，在可用内存仅约 3.8 GiB 的机器上属高风险操作；应避免在测试服务器上直接构建前端。
4. 服务器**并非硬件故障**：重启后温度 73 °C（正常）、电池 100% Full、磁盘 366 G 可用、无 thermal throttling 与 NVMe 报错。

## 五、处置建议

| 优先级 | 建议 | 说明 |
|---|---|---|
| **P0** | **禁止在 100.66.1.4 上直接执行前端构建**（`npm run build` 等大内存任务） | 改为本地/构建机构建后上传产物（AIMedTeach 已按此模式） |
| **P0** | 给 `med-ai-main` 容器**设置内存上限** | 目前未限（历史实测：单容器可涨至 15.34 G 上限），建议 `mem_limit: 2g` 级别并按实际负载校准 |
| **P1** | 扩大 swap 或调整 `vm.swappiness` | 4 GiB swap 对 15.3 GiB 内存 + Oracle + Docker 明显不足 |
| **P1** | 关闭或精简图形桌面（服务器无需 GUI） | 可释放数百 MB 并消除 `xdg-desktop-portal` 类 OOM 目标 |
| **P1** | 建立内存监控告警 | 如 `MemAvailable < 2 GiB` 或 swap 使用 > 80% 时告警 |
| **P2** | 明确 `suspend.target` 被 mask 的配置来源 | 现状是"想挂起但被禁止→反复失败"，应彻底禁用挂起触发源（合盖行为设为 `ignore`） |
| **P2** | 定期重启或滚动重启服务 | 缓解 4.5 个月连续运行带来的内存碎片与泄漏累积 |
| **P2** | 安装 `lm-sensors` + `smartmontools` | 补齐温度/风扇/磁盘健康监控（当前无数据） |
