### 1.4 最大教训（Top 5）

1. **绝不在测试服务器上跑前端构建**：该机可用内存仅 ~3.8 GiB，`NODE_OPTIONS=--max-old-space-size=2048 npm run build` 属高危；改为本地构建、只上传 9 MB 的 dist。
2. **"没有内存上限的容器"是定时炸弹**：`med-ai-main` 长期无限制（历史实测可涨至 15.34 G），与 8 G 限额的 execution、3 G 的 Oracle 叠加即已超卖整机。
3. **组网环境下 ping/TCP 探测全是"代答"，不可作为判据**：必须看 nblink service 日志（`mapping succ` / `net_measure`）与 curl 的真实响应体。
4. **自动部署脚本会挂起**：`git-poll-deploy.sh` 的 `restart_main_server` 用无 `--force-recreate` 的 `docker compose up -d`，09-11 20:32:48 卡死导致整条自动部署链中断（前端未构建、容器未重建）。
5. **产物包会覆盖服务器侧配置**：`deploy-from-package.sh` 用 `unzip -o` 释放 zip，包内 `docker-compose.yml` 是构建时快照 → 部署后必须重新覆盖并重建。

## 五、阶段二：网络中断（"假通"诊断）

### 5.1 现象

- `ping 100.66.1.4` **通**（<1 ms，TTL=64）
- `Test-NetConnection`：22 / 8080 / 8081 / 8083 / 8085 / 1521 **全部 True**（0 s 即返回）
- 但 `curl` 全部 **HTTP 000**（25 s 超时亦无响应）；`ssh` 卡在 **`Connection timed out during banner exchange`**

### 5.2 排查过程（全部无效，最终由服务器重启解决）

| 动作 | 结果 |
|---|---|
| 重启 nblink 客户端（`--cmd=autorun`，新 PID 16656） | 无效 |
| `Restart-Service NodeBabyLinkService` | 无效 |
| 停 `aTrustService` 验证（30 s 后恢复 Running） | **无效 → 排除 aTrust 干扰** |
| 长超时探测（25 s）、多轮 ssh 重试、分批短命令 | 仅在 22:33:53 抓到一次 HTTP 200 |
| 检查其他节点（devpc 100.66.1.1） | **同样不可达** → 非单机问题 |

### 5.3 正确判据（本次沉淀）

组网（节点小宝）下**所有本地探测都可能被客户端代答**，唯一可信的两类证据：

1. **nblink service 日志**（`C:\Program Files (x86)\nblink\logs\NodeBabyLinkService.log`）：
   ```
   [TCP] conn 100.66.1.4:8081 -> 10.222.222.1:53176
   [TCP] 100.66.1.4:8081 -> ...OW 127.0.0.1:8081 mapping succ
   [TCP] ... closed sent 0 recv 104 err EOF          ← 建连成功但无数据、8 s 后 EOF
   ppcore/net_measure.go: lanNum 0  npt num/rated 4/4  relay num/rated 0/0   ← 无可用数据通道
   ```
   结论：**隧道能建立映射（所以 TCP "连上"），但数据通道不转发** → 问题在服务器侧。
2. **真实 HTTP 响应体**（而非端口状态）。

同时确认 `ping` 与 `Test-NetConnection` 对**任何** 100.66.1.x 地址都返回"通"，属代答假象。

### 5.4 与网络故障的并行事实

22:03 起 `systemd-logind` 同时开始**反复尝试 suspend 并失败**：
```
systemd-logind[1146]: Suspending...
systemd-logind[1146]: Unit suspend.target is masked, refusing operation.
systemd-logind[1146]: Failed to execute suspend operation: Permission denied
```
该状态持续到 22:33（整场日志中累计出现 **312,872 次**，最早可追溯至 5 月 18 日）。
推测存在"合盖/空闲触发的挂起请求"，而 `suspend.target` 被人为 mask，导致**请求-失败-重试**空转，
与 22:03:51 服务全面不可达时间吻合（该假设列为本报告待确认项之一）。

## 六、阶段三：死机根因（global OOM）

### 6.1 证据链（`journalctl -b -1`）

```
9月11 22:33:39 kernel: systemd-resolve invoked oom-killer: gfp_mask=0x140cca(...), order=0, oom_score_adj=0
9月11 22:33:42 kernel: Node 0 Normal free:67628kB  min:67948kB   ← 已跌破内存水位线
9月11 22:33:42 kernel: Free swap = 168kB   Total swap = 4194300kB  ← swap 仅剩 168 kB
9月11 22:33:43 kernel: oom-kill:constraint=CONSTRAINT_NONE,...,global_oom,
                       task_memcg=.../xdg-desktop-portal-gnome.service,task=xdg-desktop-por,pid=3472
9月11 22:33:43 kernel: Out of memory: Killed process 3472 (xdg-desktop-por)
9月11 22:33:43 kernel: [进程快照] 数十个 ora_m00x_xe / oracle_* (UID 54321, 单个 total-vm ≈512 MB)
9月11 22:35:37/49      systemd-resolved: Using degraded feature set ...   ← 最后两条日志
22:35:49 → 22:58:50    日志完全静止（23 分钟）→ 强制重启
```

### 6.2 根因判定

- **`global_oom`**（非 cgroup 局部限制）：整机物理内存 + swap 全部耗尽；
- 被杀对象是**桌面组件**（连 GUI 都在争抢内存）；
- 内存主体：**Oracle XE 数十个子进程** + **7 个 Docker 容器** + **GNOME 桌面**；
- 加剧因素：自 **2026-04-25** 连续运行 4.5 个月、swap 早已耗尽、**本次服务器端 2 GB 堆构建**。

### 6.3 与本次操作的关联（如实记录）

- 21:45 在服务器启动 `NODE_OPTIONS=--max-old-space-size=2048 npm run build`，在可用内存仅 ~3.8 GiB 的机器上额外申请 2 GB 堆；
- OOM 快照中可见 `npm run build`（PID 2900212）与 `npm exec vue-cli`（2822331）、`vue-cl` 等进程；
- **诚实结论**：本次构建是**重要诱因/最后一根稻草**，但**不是唯一原因** —— 容器配额超卖（下表）使 OOM 成为结构性必然。

### 6.4 死机前的 7 个容器与配额审计（用户专项提问）

| # | 容器 | 镜像 | 内存上限 | 运行时长 | 说明 |
|---|---|---|---|---|---|
| 1 | `med-ai-oracle` | `gvenzl/oracle-xe:21-slim-faststart` | 3 GiB | 4 个月 | OOM 快照中数十个 `ora_*` 即其子进程 |
| 2 | `med-ai-main` | `med-ai-main:latest`（跑 0.9.281） | **无限制（0）** | 9 天 | 可涨至整机上限 |
| 3 | `med-ai-execution-server` | `med-ai-execution:latest` | 8 GiB | 3 天 | 单容器限额 > 整机一半 |
| 4 | `med-ai-main-redis` | `redis:7.2` | **无限制** | 12 天 | 重启后状态 `Exited (255)` |
| 5 | `med-ai-assistant-frontend` | `med-ai-assistant-frontend:latest` | **无限制** | 2 周 | — |
| 6 | `medteach-backend` | `medteach-backend:latest` | 1 GiB | 3 天 | 镜像 ENV `-Xmx1g` 恰好顶满容器上限 |
| 7 | `medteach-frontend` | `medteach-frontend:latest` | **无限制** | 2 天 | — |

`docker ps -aq | wc -l` = **7**；OOM 内核快照中 6 个 `containerd-shim` 与之对应。

> **配额风险**：显式限额之和 = 3 + 8 + 1 = **12 GiB**，另有 4 个容器无限制，
> 而整机仅 **15.3 GiB** —— 分配给容器的上限已逼近物理内存总量，OOM 属必然。

| `medteach-frontend` | **无限制** | **128 MiB** | — |
| **合计** | 12 GiB + 4 无限制 | **≈ 8.0 GiB** | 留 ≈7 GiB 给宿主机 |

除 Oracle 外，6 个容器均设 `memswap_limit = mem_limit`，**禁用容器 swap**（避免 swap 抖动拖死整机）。

### 8.2 实施方式（不污染生产）

1. **compose 用变量插值并保留生产默认值**：
   ```yaml
   mem_limit: ${MAIN_MEM_LIMIT:-1536m}
   memswap_limit: ${MAIN_MEM_LIMIT:-1536m}
   # execution（生产不设变量时回退原值）
   mem_limit: ${EXECUTION_MEM_LIMIT:-8g}
   memswap_limit: ${EXECUTION_MEM_LIMIT:-16g}
   ```
2. **测试专属值写入服务器本地 `.local` env**（`.gitignore` 未跟踪、`git pull` 不覆盖）：
   - `deploy/main-linux-testServer/.env.main.local`（**新建**）：`JAVA_OPTS`、`MAIN_MEM_LIMIT=1536m`、`REDIS_MEM_LIMIT=256m`
   - `deploy/execution-linux/.env.execution.local`（**追加**）：`EXECUTION_MEM_LIMIT=2g`、`JAVA_OPTS`（原有 `ORACLE_HOST/SERVICE` 适配保留）
   - 二者经 `--env-file` 传入：**既参与 compose 变量插值，又覆盖 `env_file` 同名变量（后列文件优先）**。
3. **验证解析结果**（`docker compose config`）+ **重建容器**（`up -d --force-recreate`）。

## 十、踩坑与经验（可复用）

### 10.1 网络与组网

| # | 坑 | 正确做法 |
|---|---|---|
| 1 | 组网下 `ping` / `Test-NetConnection` 全为**代答**，制造"通"的假象 | 只信 nblink service 日志与 curl 真实响应体 |
| 2 | devpc（100.66.1.1）同样不可达时误判为单机问题 | 多 peer 同时不可达 → 优先怀疑本机/链路而非目标机 |
| 3 | aTrust 与节点小宝都管 `100.66.1.x`，疑似冲突 | 本次实测**停 aTrust 无效**，可排除；但 aTrust WFP 间歇干扰仍是历史已知项 |
| 4 | 服务器死机时"TCP 能连"误导排查方向 | 隧道仅完成 mapping，应用层无响应 = 目标机侧问题 |

### 10.2 编码与命令传输

| # | 坑 | 正确做法 |
|---|---|---|
| 5 | PowerShell→ssh 传中文路径（`公共`）被 GBK 乱码成 `鍏叡` | 改用符号链接 **`/home/liuzh2008/public/`**；脚本保持纯 ASCII |
| 6 | `ssh host "cmd"` 中的引号/括号被吞（`lscpu \| grep -E "CPU\(s\)"` 报 bash 语法错） | 用 `Get-Content -Raw x.sh \| ssh testserver "tr -d '\r' \| bash -s"` 传脚本；或改用无引号命令（`head -N`） |
| 7 | 本地 CRLF 文件上传后 YAML/shell 解析异常 | 上传后统一 `sed -i 's/\r$//'` |

### 10.3 Docker 与部署

| # | 坑 | 正确做法 |
|---|---|---|
| 8 | **无内存上限的容器**与超卖配额 → 全局 OOM | 每个容器都设 `mem_limit`，并让 `memswap_limit = mem_limit` 禁容器 swap |
| 9 | JVM 堆顶满容器上限（`-Xmx1g` + limit 1g）→ 直接被 cgroup OOM-kill | 容器上限 = 堆 + 元空间 + 300–500 MB 非堆余量 |
| 10 | `deploy-from-package.sh` 的 `unzip -o` 用包内旧 compose 覆盖服务器配置 | 部署后重新覆盖 compose 并 `--force-recreate` |
| 11 | `git-poll-deploy.sh` 的 `restart_main_server` 无 `--force-recreate` 会挂起，中断整条自动部署链 | 手动部署显式加 `--force-recreate` 并用 `timeout` 包裹 |
| 12 | 容器 resize 后 `docker stats` 才反映真实限制 | 用 `docker inspect --format '{{.HostConfig.Memory}}'` 核对 |

### 10.4 流程与判断

| # | 坑 | 正确做法 |
|---|---|---|
| 13 | 在内存紧张的服务器上跑大内存构建 | 本地/构建机构建，只上传产物（dist 9 MB vs 服务器跑 2 GB 堆） |
| 14 | 误以为"代码已 git pull = 已部署" | 必须核对**容器内实际版本**（启动日志 / jar / version.txt） |
| 15 | 只用 `docker ps` 的 `Up X days` 判断部署时间 | 结合 `docker inspect .State.StartedAt`、镜像 `CreatedAt`、日志版本号 |
