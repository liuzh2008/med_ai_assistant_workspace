# 显存带宽对并发的影响（调研）

**日期**：2026-11-02
**范围**：本地部署 MoE 大模型的 decode 阶段，显存带宽与并发（batch / parallel slots）的关系
**本机背景**：R9700 32 GB（640 GB/s）+ Qwen3.8-Flash-Next GSQ-RCO Q2_0（MoE 125B / 6B 激活，512 专家 × 48 层）
**方法**：纯文献与公开资料调研 + 对本机既有实测数据的再分析（**本次未做新压测**）

---

## 摘要

三个层次的结论，从确定到不确定：

1. **decode 阶段是 memory-bound，这是共识**。每生成 1 个 token 就要把参与计算的权重字节搬一遍，算术强度只有 ~1 FLOP/Byte，而现代 GPU 的算力/带宽比高达 300–600 FLOP/Byte，所以算力绝大部分时间在等数据。
2. **dense 模型的 batch 是"免费摊销"**：权重读一次可以服务 N 个 token，吞吐接近线性增长，直到撞上算力墙。
3. **MoE 破坏了第 2 条**：每个 token 路由到不同专家，batch 里 N 个 token 会触碰 N 组不同专家，**专家权重无法跨 batch 复用**。这是本机"8 路只涨 1.63 倍"的结构性原因。

**但要修正一个过度简化的说法**：本机实测反算出的有效带宽只占峰值的 30–50%，说明"带宽"不是唯一的墙，还叠加了 kernel 效率、量化反解（dequant）、WDDM 开销。**换更高带宽的卡能抬高上限，但不能把 1.63 倍变成 8 倍。**

---

## 一、理论：decode 为什么是 memory-bound

### 1.1 算术强度与 roofline

算术强度（arithmetic intensity）定义为单位内存字节承载的浮点运算量：

```
算术强度 = FLOPs / Bytes
```

roofline 模型把它与硬件的"算力/带宽比"（machine balance）比较：低于该比值 → memory-bound；高于 → compute-bound。

### 1.2 dense 模型 decode 的计算

以 70B FP16 生成 1 个 token（batch=1）为例：

| 项 | 数值 |
|---|---|
| 搬运字节 | 70 × 10⁹ 参数 × 2 B = **140 GB** |
| 浮点运算 | 约 **140 GFLOP** |
| 算术强度 | **≈ 1 FLOP/Byte** |

对照 H100：算力 2000 TFLOPs（FP16），带宽 3.35 TB/s → machine balance **≈ 597 FLOP/Byte**。

算术强度比 machine balance 低近 600 倍 → **GPU 计算核心 >95% 的时间在等 HBM 传输**。这就是"decode 是 memory-bound"的定量含义。

> 依据：[What is GPU VRAM bandwidth and why is decoding memory-bound](https://raw.githubusercontent.com/mchittineni/ultimate-ai-engineering-guide/0710d370fa110d02b3bf0c508ab9606c1896959f/ai-system-design/what-is-gpu-vram-bandwidth-and-why-is-decoding-memory-bound.md)（含 H100 数值与 roofline 推导）；roofline 原始出处 Williams, Waterman & Patterson, *Roofline* (CACM 2009)。

### 1.3 由此得到的单流上限公式

```
理论最大 tok/s ≈ 显存带宽 / 每个 token 需要搬运的字节数
```

这条公式解释了两件事：

- **量化能提速**：字节数减少 → 上限提高。同模型 Q8 → Q4 理论上接近 2 倍（实际上受 kernel 与精度权衡限制）。
- **换同带宽的卡不提速**：这正是本机 RTX 5070（≈672 GB/s）→ R9700（640 GB/s）实测几乎没变（106 vs 99–140 tok/s）的原因。R9700 规格为 32 GB GDDR6 / 256-bit / **约 640 GB/s**、300 W、INT4 约 1531 TOPS（[规格汇总](https://www.c114.net.cn/industry/17802.html)）；RTX 5070 12 GB 为 GDDR7 192-bit / 28 Gbps / **672 GB/s**（[ComputerBase 规格条目](https://www.computerbase.de/preisvergleich/?cat=gra16_512&xf=132_4096%7E3312_7.5%7E653_NVIDIA)）。

## 二、dense 模型：batch 是"免费摊销"

### 2.1 机制

dense 模型里，所有 token 走同一套权重。batch=N 时，**同一轮权重搬运服务 N 个 token**：

```
算术强度 ≈ N FLOP/Byte
```

于是吞吐近似 N 倍增长，直到 N × 1 追平 machine balance（进入 compute-bound 区）。Harvard CS249r 教材对此的表述是：小 batch 的 dense 推理只能用掉算力的很小一部分，因为单样本执行缺乏跨样本复用（[Machine Learning Systems Vol1](https://harvard-edge.github.io/cs249r_book_dev/vol1/assets/downloads/Machine-Learning-Systems-Vol1.pdf)）。

### 2.2 实测对照（同架构 MoE 引擎在另一硬件上的公开记录）

一份第三方 MoE 推理引擎（strixllama）的 decode 预算文档给出了可直接类比的实测：

- **不开投机解码**：4 路并发 47.1 tok/s 聚合 vs 单路 19.0 → **2.5 倍**；
- 其解释是"权重字节每 batch 只读一次"（weight bytes are read once per batch）；
- **但这是在有大量共享部分（trunk/attention/shared expert）的前提下**。

> 依据：[Where a decoded token's time goes](https://raw.githubusercontent.com/rulith-dev/strixllama/b38940510c88f4714ef6df6ac6d4ac6098ab3765/docs/decode-budget.md)（该项目自报大投影实测 204–213 GB/s，属小带宽机器；机制与本文相关，绝对数值不可搬到 R9700）。

## 三、MoE：batch 摊销为什么会失效

这是本次调研最关键的机制，也是本机 8 路只涨 1.63 倍的根因。

### 3.1 同一份文档的明确论述

> "A MoE model breaks the usual assumption that batching is free. With 512 experts and 10 active per token, a verification batch of n tokens touches more experts than a batch of one, so the verify cost genuinely scales with the batch — unlike a dense model, where a 4-token verify costs about what a 1-token decode costs."

翻译要点：**512 专家、每 token 激活 10 个；batch 里 n 个 token 触碰的专家数多于 1 个 token，所以成本随 batch 真实增长**——dense 模型里 4 token 的验证成本和 1 token 解码差不多，MoE 不成立。

### 3.2 量化公式（同一文档实测拟合）

```
单步耗时 ≈ 30 ms + 1 ms × 本轮触碰的不同专家数
```

batch 从 1 增到 32 时，触碰的**不同专家数**：

| batch（token 数/步） | 1 | 4 | 8 | 16 | 32 |
|---|---|---|---|---|---|
| 不同专家数 | **10** | **39** | **76** | **139** | **238** |

注意这不是线性的 10×N，而是亚线性（10 → 39 → 76 → 139 → 238），因为**部分专家会被多个 token 共享**。但仍然是 24 倍增长，而 token 数是 32 倍——所以"每 token 净成本"只下降了一点。

### 3.3 投机解码会让情况更糟

该文档还测到：开启 MTP（多 token 投机验证）后，1/2/4 路并发只有 **37.5 → 48.9 → 57.7 tok/s（1.54 倍）**，而不开投机是 2.5 倍。

原因：**一个请求的投机验证本身就 batch 了 4 个 token**，已经把 batch 的好处提前预支；再多路并发，专家集合继续膨胀，收益递减。

> 本机完全同构：单路 `--spec 4` + MTP 接受率 78.7%（见 [本机模型-速度与专家命中率汇总-20261031.md](本机模型-速度与专家命中率汇总-20261031.md)），8 路时 MTP 直接被关闭（`drafts accepted 0 of 0`）。

## 四、本机数据与机制对得上

### 4.1 实测（2026-11-02，R9700 + HIP 0.1.55）

| 负载 | 总吞吐 | GPU 利用率（单引擎） |
|---|---|---|
| 单路持续 20 s | 99.1 tok/s | **90.9%**（峰 95.1%） |
| 8 路持续 20 s | 161.4 tok/s（每路 20.2） | 85.2%（峰 94.9%） |
| 8 路单波（验收脚本） | 123–150 tok/s | 93.5–95.8% |

**提升倍数 1.63×**，落在 strixllama 实测的"投机解码开启后 1.54×"附近，说明机制同源。

### 4.2 专家数与窗口耗时（本机引擎日志）

```
88 windows, avg 7.61 rows, 40.92 ms/window
  = run 35.27 (CUDA0 GPU-reach wait 27.18 + CPU experts 1.80) + commit 5.14 + emit 0.10
routed entries per window: VRAM 3597.1 (98.4%), PCIe 0.1 (0.0%), CPU 57.3 (1.6%)
```

- 每行（每个 token）路由 **3597.1 / 7.61 ≈ 473** 条专家-层对；
- 模型是 48 层 × 每 token 约 10 个专家 = **480**，与 473 高度吻合；
- **8 行窗口读 3597 条 = 每行 473 条，完全没有因为 batch 而减少**——这就是"专家权重无法跨 batch 复用"的直接证据；
- 对照单路窗口（`1.99 rows`，读 `860.5` 条 = 每行 432 条），比例一致。

### 4.3 由此得到的结论

8 路并发的天花板不是"没把 GPU 用满"，而是 **GPU 每步要干的工作量本身随 batch 线性增长**。吞吐只能涨 1.6 倍，因为工作量涨了 8 倍。

## 五、但要修正一个过度简化的说法：带宽并没有被吃满

### 5.1 反算有效带宽

已知每 token 路由约 480 个专家-层对，但**每个专家实际搬运多少字节并不确定**，所以只能给区间：

| 假设 | 每 token 字节 | 99 tok/s 对应有效带宽 | 占 640 GB/s |
|---|---|---|---|
| 按激活参数 6B、Q2_0（≈2.5 bit） | ≈ 1.9 GB | **≈ 186 GB/s** | **29%** |
| 按 480 专家 × 单槽 1.32 MiB（expert cache 19113 MiB / 14498 slots） | ≈ 633 MB | ≈ 63 GB/s | 10% |
| 若把 35 GB expert arena 视为上界、按命中率折算 | ≈ 2–3 GB | 200–300 GB/s | 31–47% |

**结论：有效带宽大致在峰值的 30–50%，没有饱和。** 这与"GPU 利用率 90%"并不矛盾——GPU 利用率计数器在 decode 阶段无法区分"等内存"和"在做低效计算"。

### 5.2 利用率 90% 但带宽只用一半，缺的那一半是什么

三条本机日志线索：

1. **专家 kernel 走了 fallback**
   ```
   strata expdec: CUDA0 gate/up type 42 (n_embd 2560, n_ff 640) not covered: the default kernel runs
   strata expdec: CUDA0 down type 42 (n_embd 2560, n_ff 640) not covered: the default kernel runs
   ```
   R9700（gfx1201）上没有覆盖该量化类型的专用专家 kernel，用的是通用路径 → **算力换带宽**，即"搬运同样的字节，多花了很多计算"。

2. **Q2_0 是极低比特量化，反解开销大**
   2–2.5 bit 权重要在 kernel 内解包，属于计算密集操作。量化降低了字节数（利好带宽），但抬高了每字节的计算量（不利算力）——这也是"为什么有效带宽用不到一半"的典型原因。

3. **WDDM 与主机侧效率损失**
   ```
   Windows budgets 31767 of this card's 32624 MiB for this process
   cudaHostRegister of the whole arena FAILED (invalid argument)
   large pages refused for 33975959552 B (VirtualAlloc error 1314); using 4 KB pages
   ```
   大页申请失败退回 4 KB 页、整块 pinned 注册失败、只 pin 了 44/29 GiB 切片——主机侧搬运与 pin 效率受损。

### 5.3 同一文档的旁证

strixllama 对"GPU 忙但吞吐低"的解释与本机一致：

> "a GPU reading 75% busy during decode is memory stall plus the host gap between tokens"

即：**decode 阶段的 GPU 高利用率主要来自 memory stall（等数据）和 token 之间的 host gap，而不是有效计算**。第三方论文同样把本地 MoE 的 decode 定性为 I/O 受限（[PDScope, arXiv:2610.39216](https://export.arxiv.org/abs/2610.39216)：prefill 是 compute-bound、decode 是 I/O-bound，低 batch 下两者无法摊销）。

## 六、什么能提升、什么不能

| 手段 | 对并发吞吐的作用 | 依据 |
|---|---|---|
| 提高并发（1 → 8 路） | **+63%**（99 → 161），到 8 路后基本到顶 | 本机实测；expert 集合随 batch 增长 |
| 加大 expert cache（命中率 73% → 99.6%） | 单路 +10–30%，并发下被 batch 挤占（16384 → 14498 slots） | 本机两次配置对比 |
| 提高显存带宽（同代换卡，672 → 640 GB/s） | **≈0** | 本机 5070 → R9700 实测 |
| 换 HBM 卡（H200 4.8 TB/s / MI300 5.3 TB/s 量级） | 上限抬 5–8 倍，但**拿不到 8 倍**，因为还有 kernel/dequant 损耗 | §1.3 公式 + §5.2 |
| 量化更狠（Q2 → Q1.x） | 带宽换计算，当前 kernel 未覆盖该类型时收益可能为负 | §5.2 fallback kernel |
| 投机解码（MTP/spec） | 单路有效（接受率 78.7%），**并发下被关闭且开 `--batch-mtp` 更慢** | 本机实测 114.7 tok/s |
| 缩短输出长度 / 关思维链 | **收益最大**（本机输出长度是官方 10 倍量级） | 20261031 汇总 §七 |
| 多卡数据并行（每卡独立副本） | 近似线性，**这是唯一稳的纵向扩展方式** | `serve/replicas.py`；此前 4 卡估算文档 |

## 七、对本项目容量估算的影响

1. **单卡单流 ≈ 100–140 tok/s，8 路并发总 ≈ 150–160 tok/s**。这是 R9700 在这台机器上的**硬上限区间**，不是调参问题。
2. 此前硬件估算里"32 GB 卡单流 548 tok/s、8 路每路 68.5 tok/s"是**按显存容量外推的错值**，应整体下修到实测区间（约 1/4）。凡引用该数字的容量与报价文档都要重算。
3. **规模化只有一条路：多卡 / 多机，每卡跑独立副本**。想靠"一张卡堆 8 路并发"提高产能，实测只能多 60%。
4. 若要单机吞吐再上台阶，硬件优先级应是 **带宽（HBM）** 而不是容量或算力；同时要求引擎侧补齐 gfx1201 的专用专家 kernel（当前 fallback 是明确的效率损失点，属于可以向 Strata 反馈的项）。

## 九、对一句结论的网络核查（2026-11-02 追加）

待核查的原话：

> **"堆显存增加并发换不来产能，产能只能靠多卡。"**

**核查结论：前半句在 MoE 场景成立但需要限定，后半句不成立。**

### 9.1 前半句："堆显存增加并发换不来产能" —— 有条件成立

**成立的证据（本机 + 文献一致）**：

- 本机实测：显存 12 GB → 32 GB，并发 1 → 8，产能 99 → 161 tok/s（**+63%**），不是 8 倍。
- IBM Research / IEEE CLOUD 2025《Mind the Memory Gap》摘要明确：*"While batching is commonly used to increase throughput, **performance gains plateau beyond a certain batch size**, especially with smaller models"*，而它反驳的正是"此时转向 compute-bound"的流行解释——**大 batch 推理仍然是 memory-bound，DRAM 带宽饱和才是主瓶颈**。

**但作为普遍命题是错的**，反例是 dense 模型 + KV cache 受限的场景：

- vLLM 的 PagedAttention 做的正是"省显存换产能"：把 KV cache 的显存浪费从 **60–80% 降到 <4%**，于是 *"allows the system to batch more sequences together, increase GPU utilization, and thereby significantly increase the throughput"*，最终比 HuggingFace Transformers 高 **14–24 倍**、比 TGI 高 2.2–3.5 倍。
- 更直接的反向证据：LMSYS 用 vLLM 后 *"**cut the number of GPUs** used for serving the above traffic **by 50%**"*——**不是加卡，是省卡**。

**为什么两句都能成立？因为"显存"卡的是两件不同的事**：

| 场景 | 显存决定什么 | 堆显存的收益 |
|---|---|---|
| dense / 标准 Transformer | **能同时放多少条序列**（KV cache 容量） | 大：并发直接换吞吐（vLLM 路径） |
| MoE + 专家装不下（本机） | **能常驻多少专家**（命中率） | 小：命中 73% → 99.6% 后，瓶颈转到带宽与专家搬运，边际收益递减 |

所以准确的说法是：**"堆显存"只在你缺的是"容量"时有用；一旦缺的是"带宽"，再堆容量也换不来产能。**

### 9.2 后半句："产能只能靠多卡" —— 不成立

这不是唯一路径，至少还有四条，且第一条正是上面那篇论文给的：

1. **同卡内跑多个模型副本（model replication）**
   IBM 那篇的解法就是：用 BCA 压缩显存占用，把腾出的显存和"未被用满的算力"交给**并发工作负载**，*"Specifically, we use **model replication** to improve serving throughput and GPU utilization"*。
   → 产能来自"更多并发实例"，不必然来自"更多卡"。
2. **提高显存利用效率**（PagedAttention 类）：省 50% 的卡（LMSYS 实测）。
3. **换更高带宽的卡**：HBM 卡（H200 4.8 TB/s、MI300 5.3 TB/s 量级）能把单流上限抬 5–8 倍，代价是钱包。
4. **减少每 token 的工作量**：降输出长度（本机收益最大，输出是官方 10 倍量级）、更低比特量化、补齐 gfx1201 专用专家 kernel（当前 fallback 是明确损失点）。

多卡（数据并行副本）确实是**最稳、最可预测**的一条（`serve/replicas.py`、vLLM 的 EP/DP 实践），但"最稳"不等于"只能"。

### 9.3 修正后的表述（建议替换原话）

> **在本机这种"MoE + 专家装不下 + 投机解码已提前用掉 batch 红利"的配置下，把显存从 12 GB 堆到 32 GB、并发从 1 堆到 8，产能只涨约 60%——因为瓶颈是带宽和专家权重搬运，不是显存容量。**
> **要提产能，优先级是：①缩短输出（当前收益最大）②让更多专家常驻以省 PCIe/内存往返 ③补专用专家 kernel ④更高带宽的卡 ⑤多卡/多副本（最稳）。**
> **"只能靠多卡"是过度断言；但也别指望把 batch 撑大——大 batch 在带宽饱和后同样平台化。**

### 9.4 这条核查对项目估算的含义

- 原估算"32 GB 卡 548 tok/s"仍然错，实测区间 100–140（单流）/ 150–160（8 路）不变。
- 但**"产能只能靠多卡"这句话不能写进方案**：它会让方案忽略"降输出长度"和"显存利用效率"这两条更便宜的杠杆（本机输出长度是官方 10 倍量级，这一条比换卡省钱得多）。
