# 诊断分析与诊疗计划：三方模型对照测试方案

**日期**：2026-11-03
**目的**：用数据库中真实病例，对比「本机 Qwen 3.8 Flash」「本机 DeepSeek V4.1 Flash」「官方 DeepSeek API」在**诊断分析**和**诊疗计划**两项任务上的质量，为"是否引入 V4.1"提供可引用的数据
**基线**：2026-10-30 的 5 例对比（Qwen 3.56 / 官方 4.18）——本方案在其基础上扩到 20 例、加一个任务、加一个模型

## 二、病例选取标准

### 2.1 数量与分布

| 维度 | 要求 |
|---|---|
| 总数 | **20 例** |
| 科室 | 内科 12、外科 5、其他 3（覆盖多科室，避免只测心血管） |
| 病例复杂度 | 简单 6、中等 8、复杂 6（复杂 = 多诊断、多并发症） |
| 时间范围 | 近 6 个月（2026-05 ~ 2026-10） |
| 数据完整性 | 必须有：主诉、现病史、既往史、体格检查、检验、影像（至少 2 类） |

### 2.2 排除标准

| 排除 | 原因 |
|---|---|
| 门诊病例 | 无入院记录，AI 无足够输入 |
| 住院 < 24 小时 | 病历不完整 |
| 涉及未成年/孕产妇 | 隐私敏感度高 |
| 已故患者 | 伦理审查要求 |

### 2.3 抽样方法

从 Oracle `T_PATIENT_VISIT` 按科室分层随机抽取，**每例保留真实 ID 用于取数，对外只用代号 P01–P20**。

对应关系写入 `.dsh/tmp/quality-test/mapping.json`，该文件加入 `.gitignore`。

## 三、输入组装（复用生产链路）

**方法来自 2026-10-30 的 5 例对比，已证明可行。**

| 组成 | 来源 | 长度（实测） |
|---|---|---|
| `system` 消息 | `med_ai_assistant_1.0_bs_backend/src/main/resources/systemPrompt` | 22,418 字符 |
| `user` 第 1 段：患者资料 | 调后端 `GET /api/ai/patient-data?patientId=…&promptType=诊断分析` | 5,000–14,000 字符 |
| `user` 第 2 段：模板正文 | Oracle `PROMPTTEMPLATE` 表（诊断分析 `PROMPTID=3`；诊疗计划查对应 ID） | 约 16,000 字符 |
| `user` 第 3 段：临床经验规则 | `DIAGNOSIS_CLINICAL_RULES` 激活规则，按关键字匹配 | 0–2,000 字符 |

**关键：走生产同一实现，不自己拼 prompt**——否则测的不是"线上会怎样"。

### 3.1 为什么用后端 API 取患者资料

生产定时任务用的是 `PatientDataController`，它做了：

- 多表关联（就诊、诊断、检验、影像、医嘱）
- 按 `promptType` 裁剪字段
- 隐私字段脱敏

**自己写 SQL 会漏掉这些处理，测出来的结果对不上线上。**

## 四、评分标准

### 4.1 沿用 5 例对比的 5 个维度

| # | 维度 | 判据 | 满分 |
|---|---|---|---|
| 1 | **格式契约** | 四段齐全、诊断编号连续、每条诊断依据 ≥3 条、鉴别 ≥1 条 | 1 |
| 2 | **诊断准确性** | 是否与医生最终诊断一致；有无越权修改（把 A 改成 B） | 1 |
| 3 | **依据充分性** | 每条诊断是否引用具体检验/影像/症状，而非泛泛而谈 | 1 |
| 4 | **鉴别诊断** | 是否给出合理的排除理由，而非罗列病名 | 1 |
| 5 | **冲突识别** | 是否发现数据间的矛盾（如 CTA 与造影不一致） | 1 |
| **总分** | | | **5** |

### 4.2 诊疗计划额外加两项

| # | 维度 | 判据 |
|---|---|---|
| 6 | 治疗措施完整性 | 是否覆盖药物、非药物、监测、随访 |
| 7 | 用药安全性 | 剂量、禁忌、相互作用是否合理 |

### 4.3 评分规则

| 项 | 要求 |
|---|---|
| 盲评 | 医生**不知道**输出是哪个模型生成的（打乱顺序、统一格式） |
| 评分人 | ≥2 名主治以上医师，取平均 |
| 分歧处理 | 两人分差 >1 分时，第三人仲裁 |
| 记录 | 每份输出附评分表 + 评语 |

## 五、执行步骤

### 第 1 步：准备（1 天）

| # | 动作 | 产出 |
|---|---|---|
| 1 | 从 Oracle 抽 20 例，记录 ID 与分科 | `mapping.json`（不入库） |
| 2 | 启动后端（`--server.port=18081`），验证 `/api/ai/patient-data` 可取数 | 20 份患者资料 |
| 3 | 从 `PROMPTTEMPLATE` 取两个任务的模板 | 2 份模板 |
| 4 | 从 `DIAGNOSIS_CLINICAL_RULES` 取激活规则 | 规则集 |

### 第 2 步：跑 Qwen 本地（半天）

```bash
# 起 Qwen（端口 5080）
cd /data/strata/terminal/0.1.56
sg render -c "STRATA_DATA_DIR=/data/strata nohup ./python/bin/python3 -X utf8 -m serve.server \
  --engine strata --config /data/strata/q2_0-linux.json \
  --host 127.0.0.1 --port 5080 --parallel 4 > /data/strata/serve-qwen.out 2>&1 &"

# 跑 20 例 × 2 任务
node .dsh/tmp/quality-test/run-batch.mjs --models qwen --tasks diag,plan --pids P01..P20
```

### 第 3 步：跑官方 DeepSeek（1 小时）

```bash
node .dsh/tmp/quality-test/run-batch.mjs --models official --tasks diag,plan
```

> 官方 API 走 `https://api.deepseek.com`，**数据出医院**——必须先脱敏（见第六节）。

### 第 4 步：跑 V4.1 本地（等模型到位）

```bash
# 起 V4.1（端口 5082）
# 模型是 239–274 GB，首次加载 2–5 分钟
node .dsh/tmp/quality-test/run-batch.mjs --models dsv41 --tasks diag,plan
```

### 第 5 步：盲评（医院安排）

| # | 动作 |
|---|---|
| 1 | 把 120 份输出打乱顺序，去掉模型标识，编成 S01–S120 |
| 2 | 分发评分表给 ≥2 名医师 |
| 3 | 回收、汇总、算平均分与标准差 |
| 4 | 解密映射，得到三个模型的得分 |

### 第 6 步：出报告

## 六、数据安全（官方 API 的硬约束）

**官方 DeepSeek 是云端 API，输入数据会离开医院。**

| 措施 | 要求 |
|---|---|
| 脱敏 | 姓名、身份证、手机号、住院号、床号全部替换为代号 |
| 去标识 | 具体日期改为「入院第 N 天」 |
| 抽样审查 | 脱敏后由信息科抽查 3 份，确认无法反推 |
| 审批 | 走医院数据外发审批流程（如需要） |
| 不留存 | 官方 API 调用后不保留请求日志（或用企业版无留存） |

**如果医院不允许任何数据出内网，这一列只能取消**——那就变成"Qwen vs V4.1"两方对比。

## 十一、我的建议

**分两阶段做，先不碰 V4.1：**

**阶段 1（现在就能做，不花现金）**
- Qwen 本地 vs 官方 DeepSeek，20 例 × 2 任务 = 60 份
- 这一步的价值：把 5 例的结论（3.56 vs 4.18）扩展到 20 例，样本更可信
- 如果 60 份跑完，Qwen 的分数依然在 3.5 左右，说明本地模型确实差一档

**阶段 2（V4.1 下载后）**
- 补 40 份 V4.1 输出
- 三方对比出最终结论

**为什么先做阶段 1**：V4.1 要下 257 GB、一天时间，而阶段 1 一天就能出结果——先拿到"Qwen 到底差多少"的可靠数字，再决定值不值得为 V4.1 投入。
