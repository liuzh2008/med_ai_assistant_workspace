# 含 CLOB 实体批量查询 OOM 问题：成因分析与标准解决方案调研报告

**日期**：2026-08-13
**版本**：V1.0
**状态**：已结项（方案 A 已进入实施）

---

## 一、背景

2026-08-13 生产环境执行服务器（`med-ai-execution-server`）出现周期性自动重启，日志特征为 `exited with code 137 (restarting)`。诊断确认：退出码 137 = 128 + 9（SIGKILL），进程被内核 OOM Killer 强制杀死，触发点为每 5 分钟执行的 `ConsistencyCheckService` 定时对账任务，其包含的 `findByStatus(SENT)` 查询一次性加载 19,278 条记录（每条含 3 个 CLOB 大字段），内存瞬间冲高触发 OOM。

修复过程中确认：该问题并非个例，同一模式（含 `@Lob` CLOB 字段的实体批量查询）在代码库多处存在。本报告系统梳理该问题的成因（特别是 AI 辅助开发背景下的产生机理）与业界标准解决方案，作为后续规范完善与代码治理的依据。

---

## 二、问题现象与根因链

### 2.1 根因链

```
exit code 137 = SIGKILL（内核 OOM Killer 强杀，非 Java 异常）
    ↓
触发点：每 5 分钟的 ConsistencyCheckService 定时对账
    ↓
代码缺陷：findByStatus(SENT) 一次性加载 19,278 条记录（每条含 3 个 CLOB）
          + findByStatusName("已提交") 全量加载 Prompt（含多个 CLOB）
    ↓
内存瞬间冲高 → 容器/宿主机内存耗尽 → SIGKILL
    ↓
restart: unless-stopped 自动拉起 → 循环重启
```

### 2.2 技术机理

1. **实体查询固定 select 全部列**：JPQL `SELECT e FROM Entity e` 是实体查询，Hibernate 必须 select 全部映射列，包括 CLOB。
2. **`@Lob` 默认 EAGER 映射**：`@Basic(fetch = LAZY)` 需要 Hibernate 字节码增强（bytecode enhancement）才生效，本项目未启用，直接标注不产生效果。
3. **进程级 OOM 无堆转储**：`-XX:+HeapDumpOnOutOfMemoryError` 仅在 JVM 堆 OOM（OutOfMemoryError）时生效；容器级 OOM Killer 发 SIGKILL 时 JVM 来不及生成 heapdump，这本身是判别"容器级 OOM"与"Java 堆 OOM"的依据。
4. **容器限制配置失效**：`deploy.resources.limits.memory` 仅在 `docker stack deploy`（Swarm）模式生效，`docker compose up` 下静默忽略，需使用顶层 `mem_limit`。

### 2.3 本项目实锤证据

| 位置 | 代码 | 状态 |
|------|------|------|
| `PromptRepository.findByStatusNameLimited` | 注释明确写着"OOM修复：限制每次轮询最多加载的Prompt数量" | 轮询路径已修复 |
| `PromptPollingService` | 使用 `findByStatusNameLimited` + `PageRequest.of(0, MAX_POLLING_BATCH_SIZE)` | 已修复 |
| `ConsistencyCheckService` | `findByStatusName(STATUS_SUBMITTED)` / `findByStatus(SENT)` 无限制全量 | 缺陷（本次修复） |
| `PromptDataConsistencyService.diagnose()` | `promptRepository.findAll()` 全表 + stream 过滤 | 缺陷（待治理） |
| `DataExtractionService` | `findByStatus(DECRYPTED)` 无限制全量 | 潜在风险 |

## 三、成因分析：为何在 AI 开发时产生

### 3.1 AI 生成代码的固有倾向："局部正确，全局无感"

- **派生查询是最自然的表达**：`findByStatusName(status)` 是 Spring Data 教程默认教法，AI 倾向于生成最简洁、最惯用的代码，不会主动推理"该状态在生产可能有 2 万条记录且每条含 CLOB"。
- **教科书式写法**：`findAll().stream().filter(...)` 是 AI 高频生成的模式（本报告 2.3 节证据），逻辑正确但完全无视数据规模。
- **学术研究佐证**（arXiv 2025 系统文献综述 *A Survey of Bugs in AI-Generated Code*）：AI 生成代码的 bug 分类中有一类 performance-related bugs，其特征被描述为"**程序运行正确，但资源表现不符合要求**"——与本案例完全吻合：功能正确、单测通过、测试环境正常，唯独在生产数据量下 OOM。

### 3.2 测试环境掩盖问题

- 开发/测试环境 SENT 记录仅几百条，全量加载毫无压力；
- 单元测试使用 Mock 仓库，永不接触真实数据量与真实 CLOB；
- 问题只在生产数据积累到 19,278 条时爆发——"生产才爆炸"型缺陷，开发阶段无法自然发现。

### 3.3 修复的模式扩散盲区（本项目最典型）

AI 辅助修复是"点对点"的：报错在哪就修哪，修完即止，不会主动在全代码库排查同类模式。于是同一个 OOM 缺陷以三种形态共存于轮询、一致性检查、诊断服务三条路径中，只修了第一条（见 2.3 节证据表）。

### 3.4 架构层原因

- Entity 含 `@Lob` CLOB 是合理的领域建模（加密数据、AI 生成结果本就该是 CLOB）；
- 同一张表被"业务处理路径"（需要完整实体）与"巡检/诊断路径"（只需要 ID + 状态）共用，AI 不会为不同路径设计不同粒度的查询接口；
- 批量巡检与实时业务混用同一 Repository 方法，缺少按用途区分的查询契约。

## 四、标准解决方案调研

### 4.1 方案矩阵（按成本/收益排序）

| # | 标准方案 | 机制 | 适用场景 | 本项目结论 |
|---|---|---|---|---|
| 1 | **分页（Pagination）** | `Pageable` 限制每批加载量，防一次性实体堆积 | 批量巡检/轮询/补偿任务 | ✅ 已实施（每批 200 条） |
| 2 | **投影查询（Projection）** | JPQL 只 select 需要的列，CLOB 不出现在 SQL；Spring Data 接口投影（closed projection）自动优化 select 列 | 列表/巡检只需少量字段 | ✅ 本次实施（方案 A） |
| 3 | **按需单条加载** | 列表只拿 ID，需要 CLOB 内容时 `findById` 单条读取 | 少数记录需要详情（如错误信息） | ✅ 本次实施 |
| 4 | **count 先行短路** | 巡检开头 `countByStatus`，为 0 直接跳过 | 定时巡检任务 | 可选（`countByStatus` 已存在） |
| 5 | **懒加载 + 字节码增强** | `@Basic(fetch=LAZY)` + Hibernate bytecode enhancement | 全项目统一懒加载 | ❌ 不推荐（改动全项目加载行为） |
| 6 | **表结构拆分（垂直分表）** | CLOB 大字段拆到 1:1 副表，主表只留轻量字段 | 架构级根治 | ❌ 暂不推荐（改动大、需数据迁移） |

### 4.2 社区共识与参考依据

- **Hibernate 官方社区**（discourse.hibernate.org）：只 select 部分列始终比加载整个实体性能更好，尤其在查询含大字段/多表 join 时；实体加载后 MapStruct 拷贝是常见但低效的做法。
- **业界基准**（Yellow GNU：SELECT * vs Explicit Column Selection in JPA）：DTO 投影在 CLOB/宽表场景可带来数量级差异，且能利用索引覆盖扫描。
- **JPA 官方文档**（Spring Data JPA Query Methods）：接口投影对 closed projection 自动优化为只 select 暴露的属性；String-based Tuple Query 为 Hibernate 支持。
- **字节码增强**（Hibernate 官方）：`@Basic(fetch = LAZY)` 需启用 bytecode enhancement，未启用时不生效且无告警，易被误用。

### 4.3 标准组合拳（推荐顺序）

```
分页（防实体堆积） → 投影（防 CLOB 进 SQL/结果集） → 按需加载（少数详情字段） → count 短路（巡检优化）
```

### 4.4 AI 开发流程层面的预防措施

1. **静态防线**：项目规范明确"含 `@Lob` 实体的 Repository 方法禁止无 Pageable/无投影的全量返回"（已写入 `.qoder/rules/04-database-oracle.md`）。
2. **审查专项**：代码审查清单新增"性能与资源"维度，对 `findByStatusName(`、`findAll()`、`findByStatus(` 等全量查询做 grep 专项检查（已写入 `.qoder/commands/code-review.md`）。
3. **模式排查习惯**：修复某类缺陷（如 OOM）后，全库搜索同类模式一并修复，避免"修一处漏三处"。
4. **生产数据量意识**：巡检/诊断类功能设计时以生产最大数据量为基准（本项目 SENT 19,278 条且持续增长），而非测试环境数据量。

## 六、结论

1. 含 CLOB 实体的批量查询 OOM 是 AI 辅助开发中高频且隐蔽的缺陷模式：功能正确、测试通过、测试环境无感，只在生产数据量下爆发。
2. 标准解决方案为**分页 + 投影 + 按需加载**的组合拳，已在本项目完成实施并通过编译验证。
3. 治理成果已固化为三类资产：本报告（知识沉淀）、项目数据库规范（静态防线）、code-review 审查清单（动态防线）。
