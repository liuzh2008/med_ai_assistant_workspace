### 修改类型
fix(执行服务器) — 生产环境执行服务器 OOM 自动重启（exit 137）根治

### 影响范围
- 后端 `ExecutionServerEncryptedDataTempRepository.java` — 新增分页查询 `findByStatusPaged(status, Pageable)`（按接收时间升序，防全量加载 CLOB 记录）
- 后端 `ConsistencyCheckService.java` — `checkSubmittedPromptsWithoutEncryptedData` / `checkSentDataWithIncompletePrompts` 全量查询改分页循环（每批 200 条），复用 `findByStatusNameLimited`
- 后端 `PromptDataConsistencyService.java` — `checkSentButPromptIncomplete` / `checkErrorButPromptNotFailed` 改分页循环，问题记录对最多保留 200 对（总数仍准确统计）
- 部署 `deploy/execution-linux(-yanting)/docker-compose-execution-{linux,image}.yml`（4 文件）— 新增顶层 `mem_limit: 8g`（compose up 生效；`deploy.resources` 仅 swarm 模式生效）
- 部署 `deploy/execution-linux/.env.execution` — JVM 参数补充 `-XX:MaxMetaspaceSize=512m -XX:MetaspaceSize=256m`
- 部署 `deploy/execution-linux-yanting/Dockerfile.execution.linux` — 移除 `-XX:+ExitOnOutOfMemoryError`（与 execution-linux 版本对齐，防 OOM 后 exit 3 无限重启）

### 简要描述

**现象**：生产环境执行服务器周期性 `exited with code 137 (restarting)` 自动重启。日志显示 14:54:44 一致性检查开始执行 Hibernate 全量查询后立即被 SIGKILL。

**根因**：
1. 退出码 137 = 128 + 9（SIGKILL），进程被内核/容器 OOM Killer 强制杀死（非 Java 堆 OOM，故无 heapdump 生成）。
2. 代码层内存炸弹：`ConsistencyCheckService` 每 5 分钟执行的全量查询——`findByStatusName("已提交")` 加载全部已提交 Prompt（含多个 CLOB 大字段）、`findByStatus(SENT)` 一次性加载 19278 条 SENT 记录（每条含 3 个 CLOB 字段），内存瞬间冲高触发 OOM。轮询路径早已用 `findByStatusNameLimited` 做过 OOM 修复，一致性检查路径漏改。
3. 配置层：`deploy.resources.limits.memory: 6G` 仅 swarm 模式生效，`docker compose up` 下容器无内存限制，完全依赖宿主机内存，`-Xmx4g` 堆 + 堆外 ≈ 5G+ 在宿主机内存紧张时成为 OOM Killer 首选目标。

**代码修复**：
1. 一致性检查与诊断服务的 4 处全量查询全部改为分页循环（每批 200 条），单批内存占用可控。
2. 诊断报告问题对上限 200 对，防止异常数据量下报告构建自身 OOM。

**部署配置修复**：
1. 顶层 `mem_limit: 8g`（compose up 生效），JVM 堆 4G 预留充足堆外余量。
2. JVM 参数补充元空间显式限制，防止类加载失控推高总内存。
3. yanting Dockerfile 移除 `-XX:+ExitOnOutOfMemoryError`（历史遗留，会配合 restart 策略无限重启）。

**验证**：
- 后端 `mvnw.cmd compile` BUILD SUCCESS

**上线动作（需在生产服务器执行）**：
1. 推送后端代码 → 重新构建镜像 → `docker compose up -d` 重建执行服务器容器
2. 部署前确认宿主机可用内存 ≥ 10G（`free -h`），并检查 `dmesg | grep -i oom` 确认历史 OOM 记录
3. 观察 2 个一致性检查周期（约 10 分钟）确认不再重启

### 修改类型
fix(部署) — 生产环境执行服务器 compose 校验失败：mem_limit 与 deploy.resources.limits.memory 值不一致

### 影响范围
- 部署 `deploy/execution-linux(-yanting)/docker-compose-execution-{linux,image}.yml`（4 文件）— `deploy.resources.limits.memory` 由 6G 改为 8G，与顶层 `mem_limit: 8g` 对齐；移除已废弃的 `version: '3.8'` 声明

### 简要描述

**现象**：生产环境 `deploy.sh` 第 5 步 `docker compose up` 报错退出：
```
services.med-ai-execution-server: can't set distinct values on 'mem_limit' and 'deploy.resources.limits.memory': invalid compose project
```

**根因**：新版 Docker Compose（v2）对 `mem_limit` 与 `deploy.resources.limits.memory` 做一致性校验，两者值不一致（8g vs 6G）直接拒绝解析。历史配置中 6G 是 swarm 时代的旧值，8g 是后加的 compose up 生效值。

**修复**：两处内存限制统一为 8G（保持 OOM 修复时确定的 8G 上限不变），同时移除已废弃的 `version: '3.8'`（消除每次部署的 WARN）。

**验证**：
- 4 个 compose 文件 YAML 语法解析通过
- 生产环境 `mem_limit: 8g` 与 `deploy.resources.limits.memory: 8G` 已一致

**上线动作（需在生产服务器执行）**：
1. 将修复后的 `docker-compose-execution-image.yml` 同步到生产服务器 `/opt/execution-linux/`
2. 重新执行 `./deploy.sh`（或触发 auto-deploy）
