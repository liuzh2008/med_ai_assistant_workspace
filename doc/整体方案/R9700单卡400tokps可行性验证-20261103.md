# R9700 单卡 400 tok/s 可行性验证报告

**日期**：2026-11-03
**目标**：在 Ubuntu + R9700 32 GB 单卡 + 64 GB 内存的硬件上，验证能否达到 **400 tok/s 总产能**
**方法**：Docker + ROCm + vLLM 官方镜像，逐一测试 27B 模型的三种量化格式
**结论**：**硬件支持，软件栈不支持。** 在官方可获得的工具链上，27B 全部三种量化都无法起服务；第三方 385.8 tok/s 依赖一套当前拉不到的定制镜像。

---

## 一、结论摘要

| 验证项 | 结果 |
|---|---|
| Linux 环境（Ubuntu 24.04 + 内核 6.17） | ✅ 正常 |
| R9700 被内核识别（KFD / amdgpu） | ✅ `/dev/kfd` 存在，`added device 1002:7551` |
| ROCm 运行时在容器内可用 | ✅ `rocminfo` → Agent 2 = **gfx1201** |
| PyTorch GPU 可用 | ✅ `torch 2.13.0`，`gpu_available=True`，`devices=1` |
| vLLM 版本 | ✅ `0.32.0`（ROCm 镜像 46.8 GB） |
| **27B + FP8** | ❌ 显存不足（权重 28.75 GiB，加载完只剩 32 MB） |
| **27B + Quark MXFP4** | ❌ 官方不支持原生 MXFP4，模拟反量化后 OOM |
| **27B + AWQ INT4** | ❌ **GPU kernel 崩溃**（`Memory access fault`） |
| 定制镜像 `vllm-radiance:0.9.3` | ❌ 拉取失败（403 Forbidden） |

**判断**：单卡 R9700 的带宽（640 GB/s）在物理上支持 385.8 tok/s（第三方同卡实测），但该结果**不可用官方 vLLM 复现**；标准工具链（llama.cpp）上限约 95.7 tok/s。**400 tok/s 在现有软件条件下不可达。**

## 三、验证过程

### 3.1 ROCm 在容器内可用（已通过）

```bash
sudo docker run --rm --device=/dev/kfd --device=/dev/dri \
  --group-add 992 --group-add 44 \
  --entrypoint bash vllm/vllm-openai-rocm:latest -lc '
    rocminfo | grep -E "Marketing Name|gfx" | head -6
    python3 -c "import torch;print(torch.__version__, torch.cuda.is_available(), torch.cuda.device_count())"'
```

输出：

```
Name:                    gfx1201
Marketing Name:          AMD Radeon Graphics
    Name:                amdgcn-amd-amdhsa--gfx1201
    Name:                amdgcn-amd-amdhsa--gfx12-generic
torch 2.13.0+git733fca1
gpu_available True
devices 1
vllm 0.32.0
```

**注意**：`--group-add` 必须用**数字 GID**（`992`、`44`）。用名字会报
`Unable to find group render: no matching entries in group file`，因为镜像内的组表与宿主不同。

### 3.2 27B 模型三种量化，全部失败

#### （1）FP8 —— 显存不足

模型 `Qwen/Qwen3.8-27B-FP8`（29 GB，66 个 shard）。

```
Loading safetensors checkpoint shards: 100%
[rank0]: memory allocation failed with OOM on device 0 while trying to allocate 301989888 bytes
        (free: 132120576, total: 34208743424)
torch.OutOfMemoryError: CUDA out of memory. Tried to allocate 288.00 MiB.
        GPU 0 has a total capacity of 31.86 GiB of which 32.00 MiB is free.
        Of the allocated memory 31.40 GiB is allocated by PyTorch
```

**原因**：FP8 27B 权重 **28.75 GiB**，加载完只剩 32 MB，任何 KV/激活分配都失败。

#### （2）AMD Quark MXFP4 —— 官方不支持原生 MXFP4

模型 `amd/Qwen3.8-27B-Quark-AWQ-MXFP4`（19 GB，18.4 GiB）。

```
WARNING quark_ocp_mx.py:91] The current platform does not support native MXFP4/MXFP6 computation.
        Simulated weight dequantization and activation QDQ will be used,
        with the linear layers computed in high precision.
WARNING emulation.py:91] The current platform does not support native MXFP4 computation.
        Using EmulationMxfp4LinearKernel ...
torch.OutOfMemoryError: ... 30.64 GiB is allocated by PyTorch ... 150.00 MiB is free
```

**原因**：`quantization=quark` 被正确识别，但 ROCm 后端**没有 MXFP4 原生计算路径**，退回"模拟反量化"——权重被展开成高精度，18.4 GiB 反而涨到 30.64 GiB，OOM。

> 这正是第三方要用**手写 fp8-WMMA HIP kernel** 的原因：官方 AITER 把 gfx12x 门禁掉了，RDNA4 的 fp8 张量默认走不通。

#### （3）AWQ INT4 —— GPU kernel 崩溃

模型 `cyankiwi/Qwen3.8-27B-AWQ-INT4`（20 GB）。

```
INFO [__init__.py:923] Using RDNAHybridW4A16LinearKernel for mixed-precision linear
INFO [compressed_tensors_wNa16.py:138] Using RDNAHybridW4A16LinearKernel for CompressedTensorsWNA16
Memory access fault by GPU node-1 (Agent handle: 0x5eb78420) on address 0x7aae2a20f000.
        Reason: Page not present or supervisor privilege.
GPU coredump: execvp failed: No such file or directory
```

**这是 kernel bug，不是显存问题**（权重 19.44 GiB，剩余 11.57 GiB）。vLLM 为 RDNA 准备的 `RDNAHybridW4A16LinearKernel` 在 gfx1201 上直接触发 GPU 页错误。

调参尝试均无效：
- `--gpu-memory-utilization 0.85`
- `--enforce-eager`
- `--max-num-seqs 32`
- `PYTORCH_HIP_ALLOC_CONF=expandable_segments:True`

### 3.3 定制镜像路线（不可得）

第三方 385.8 tok/s 的配置是 `stilldeadcode/vllm-radiance:0.9.3` + `Launch80/Qwen3.8-27B-PARO-MXFP4`，
依赖 [ggz14 的 fp8-WMMA HIP kernel](https://codeberg.org/ggz14/radiance-vllm-mxfp4)。

拉取结果：

```
Error response from daemon: failed to resolve reference
  "docker.io/stilldeadcode/vllm-radiance:0.9.3":
  unexpected status from HEAD request to https://docker.m.daocloud.io/v2/...: 403 Forbidden
```

**拿不到。** 且该镜像自述为"学术验证，非生产推荐"。

## 四、为什么 385.8 tok/s 不可复现

| 条件 | 第三方（385.8） | 本机官方栈 |
|---|---|---|
| 引擎 | vllm-radiance 0.9.3（含手写 kernel） | vLLM 0.32.0 官方 |
| 量化 | MXFP4 W4A8（18.07 GiB） | Quark MXFP4（18.4 GiB） |
| MXFP4 原生计算 | ✅ 手写 HIP kernel | ❌ 模拟反量化 → OOM |
| 上下文 | 65k/请求，103k pool | 未起服务 |
| 系统 | CachyOS + ROCm 7.14（容器） | Ubuntu 24.04 + 镜像内 ROCm |

**差距不在硬件，在 kernel。** 同一张卡、同一带宽，官方栈缺的是"让 RDNA4 的 fp8 张量真正跑起来"的那层代码。

### 参照：标准工具链的能力上限

第三方在同一张 R9700 上的对照数据（[r9700-local-inference-notes](https://github.com/NikoCloud/r9700-local-inference-notes)）：

| 引擎 | 峰值聚合吞吐 |
|---|---|
| llama.cpp（Vulkan，27B Q4_K_S） | **95.7 tok/s @ n=2**（n 更大不再涨） |
| vLLM radiance（27B MXFP4） | **385.8 tok/s @ n=24** |

## 五、踩坑记录：根分区被反复写满

这是本次最重要的运维教训，**24 GB 的系统盘根本装不下这套推理栈**。

| 事件 | 占用 | 处理 |
|---|---|---|
| `apt install rocm`（原生安装） | dpkg 中断，根分区 100% | **放弃原生安装**，改 Docker |
| `/var/lib/containerd` | 9.5 GB（docker.io 29.x 默认 containerd snapshotter，**绕过 daemon.json 的 data-root**） | 改 `/etc/containerd/config.toml` 的 `root` 到 `/data/containerd` |
| `/var/lib/apport` + `/var/crash` | 2.4 GB（**vLLM GPU 崩溃产生的 coredump 报告**） | `rm -rf /var/lib/apport/* /var/crash/*`，停用 apport |
| 一度连 `bash` 工具都无法启动 | `ENOSPC: mkdtemp '/tmp/...'` | 必须人工在终端清理 |

### 两个必须记住的判据

1. **`docker info` 显示 `Docker Root Dir: /data/docker` 不代表镜像写在 /data。**
   要看 `Storage Driver` 下面是否有 `driver-type: io.containerd.snapshotter.v1`——有就是 containerd 在管，实际路径由 `/etc/containerd/config.toml` 的 `root` 决定。
   验证方法：拉一个镜像后对比 `du -sm /data/containerd /var/lib/containerd`。

2. **GPU kernel 崩溃会在系统盘留下 GB 级 coredump。**
   `Memory access fault` 之后检查 `/var/lib/apport`、`/var/crash`。

## 六、完整复现命令

```bash
# 1) containerd 存储迁到 /data（关键）
sudo mkdir -p /etc/containerd /data/containerd
sudo containerd config default | sudo tee /etc/containerd/config.toml >/dev/null
sudo sed -i "s|^root = '/var/lib/containerd'|root = '/data/containerd'|" /etc/containerd/config.toml
sudo systemctl restart containerd docker

# 2) Docker 镜像加速（registry-1.docker.io 直连不通）
sudo tee /etc/docker/daemon.json >/dev/null <<'JSON'
{ "data-root": "/data/docker", "registry-mirrors": ["https://docker.m.daocloud.io"] }
JSON
sudo systemctl restart docker

# 3) 拉 vLLM ROCm 镜像（46.8 GB）
sudo docker pull vllm/vllm-openai-rocm:latest

# 4) 验证 GPU（注意数字 GID）
sudo docker run --rm --device=/dev/kfd --device=/dev/dri \
  --group-add 992 --group-add 44 --entrypoint bash \
  vllm/vllm-openai-rocm:latest -lc 'rocminfo | grep gfx | head -3'

# 5) 下模型（HF 直连不通，走 hf-mirror + 禁 Xet）
sudo docker run --rm --entrypoint python3 \
  -e HF_ENDPOINT=https://hf-mirror.com -e HF_HUB_DISABLE_XET=1 \
  -v /data/models:/models vllm/vllm-openai-rocm:latest \
  -c "from huggingface_hub import snapshot_download; snapshot_download('Qwen/Qwen3.8-27B-FP8', local_dir='/models/qwen3.8-27b-fp8')"

# 6) 起服务（三种量化各自 OOM / 崩溃，见 §3.2）
sudo docker run -d --name vllm27b --device=/dev/kfd --device=/dev/dri \
  --group-add 992 --group-add 44 -v /data/models:/models -p 8000:8000 \
  vllm/vllm-openai-rocm:latest /models/qwen3.8-27b-awq \
  --max-model-len 8192 --gpu-memory-utilization 0.85 --enforce-eager
```

**关键环境变量**：
- `HF_ENDPOINT=https://hf-mirror.com`（huggingface.co 直连不通）
- `HF_HUB_DISABLE_XET=1`（hf-mirror 不支持 Xet，否则 `401 Unauthorized`）

## 七、后续可选路径

| 路径 | 预期吞吐 | 成本/风险 |
|---|---|---|
| 保持 R9700，27B 走 llama.cpp | ~95 tok/s | 0 元，需编译 HIP 后端 |
| 加 3 张 R9700（4 卡副本） | ~560 tok/s | 约 4.8 万，模型与质量不动 |
| 自建 radiance 栈 | 385.8（理论） | 需从 codeberg 源码编译 + 手写 kernel，工作量与不确定性都高 |
| 2× RX 9070 XT 16G | ~80–100 tok/s | 约 2.4 万整机，显存 32 GB，低于目标 |
| 2× RTX 5070 12G | ~50–70 tok/s | 约 2.8 万整机，24 GB 显存，**不推荐** |

**结论重申**：单机 400 tok/s 只有两条路——**4 卡副本**，或**拿到那套定制推理栈**。单卡换任何消费级型号都不够。
