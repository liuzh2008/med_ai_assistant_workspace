## 三、速度测试结果

### 3.1 测试方法

- **HTTP 接口**：`POST http://127.0.0.1:8080/v1/chat/completions`，`temperature=0`，`max_tokens` 固定
- **decode 速度**：`completion_tokens / 墙钟`，另用引擎自报 `N generated in M ms (X tok/s)` 交叉核对
- **prefill 速度**：每次使用**唯一 prompt 前缀**（`[测量 <时间戳>]`）规避会话复用，读引擎日志的 `prompt N tokens = 0 reused + N read in M ms`
- **冷/热区分**：模型加载后首轮为冷态；连续第二轮为热态（专家缓存已填充）
- 脚本：`/data/strata/v41-speed-test.sh`、`/data/strata/v41-prefill-test.py`

### 3.2 解码速度（热态，重复两轮）

| 场景 | 第一轮 | 第二轮 | 说明 |
|---|---|---|---|
| 256 tok 输出 | 9.92 | 7.48 | 短输出，含首 token 开销分摊 |
| 512 tok 输出 | 11.29 | **14.35** | |
| 1024 tok 输出 | 15.30 | **18.79** | 稳定峰值 |
| 长 prompt（8170）+ 64 tok | 2.34 | 8.72 | 冷/热差异来自 prefill |
| 短 prompt + 16 tok（缓存热） | — | **27.5–30.2** | 引擎日志实测 |

> **规律**：输出越长，平均 decode 越高——前几十个 token 要按访问模式读入冷专家，摊薄了平均值。**首轮普遍比第二轮低 20–30%**，报数时应取热态。

### 3.3 Prefill（唯一 prompt，无复用）

| Prompt 长度 | Prefill 耗时 | Prefill 速度 |
|---|---|---|
| 8,742 tok | 20,162 ms | **433.6 tok/s** |
| 34,842 tok | 40,592 ms | **858.3 tok/s** |
| 69,642 tok | 68,000 ms | **1,024.2 tok/s** |

**规模效应显著**：prompt 从 8.7K 增至 69.6K，吞吐提升 2.4 倍（分块流水与专家复用摊薄固定开销）。9 万 token 级病历全文输入约需 **90 秒**读完。

### 3.4 官方基准 `strata bench serve --suite serving-smoke`


`serial`（短 prompt 短输出）27.1 tok/s 与手工测得 27.5–30.2 一致。

### 3.5 DSpark 对照实验（关键否定结果）

调研文档 §5 外推“单卡 + DSpark 可达 35–45 tok/s”。实测：

| 配置 | 1024 tok 输出 | 512 tok | 短输出 16 tok | 引擎行为 |
|---|---|---|---|---|
| `--dspark auto`（默认） | **18.79** | 14.35 | 27.5–30.2 | **不加载** |
| `--dspark on`（强制） | **13.74（−26.9%）** | 12.40 | 23.4 | 加载，草稿接受率 **71–100%** |

引擎在 `auto` 下的拒绝理由（日志原文）：

> `DSpark not loaded: the routed experts (149 GB) are far more than the GPU holds (33 GB), where its verify rounds read 3.3x a token's bytes and gain nothing (--dspark on loads it anyway)`

强制开启后日志显示草稿命中率很高（`drafts 113 of 124 kept; per position 91%/94%/95%/100%/100%`），**但总速度仍下降**——验证轮次把专家读取字节数放大 3.3 倍，命中率再高也补不回来。

**结论：本机（专家 149 GB 主要在 CPU/SSD）应保持 `--dspark auto`，不要强制 `on`。** 视频中“四卡 R9700 + DSpark 55–69 tok/s”成立的前提是专家基本驻留显存，与本机拓扑不同。

### 3.6 2 并发试验（能否启动 + 速度如何）

**启动**：`--parallel 2` 从冷启动到 `loaded:true` 用时 **35 秒**，无报错、无 OOM。引擎日志确认生效：

```
ds4: --parallel 2: 2 conversations at once, each its own rings and KV
                  (0.12 GB more VRAM for the other 1, from the experts' room)
ds4: RAM store: up to 3521 slots of 11.4 MB (40.1 GB)   ← 单路时 3586 slots / 40.8 GB
maya ds4 serve: 2 conversations at once (--parallel): GEN needs rid=<id>
```

代价仅是显存多占 0.12 GB、RAM store 少 65 个槽（40.8 → 40.1 GB）。注意日志里 `tensor parallel 2 -> 1` 是**张量并行**降级（单卡无第二 GPU 可切分），与请求级并发无关，不影响本次试验。

**速度（严格交替 A/B，每轮先单路再 2 并发，各 3 轮取平均）**

| 输出长度 | 单路聚合 | 2 并发聚合 | 并发收益 | 2 并发下每请求 | 单请求延迟变化 |
|---|---|---|---|---|---|
| 512 tok（3 轮） | 14.72 tok/s | **23.27 tok/s** | **+58.1%** | 11.63 tok/s | 33.4–37.2 s → 43.4–44.9 s |
| 1024 tok（2 轮） | 17.24 tok/s | **24.34 tok/s** | **+41.2%** | 12.18 tok/s | 58.8–60.0 s → 83.3–84.5 s |

逐轮数据（512 tok）：单路 13.75 / 15.10 / 15.31，2 并发 22.78 / 23.44 / 23.59 —— **复现性很好，波动 <4%**。

**解读**

- 2 并发**可用且收益明显**，但**不是线性翻倍**（+41%～+58%，而非 +100%）。瓶颈仍是专家读取（RAM/SSD 带宽），两个请求能共用一部分窗口读取，故有增益但会被同一通道摊薄。
- **输出越短，并发收益越高**（512 tok +58% > 1024 tok +41%）：单请求的固定开销（首 token、冷专家读入）被第二个请求摊薄。
- **单请求延迟变差约 30–40%**（512 tok 从 34 s 到 44 s）。交互式单用户场景下 2 并发只带来延迟恶化；**适合"多人排队"而非"单人更快"**。
- 资源仍有余量：2 并发压测期间 `available 11 GiB`、引擎 RSS 43.7 GB、CPU 1961%（约 19.6 核），未触发 OOM。

**启动命令**

```bash
sg render -c 'cd /data/strata/terminal/0.1.56 && exec ./python/bin/python3.12 serve/server.py \
  --engine strata --config strata-deepseek-v4.1-flash-ist-das-2.25bpw.json \
  --port 8080 --parallel 2'
```

> `--parallel` 只覆盖本次运行的槽位数，不改写保存的 run config；去掉该参数即回到单路。

## 七、质量（短输出抽样，6 题）

> 按用户要求**不测“诊断分析”等长输出场景**，此处只做**≤300 token 的短问答事实核查**，用于确认 2-bit 量化后基础医学知识未崩塌。长病历分析与 Qwen 对照另行安排。

| 题 | 考察点 | 模型答案要点 | 判定 |
|---|---|---|---|
| Q1 脓毒症 | Sepsis-3 定义与诊断 | 感染致失调宿主反应引起的器官功能障碍；感染 + **SOFA 较基线 ≥2**；休克 = 升压药维持 MAP≥65 且乳酸>2；qSOFA 仅筛查 | ✅ 全部命中 |
| Q2 高钾急症 | 处理顺序 | 第一步**静脉钙剂**稳定心肌膜、拮抗心脏毒性，再降钾 | ✅ 正确 |

## 八、后续建议

1. **保持 `--dspark auto`**，不要再强制 `on`（实测负收益）。
2. **预热后再报数**：对外性能口径取“热态第二轮”，否则会低估 20–30%。
3. **若要提速，优先加内存**：本机瓶颈顺序是 RAM > SSD > GPU。62 → 128 GiB 可让更多专家留在 RAM（调研文档 §4.2 中 251 GB 配置达 25.6 tok/s）。
4. **临时性的 GTT/显存策略**：32 GB 卡把 30.8 GB 用满，若需同时跑视觉或更大上下文，需下调 `--max-context` 或 `--reserve-mib`。
5. **质量对照另开一轮**：本轮只做了 6 题短问答事实核查；诊断分析能力与 Qwen 3.56/5 的同题对照尚未做（需停机切换，62 GiB 无法并存）。
6. **GPU 权限永久化**：当前所有 GPU 操作依赖 `sg render`，建议重启一次登录会话或 `dsh-web.service`，使 `render` 组生效。
7. **并发策略**：多人同时使用时上 `--parallel 2`（聚合 +41%～+58%，单请求延迟 +30%～40%）；单用户交互场景保持单路，延迟更低。若要 4 路，需先实测显存与 RAM store 缩水（每多一路约让 RAM store 少 65 槽），并注意与 Qwen 的内存冲突。
