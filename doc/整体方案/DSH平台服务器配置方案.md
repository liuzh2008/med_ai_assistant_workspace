# DSH 平台服务器配置方案

> 状态：定稿（2026-09-07 单机档；2026-09-08 补 500 医生生产档 §7）
> 定位与分档：
> - **方案 A（单机档，§1-§6）**：台式机，DSH 平台 + MedAi 全家桶同机，面向**几十人**规模/试点（预算 7000-10000 元）。
> - **方案 B（500 医生生产档，§7）**：双片分片服务器 + 池化调度 + 网关双活，面向**500 名医生**生产（预算约 5-9 万元）。
> 均可达 iptables/容器隔离的 Linux 达标形态；本机 Windows 63.8GB 为试点主环境；100.66.1.4 为测试/形态验证机。

## 0. 分档选择

| 目标规模 | 采用 | 说明 |
|---|---|---|
| 1-3 人（生产 MedAi 配套） | 现有 MedAi 生产 VM 即可（7.3GB VM，实测约 2.4GB 需求） | 方案 v1.3 §4.6.3 |
| 几十人（30-50 账号 / 10-30 并发） | **方案 A（§1-§6）** | 单机 64GB 从容 |
| **500 名医生生产** | **方案 B（§7）** | 关键输入为峰值并发（建议按在线率 15-25% 估） |

## 1. 负载画像（据《DSH服务器化多租户平台架构方案》§4.6）

| 负载 | 量级 | 硬件要求 |
|---|---|---|
| MedAi 全家桶（同机） | ~6-8GB（100.66.1.4 容器实测口径：Oracle 21c XE、main、execution、redis、前端） | 内存；Java 多核 |
| DSH 实例池（近期） | 16-32 池 / 10-30 并发 ≈ 10-16GB | 内存瓶颈（~0.35GB/实例基线，阶段 0 实测校准） |
| DSH 实例池（远期 1 shard） | 50-80 池 ≈ 25-40GB | 内存扩容路线：64GB → 128GB |
| LLM 推理 | 不在本机（MedAi llmproxy/DeepSeek 出口） | 无需高端 CPU/GPU |
| 会话写入 | JSONL zstd 高频追加 | NVMe 必须 |

## 2. 配置清单（主力档）

| 组件 | 选型 | 备注 |
|---|---|---|
| CPU | AMD Ryzen 9 7900X（12C/24T） | 可选升级 7950X（16C/32T） |
| 主板 | B650E，4×DDR5 槽 | 内存扩展核心：2×32 起步 → 插满 128GB |
| 内存 | DDR5-5600 64GB（2×32GB） | 近期从容；远期补 2×32 至 128GB |
| 系统盘 | NVMe PCIe4.0 1TB | OS + 共享 DSH 代码（只读） |
| 数据盘 | NVMe 2TB（独立盘） | users/ 会话 + MedAi 容器 volume |
| 备份盘 | 4TB HDD 或 NAS | 每日增量备份，独立于数据盘 |
| 电源 | 750W 金牌 | 7×24 常驻 |
| 散热/机箱 | 塔式风冷；机箱 ≥3 盘位 | 长期散热冗余 |
| UPS | 在线式 1kVA（强烈建议） | 断电/写入中断防护 |
| 网络 | 板载 2.5GbE | 内网余量 |
| 系统 | Ubuntu Server 24.04 LTS | headless；BIOS 设断电来电自启 |
| 远程 | SSH + 向日葵/AweSun | 消费级无 IPMI |

## 3. 容量对应

- 近期同机：MedAi ~6-8GB + DSH 池 10-16GB + 系统余量 ≈ 64GB 从容。
- 远期同机（1 shard）：MedAi ~8GB + 池 25-40GB ≈ 64GB 吃紧 → 补至 128GB（4 槽插满即达，无主板更换）。

## 4. 预算

- 不含 UPS：约 7500-9500 元（2026-09 市场参考，以实际为准）。
- UPS：约 1000 元另计。

## 5. 采购与装机注意事项

1. 确认 CPU/主板组合支持 4×DDR5 满插稳定（查主板 QVL）。
2. 机箱需 ≥3 盘位（2 NVMe + 1 HDD）；NVMe 散热片齐备。
3. 数据盘与备份盘不同物理盘；上线后即配每日备份任务。
4. 装机后按《DSH生产部署指南.md》装 DSH + Docker（MedAi 容器）+ 方案 §3.2 目录布局初始化。
5. 接入内网前先完成：SSH 加固、UFW 白名单、审计日志、UPS 联动关机。

# 7. 方案 B：500 名医生生产配置

> 适用：全院 500 名医生账号、日常使用 AI 助手（查房/文书/质控）。
> 核心结论：**500 医生 ≠ 500 个常驻实例**；规格由**峰值并发活跃会话数**决定，且**必须实现池化调度**（按需启停 + 空闲回收）——否则 500 × 0.3GB = 150GB 光基线。

## 7.1 计算基线（实测锚点，非估算）

| 参数 | 取值 | 来源 |
|---|---|---|
| 实例基线 B（进程常驻） | **≈297MB/实例** | 100.66.1.4 实测（npm 干净版，8 实例稳定；dev 版 403-466MB 为上界） |
| 每活跃会话增量 S | ≈150-200MB（本档按保守 200MB 计） | 估算（架构方案 §7.2 待实测项） |
| 网关 | ≈80MB | 实测 |
| MedAi 全家桶（**仅方案 A 同机时**） | ~8GB | 容器实测 |

**内存公式**：`内存 ≈ 池上限 N × 0.3GB + 峰值活跃会话 C × 0.2GB + 20% 余量`
（N = 池上限即常驻实例数；C = 峰值活跃会话数；池化下 N ≈ C）

## 7.2 按峰值并发分档

| 场景（在线率） | 峰值并发 C | DSH 内存需求 | 建议规格 |
|---|---|---|---|
| 保守（10%，夜班/门诊低谷） | ~50 | 50×0.3 + 50×0.2 + 20% ≈ **30GB** | 单台 64GB |
| **推荐基线（20%）** | **~100** | 100×0.3 + 100×0.2 + 20% ≈ **60GB** | **2 台 64GB 分片**（每片 50 池，占用 ~25GB，余量充足） |
| 高峰（30%，早交班/查房高峰） | ~150 | 150×0.3 + 150×0.2 + 20% ≈ **90GB** | 2 台 96-128GB（每片 75）或 3 台 64GB |

> 在线率需业务确认；医生使用集中在早交班/查房/下班前文书时段，峰值占比通常显著高于日常均值。

## 7.3 推荐配置（2 片分片，每台 × 2）

| 组件 | 选型 | 说明 |
|---|---|---|
| CPU | AMD EPYC 4584PX / Ryzen 9 7950X（16C/32T），或 Xeon E-2488 + W680 | LLM 推理不在本机；16 核支撑 75-100 实例的工具/subagent 突发 |
| 内存 | **DDR5 ECC 64GB（2×32，留 2 槽扩 128）** | 覆盖 100-150 并发；医疗数据 + 7×24 建议 ECC |
| 系统盘 | 1TB NVMe（可选 RAID1） | OS + 共享 DSH 代码（只读） |
| 数据盘 | **2TB NVMe**（每用户 DSH_HOME + 会话） | 500 医生会话累积 ≈ 1-2TB/年（按 15 会话/天/人、zstd 后估算） |
| 备份 | 集中 **NAS 8-16TB**（两片用户目录每日增量） | 会话 JSONL 支持增量；必须独立于数据盘 |
| 网络 | 双 2.5GbE（bond） | 内网足够（流式文本流量小） |
| 电源 | 750W 铂金 + **在线式 UPS** | 长期常驻；断电防会话写入中断 |
| 系统 | Ubuntu Server 24.04 LTS（headless） | iptables/容器隔离达标形态；BIOS 来电自启 |
| 远程 | SSH +（可选）带外管理 | 消费级主板无 IPMI，生产建议选带 BMC 的服务器主板 |

## 7.4 架构组件（方案 B 组成）

```
500 医生浏览器
   │
   ├─ 负载均衡（nginx/HAProxy：userId 一致性哈希）
   │     └─ 网关 ×2（双活，2C/2GB，keepalived VIP）
   │
   ├─ 分片 1（250 用户；实例池上限 50-75）
   └─ 分片 2（250 用户；实例池上限 50-75）
        每片：池 supervisor（上限/LRU/空闲 30 分钟回收/预热）
        模型出口 → MedAi llmproxy（每用户独立 token + 配额）
```

- **分片路由**：userId 一致性哈希 → shard（架构方案 §4.6.5，网关持路由表，可热更新）
- **网关双活**：网关为唯一入口，必须冗余（双实例 + VIP / 反向代理健康检查）
- **池化调度**：每片一个 supervisor；`dsh-platform.sh` 原型需升级为池化版（当前为全常驻）
- **与 MedAi 分离部署**：DSH 平台独立服务器（本方案），MedAi 生产维持现有体系（llmproxy 为唯一模型出口）

## 7.5 预算

| 项 | 估算 |
|---|---|
| 分片服务器 ×2（16C/64GB ECC/4TB NVMe/冗余电源） | 约 2.5-3.5 万元/台 → **5-7 万元** |
| NAS 备份（8-16TB） | 约 0.8-1.5 万元 |
| UPS + 网关节点 + 网络 | 约 0.5-1 万元 |
| **合计** | **约 7-9 万元**（2026-09 市场参考，以实际为准） |

## 7.6 必须配套的改造（部署阶段工作项）

1. **池化调度**（架构方案 §4.2）：按需启停 + 空闲回收 + 上限/LRU + 预热；是规格能压到 2 台的前提
2. **每用户磁盘配额与归档**：会话累积治理、保留期策略、备份/恢复演练
3. **llmproxy 每用户配额治理**：500 个 machine token；**并确认 MedAi 后端（llmproxy/业务接口）自身能承载 500 医生并发**（该容量不在 DSH 服务器上）
4. **高可用**：分片故障时用户重调度、网关冗余、监控告警（内存/实例数/错误率）
5. **开户自动化与审计**：batch-provision 已有；审计日志无 PII、账号生命周期（入职/离职/停用）
6. **安全加固**：iptables/容器网络租户隔离、CSRF/限流、代码树只读、凭据 0600

## 7.7 待确认输入（决定最终规格）

| 输入 | 影响 |
|---|---|
| 500 医生的**峰值同时在用数**（建议按 15-25% 估，即 75-125） | 直接决定内存与分片数（§7.2 分档） |
| DSH 平台是否与 MedAi 生产同机 | 同机需再加 ~8GB 且资源竞争（**建议分离**） |
| 预算档位 / 是否可分批采购 | 预算紧可先 1 台 128GB 承载 100 并发，预留第二台分片位 |

## 7.8 采购与实施注意

1. 内存优先：预算向内存倾斜（ECC 优先），CPU 16 核足够；**不要为 DSH 配 GPU**（推理在 DeepSeek/MedAi 侧）。
2. 分片一致性：两台尽量同规格同批次，便于故障互备与重调度。
3. 数据盘与备份必须物理分离；上线即配每日备份 + 月度恢复演练。
4. 部署顺序：池化改造 → 监控/告警 → 试点扩员（50 → 150 → 250 → 500 分批）→ 全量。
5. 接入内网前完成：SSH 加固、UFW 白名单、审计、UPS 联动关机、BIOS 来电自启。
