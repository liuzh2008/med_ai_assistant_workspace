### 2026-08-16 DSH 插件化联调 + 解绑决策：网关宕机 → 对话期明示降级（用户拍板）
- **决策（用户拍板）**：`failOnStartupError: true → false`（**解绑**）——网关宕机时 DSH 照常启动，不再启动即失败。原因：医疗站点运维窗口不希望网关维护导致 DSH 整体不可用。
- **实现**：`@medai/dsh-pii-guard` 扩展"工具在位明示降级"——`agent/pre-step` 检查 `ctx.tools.schemas()` 是否含 `mcp__medai__*`（DSH 源码确认 API：`ctx.tools.schemas()/get(name)`，core/tools README）；缺失（启动时连接失败→mcp-client "activates with no tools"）→ 向 enter 决策注入唯一 system 提示（`DEGRADED_PROMPT`：明确告知"数据服务暂不可用"、严禁编造），去重防对话膨胀；注册表查询异常视为在位（不误报）。运行中宕机路径不变：工具已注册→调用失败 isError→agent 按提示明示 + M2-T8 工具在位告警。
- **关键认知（为何不能只改 false）**：mcp-client `failOnStartupError:false` 行为是"activates with no tools"（零工具）——纯解绑会退回"静默零工具"（agent 无工具可调→编造/空答）；必须叠加可用性提示注入，把零工具转化为 agent 可感知的降级。**解绑 = patch 改 false + 插件降级提示，二者缺一不可**。
- **联调事实**：web profile 已 `dsh plugin add`（pnpm add link）@medai/dsh-pii-guard + @deepseek-ai/dsh-mcp-client 0.0.1-rc.1；cordis.patch.yml 用 `- insert:` 新增实例（targeted `- id:` 对不存在行会报 "entry not found"）；`--dump-config` 验证组合（mcp-medai Authorization/failOnStartupError + dsh-pii-guard）；DSH 与后端 8081 保持 ESTABLISHED（mcp 激活成功）。用户手动重启 DSH（PID 变化）；browser 工具禁 127.0.0.1 回环（验证走 CLI/netstat 间接证据）。

### 2026-08-16 DSH 会话失效根治：MCP 切 STATELESS 无状态协议（数百台客户端零改动）
- **问题**：后端重启后 DSH 报 `Session not found`（streamable-http 服务端会话在内存，重启清空；mcp-client 重连仅由传输层 onclose 驱动，空闲短连接下后端快速重启不触发 → 会话僵死）。**生产影响**：医院主服务器重启 → 数百台 DSH 全部工具失效。
- **试错路径（记录避免重复）**：①DSH `cordis.patch.yml` 加 `reconnect` 策略（mcp-client 0.0.1-rc.1 官方配置，默认 500ms 翻倍/30s/10 次）——**实测无效**：重连由 onclose 驱动，空闲无连接 → 不触发；②M2 fork `mcp-spring-webmvc-0.18.3` 宽容会话——评估时发现 **SDK 0.18.3 自带 `WebMvcStatelessServerTransport` + Spring AI 1.1.6 `McpServerStatelessWebMvcAutoConfiguration`**（`ServerProtocol.STATELESS` 枚举）→ 无需 fork。
- **根治（已实施 + GUI 实测通过）**：`spring.ai.mcp.server.protocol=STREAMABLE → STATELESS`。无状态传输：无会话表、不返回 Mcp-Session-Id、每次 POST 独立处理（McpStatelessServerHandler 直接分发，无初始化/会话校验）→ **后端重启后客户端旧会话天然不失效**，数百台 DSH 零改动自动恢复。
- **验证**：tools/call 无会话前置直接可用；MCP 集成测试 69/69（protocol 断言改 STATELESS）；verify-mcp-gateway.sh PASS=6/FAIL=0（握手断言适配：无 Mcp-Session-Id 为正常）；**DSH GUI 实测持旧会话直接恢复**。
- **分层防御现状**：STATELESS（根治会话失效）+ reconnect（覆盖连接断开）+ @medai/dsh-pii-guard 降级提示（覆盖后端完全不可达）+ M2-T8 工具在位告警。
- **注意**：STATELESS 响应为普通 JSON（非 SSE 流）；`StringHttpMessageConverter` workaround 仍需（stateless 也 request.body(String.class)）；SDK ≥1.0 升级时重评估。

### 2026-08-14 LLM 代理与清洗架构定案：执行服务器代理 + 三层清洗（用户提出，已采纳升级）

### 2026-08-14 DSH 升级策略（本机部署形态下的必要性判断）

### 2026-08-14 造 vs 买对比：采用 DSH vs 自建类 harness 框架（对比结论已给出，待用户定夺）
- **核心原则（本对比最大结论）**：**"编排层可替换"**——业务能力全部走标准工具协议（MCP/工具 schema），编排层（DSH 或自建）可替换，避免被任一方锁定；此前全部设计（脱敏双层/审批/RBAC 复用/规范/映射表）在两种选择下均有效。
- **对比要点**：DSH=功能覆盖广（agent 循环/子代理/MCP/技能/定时/后台任务/GUI 全有，7 万+文件印证复杂度）、验证快（几天出演示）、生态跟上游，但 TS 栈、developer preview 破坏性变更、无认证/租户、Windows 沙箱仅文件写 partial、会话明文 JSONL，安全外围必须自建（已设计）；自建=Java 原生、认证/审计/审批可出生即带、代码完全自有（医院交付资质友好）、范围可裁剪（医疗不需要 shell/代码执行/子代理，仅需 DSH 功能的约 20%），但 agent 循环正确性极难（流式/工具调用/重试取消/上下文压缩/回放边角极多），核心循环 3-6 人月起 + 长期 0.5-1 人维护，无生态。

### 2026-08-14 脱敏双层防护决策：LLM 调用前出口兜底（用户提出，已采纳）
- **问题**：DSH 调 LLM 前必须脱敏；数据进 LLM 的通道不止工具结果——用户输入（口述姓名）、文件/技能内容、会话历史都可能带 PII，仅网关输出脱敏（数据面）不够。
- **决策**：双层防护——第 1 层源头脱敏（MCP 网关字段白名单+映射，已设计）；第 2 层 **LLM 出口脱敏插件**（DSH 侧 TS 插件，挂 `agent/pre-step` 改写消息 / `agent/request` waterfall 拦截）：确定性模式（身份证/手机/医保/住院号）正则掩码 + 姓名按网关下发映射表替换为泛化指代（"3床患者/患者P000123"）+ 残留不明 PII 阻断告警 + 审计每请求脱敏项数。
- **原则**：映射规则由 Java 网关维护下发（遵守"规则在 Java 侧"铁律）；性能用确定性正则+字典（不做 NER）；输入侧干净 → thinking/日志/回放全链无 PII。
- **关联**：方案文档 6.3 章、规范安全必检表已同步。

### 2026-08-13 AI诊断「改名后保留诊断依据」：行级绑定 + 四级显示匹配链
- **决策**：诊断依据展示从「按名称匹配」改为「行级绑定」——绑定以行的稳定标识（`d_<diagnosisId>` / `aim_<diagnosisId>` / `ai_<原始AI名归一化>`）为 key，与显示名称解耦；用户把同一诊断改成任何名称，绑定不丢。
- **显示匹配链**（`selectedDiagnosisBlock`）：行级绑定 → 归一化精确匹配 → 安全包含匹配（仅行名⊇块名，防"高血压"误配"高血压肾病"）→ 模糊匹配（Levenshtein ≥ 0.65，仅显示时 `allowFuzzy=true` 启用，命中带 `__fuzzy*` 标记并在依据上方显示黄色说明）。
- **原因**：名称可被改成任意值（如"高血压病3级 很高危"→"高血压病3级很高危"→无关名称），任何基于名称的缓存/匹配都无法保证改名后必然显示依据。
