- **内容去重**：同一 content 的消息不重复注入（agent 多轮 pre-step 触发幂等）。

### 2026-08-17 DSH P6-C6 sessionMap 会话分治设计（N2a dsh-session-sync）
- **select(contextKey) 唯一入口**：命中且会话存在（navigator.open=true）→ 恢复不新建；未命中或**命中但会话已消失（看门狗清理等）→ 重建并更新映射**（US-N2-02 边界，防映射指向死会话）；重入院 key 变化自然新建，N2 零医疗判断。
- **变更即持久化 + 失败不阻塞**：每次新建后立即 store.save（原子写 = 同目录 .tmp + rename，杜绝半写文件被读）；save 异常吞掉——内存映射始终可用，下次变更再写（降级铁律）；load 文件不存在/损坏 → 返回空映射不抛。
- **依赖注入抽象**：`SessionNavigator`（open/create，S1 会话导航 API 替换点）+ `SessionMapStore`（load/save）+ `FsPromisesLike`（node:fs/promises 接口子集，fsTypes.ts，仅 readFile/writeFile/rename）——测试与 DSH 环境均最小 fake 注入。
- **踩坑**：①测试自身 bug——启动加载用例的 fake 须把预加载 sessionId 加入“现存会话”集合（makeFakes(initialAlive)），否则 open 返回 false 走重建分支，断言“created=true 而非 false”；②session-sync 首次使用 node 模块 → 必须加 `@types/node`（^24，node 24.11.1）+ tsconfig types 加 "node"，否则 tsc 报 Cannot find module 'node:fs'。

### 2026-08-17 DSH P6-C5 identity 身份内存持有设计（N2a dsh-session-sync 首模块）
- **三态状态机 absent/active/logging-out**：`beginLogout`（收到 pre-logout）进入 logging-out 但 **JWT 保留至 flush 完成**（存档推送签名仍需要），`clearIdentity` 由 flush 编排器在完成后调用，作为“后续推送不再带该 JWT”的置空边界（验收 US-N2-01）。

### 2026-08-16 DSH 会话失效根治：MCP 切 STATELESS 无状态协议（数百台客户端零改动）

- **根治（已实施 + GUI 实测通过）**：`spring.ai.mcp.server.protocol=STREAMABLE → STATELESS`。无状态传输：无会话表、不返回 Mcp-Session-Id、每次 POST 独立处理（McpStatelessServerHandler 直接分发，无初始化/会话校验）→ **后端重启后客户端旧会话天然不失效**，数百台 DSH 零改动自动恢复。

- **分层防御现状**：STATELESS（根治会话失效）+ reconnect（覆盖连接断开）+ @medai/dsh-pii-guard 降级提示（覆盖后端完全不可达）+ M2-T8 工具在位告警。

### 2026-08-14 LLM 代理与清洗架构定案：执行服务器代理 + 三层清洗（用户提出，已采纳升级）

### 2026-08-14 造 vs 买对比：采用 DSH vs 自建类 harness 框架（对比结论已给出，待用户定夺）
- **核心原则（本对比最大结论）**：**"编排层可替换"**——业务能力全部走标准工具协议（MCP/工具 schema），编排层（DSH 或自建）可替换，避免被任一方锁定；此前全部设计（脱敏双层/审批/RBAC 复用/规范/映射表）在两种选择下均有效。
- **对比要点**：DSH=功能覆盖广（agent 循环/子代理/MCP/技能/定时/后台任务/GUI 全有，7 万+文件印证复杂度）、验证快（几天出演示）、生态跟上游，但 TS 栈、developer preview 破坏性变更、无认证/租户、Windows 沙箱仅文件写 partial、会话明文 JSONL，安全外围必须自建（已设计）；自建=Java 原生、认证/审计/审批可出生即带、代码完全自有（医院交付资质友好）、范围可裁剪（医疗不需要 shell/代码执行/子代理，仅需 DSH 功能的约 20%），但 agent 循环正确性极难（流式/工具调用/重试取消/上下文压缩/回放边角极多），核心循环 3-6 人月起 + 长期 0.5-1 人维护，无生态。

### 2026-08-14 脱敏双层防护决策：LLM 调用前出口兜底（用户提出，已采纳）
- **问题**：DSH 调 LLM 前必须脱敏；数据进 LLM 的通道不止工具结果——用户输入（口述姓名）、文件/技能内容、会话历史都可能带 PII，仅网关输出脱敏（数据面）不够。
- **决策**：双层防护——第 1 层源头脱敏（MCP 网关字段白名单+映射，已设计）；第 2 层 **LLM 出口脱敏插件**（DSH 侧 TS 插件，挂 `agent/pre-step` 改写消息 / `agent/request` waterfall 拦截）：确定性模式（身份证/手机/医保/住院号）正则掩码 + 姓名按网关下发映射表替换为泛化指代（"3床患者/患者P000123"）+ 残留不明 PII 阻断告警 + 审计每请求脱敏项数。
- **原则**：映射规则由 Java 网关维护下发（遵守"规则在 Java 侧"铁律）；性能用确定性正则+字典（不做 NER）；输入侧干净 → thinking/日志/回放全链无 PII。
- **关联**：方案文档 6.3 章、规范安全必检表已同步。

### 2026-08-25 实时语音 WS 被主系统 CORS 403：根因与治本（用户拍板改白名单）
- 现象：教学前端 8085 实时语音 `ws://100.66.1.3:8085/api/voice/realtime` 失败；**同一台电脑 MedAI(8080) 实时语音正常**。
- 根因（原始 Upgrade 模拟浏览器握手逐头分解定位）：403 响应体 `Invalid CORS request`，**由 `Origin: http://100.66.1.3:8085` 触发**——主系统 8081 `CorsFilter`（WebConfig + `app.cors.allowed-origins`）白名单**含 8080 与 localhost:8085，缺教学前端局域网地址**；浏览器 WS 握手必带 Origin → 403（WebSocketConfig 的 `setAllowedOrigins("*")` 不敌 MVC CorsFilter）。与 aTrust/网络/浏览器无关。
- 修复（dev，前端侧）：`vite.config.ts` `/api/voice/realtime` proxy 加 `configure` 钩子 `proxy.on('proxyReqWs', req => req.removeHeader('origin'))`（WS 不受浏览器同源限制）+ `server.allowedHosts: true`（防 vite DNS-rebinding 校验）→ 重启 8085 后完整浏览器握手（Origin+Ext+UA）101 ✓。
- 治本（用户拍板"改主系统 CORS 白名单"）：`src/main/resources/application.properties` 与 `deploy/main-linux-testServer/config/application.properties` 的 `app.cors.allowed-origins` 加 `http://100.66.1.3:8085,http://100.66.1.4:8085,http://100.66.1.1:8085`；生产（main-linux-oracle/-yanting）暂不加（用户确认教学系统生产未部署/未定）。教学前端生产容器 `med-teach-frontend/nginx.conf` 补 `location /api/voice/realtime` → `main-server:8081`（带 WS Upgrade 头；原 `/api/` 全转 8083 会导致生产 WS 失败）。
- 生效：dev 已由 vite 代理可用；src 白名单下次重启 8081 生效；testServer 部署时生效；生产部署教学系统时再配白名单。
- 排查方法可复用：**模拟浏览器 WS 握手用原始 http.request Upgrade（带 Origin/Sec-WebSocket-Extensions/UA），逐头定位 403 触发条件**（Node 内置 WebSocket 不带 Origin 会误判"代理通"）。
