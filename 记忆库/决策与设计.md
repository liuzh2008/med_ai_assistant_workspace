### 2026-08-13 建立项目自动长期记忆体系
- **决策**：用「AGENTS.md 强制协议 + memory-manager 技能 + 记忆库/ 文件库」三件套实现自动记忆，替代人工维护。
- **机制**：
  - 根 `AGENTS.md`（DSH 原生自动注入）强制每会话执行记忆协议；

- **关联**：AGENTS.md、`.qoder/skills/memory-manager/SKILL.md`、`记忆库/索引.md`

### 2026-08-14 诊断临床规则注入：白名单仅"诊断分析" + 规则同步两跳链路确认
- **决策**：`combinePromptContent` 收口注入的白名单收紧为 `Set.of("诊断分析")`（不含"诊断审查"）——Gate 2 审查 Prompt 由 `DiagnosisReviewListener` 组装（objectiveContent 末尾已含 `ClinicalExperienceProvider` 注入段）且同样走 `submitPromptInternal → combinePromptContent`，白名单含"诊断审查"会导致同一 Prompt 双份规则段。Gate 2 现有链路匹配源为 AI 输出、禁区特征词可命中，功能不缺失。
- **架构事实（两跳规则同步）**：`ClinicalRuleSyncService`（`@Profile("execution")`）从 GitHub 拉规则到 `RemoteClinicalRuleCache` 内存缓存，**不写 DB**；主服务器 DB 由 `ClinicalRuleUpdateService`（`@Profile("main")`）经 `POST /api/clinical-rules/sync`（异步 taskId 轮询）从执行服务器 API 拉全量后逐条 UPSERT（keywordMatch 匹配、版本相同跳过）。
- **架构事实（模板表无自动同步）**：运行时 Prompt 模板从主服务器 `PROMPT_TEMPLATES` 表读取（`promptTemplateRepository.findByPromptTypeAndPromptName`）；GitHub `prompt-templates/` 文件仅作版本库，模板补丁需双改（GitHub 文件 + `PUT /api/ai/updatePromptTemplate` 更新 DB 表）。
- **关联**：《诊断分析临床规则注入实施计划.md》（doc/迭代/诊断分析优化/）。

### 2026-08-14 DSH 安全评估要点（Idea 验证阶段，已向用户给出完整清单）
- **DSH 沙箱只约束文件写**：官方文档明示 "File effects are the whole policy vocabulary"（无网络/进程/设备/凭据限制）；Windows 后端为 WRITE_RESTRICTED 令牌且 `enforcement: 'partial'`——读、网络、进程可见性不受限（packages/sandbox/*/README.md）。→ 网络出口控制必须靠主机防火墙/代理，不能靠 DSH 沙箱。
- **无认证层**：identity 包仅匿名遥测 ID（"do not represent an authenticated account"）；会话 JSONL（~/.dsh/sessions/）持久化全部工具输入输出+thinking → PII 落盘、无限保留。
- **提示注入面大**：患者数据（病历/检验单）是不可信内容，经工具结果回填模型上下文；缓解靠 MCP 网关输出清洗/脱敏 + 写操作必审 + 网络工具禁用 + 会话按患者分开。
- **验证阶段安全基线**：只用本地脱敏测试库（211 条镜像，禁生产）、验证实例禁 shell/代码/web 工具、MCP 只读工具+输出脱敏、主机防火墙限制 DSH 出网（只放模型 API+后端）、关遥测、会话按患者分开、API key 限额。
- **状态**：本方案目前仅 Idea 验证阶段，未进入实施。

### 2026-08-14 DSH 模块插件化方向决策（用户已拍板，待出实施方案）
- **目标（三线全要）**：A. DSH agent 调用业务系统能力；C. 业务界面嵌入 DSH GUI；B. DSH 嵌入医生工作站（Vue）。优先级与路线：A 走 MCP/TS 工具插件，C 走 client bundle（dsh.client，可无 fork），B 走 ACP/JSON-RPC/iframe，B 最重放后期。

- **试点模块**：患者/病历/检验查询（只读）。
- **技术事实**：主服务器 pom 同时含 spring-boot-starter-websocket（传递 servlet web-mvc）与 webflux → servlet 栈为主，MCP starter 选 `spring-ai-starter-mcp-server-webmvc`（Spring AI 1.0.x，版本实施时定）。
- **合规要点**：DSH 会话日志（~/.dsh/sessions/ JSONL）会持久化工具输入输出 → MCP 工具输出必须全量脱敏（复用 PatientDataDesensitizationService），否则患者 PII 落盘违反全局约束。

### 2026-08-14 部署形态最终决策：仅本机部署，取消服务器集中路径（用户拍板：开发难度太大）
- **决策**：不再使用服务器部署；DSH 跑在医生机 127.0.0.1:3080（一人一机一账户），工作站以 iframe 内嵌调用（v1）或协议端点（四期）。此决策**取代**此前"服务器集中+认证接入层/本机优先"的部署定调。

### 2026-08-14 LLM 代理与清洗架构定案：执行服务器代理 + 三层清洗（用户提出，已采纳升级）
- **定案**：本机部署下 LLM 连接统一经**执行服务器代理**（医生机不再直连模型 API）；清洗三层——MCP 网关输出脱敏（数据面）→ DSH 侧轻量正则（前端减负）→ **执行服务器代理层权威清洗+阻断+审计（主防线，Java 实现）**。
- **收益**：出网面 N→1（纯隔离内网可行）；API key 仅存执行服务器（医生机零凭据）；限流/审计集中。
- **"足够"四前提**：①权威清洗在代理层（新增 DSH 专用 LLM 代理端点，现有链路无此能力）②代理层鉴权+HTTPS+限流配额 ③代理层日志管控与 .dsh/sessions 同等 ④残余风险销项（准标识符/供应商留存条款/医生机磁盘管控/代理层安全评审/姓名清洗权衡）。
- **结论**：安全焦点收敛为"守住执行服务器一处"；代理层按高价值目标独立评审。
- **关联**：方案文档 6.4 章新增。

### 2026-08-14 DSH 升级策略（本机部署形态下的必要性判断）
- **结论**：**功能上不必要，安全上必须跟踪**——钉住基线（47f943859b fork）可长期运行，因为业务能力在 Java/MCP 网关侧与 DSH 解耦；但 developer preview 无 LTS、依赖树巨大（node_modules 6 万+文件），"永远不升"不成立。
- **四类升级触发**（按优先级）：①安全通告/CVE（唯一强制级）②影响本项目场景的 bug（如 MCP 重连预算耗尽）③所需新功能（schedule/compaction 增强）④生态兼容。官方常规迭代/UI 打磨/用不到的功能**不必升**。
- **本机形态特性**：爆炸半径小（单机坏=该医生助手降级，工作站业务不受影响）→ 可科室灰度、逐台升级；代价=N 台分发，需走 medai-builds 发布通道 + 版本可见（内嵌界面显示版本号）。越久不升 rebase 距离越大 → 建议**季度/半年追平**一次（现有 DSH-custom 流程：rebase → 补丁重导出 → 构建 → 分发）。
- **关联**：方案文档 11.3 O1 行已更新。

### 2026-08-14 造 vs 买对比：采用 DSH vs 自建类 harness 框架（对比结论已给出，待用户定夺）
- **核心原则（本对比最大结论）**：**"编排层可替换"**——业务能力全部走标准工具协议（MCP/工具 schema），编排层（DSH 或自建）可替换，避免被任一方锁定；此前全部设计（脱敏双层/审批/RBAC 复用/规范/映射表）在两种选择下均有效。
- **对比要点**：DSH=功能覆盖广（agent 循环/子代理/MCP/技能/定时/后台任务/GUI 全有，7 万+文件印证复杂度）、验证快（几天出演示）、生态跟上游，但 TS 栈、developer preview 破坏性变更、无认证/租户、Windows 沙箱仅文件写 partial、会话明文 JSONL，安全外围必须自建（已设计）；自建=Java 原生、认证/审计/审批可出生即带、代码完全自有（医院交付资质友好）、范围可裁剪（医疗不需要 shell/代码执行/子代理，仅需 DSH 功能的约 20%），但 agent 循环正确性极难（流式/工具调用/重试取消/上下文压缩/回放边角极多），核心循环 3-6 人月起 + 长期 0.5-1 人维护，无生态。
- **阶段决策建议（已向用户提出）**：Idea 验证用 DSH（零成本探索）→ 正式立项时按触发条件定：①立项评审对 preview 第三方组件有合规障碍 ②医院要求完全自有代码 ③DSH 上游停更/授权变化 ④团队不愿投入 TS 且自建范围压到最小 → 任一命中则自建"医疗专用轻量编排层"（Java，范围=对话+工具+审批+定时+审计），业务插件零改动平移。
- **用户补充的关键区别（2026-08-14）**：DSH 本质是**开发者个人使用的单用户工具**，不适合多用户场景——账户/租户/配额/按用户审计/按用户配置无处安放，只能"单用户内核+自建多用户外壳"，且单用户假设仍从缝隙漏出（会话明文共盘、凭据按实例、审批假设单人在终端）；自建 harness 可把多用户作为第一公民、直接复用现有 RBAC/科室用户体系。此条是自建路线的最强结构性论据，已写入方案文档 5.2"定位结论"。
- **工作流驱动复核（2026-08-14）**：按《住院部医生日常工作流程》35 步拆能力簇量化——DSH 白送 ≈15 步（对话编排，恰是自建最贵的 3-6 人月）；选择无关 ≈10 步（查询/模板/脱敏/质控/语音）；自建占优 ≈8 步（时限告警/多级审批/多用户/工作站界面，恰是医疗命门）。结论：分阶段决策不变（Idea 验证用 DSH）；若自建，第一版范围=15 个生成类步骤所需最小编排层，其余共用同一套 MCP 工具。已写入工作流文档第 7 章。
- **状态**：用户尚未定夺；Idea 验证仍按 DSH 路线设计材料齐备。

### 2026-08-14 脱敏双层防护决策：LLM 调用前出口兜底（用户提出，已采纳）
- **问题**：DSH 调 LLM 前必须脱敏；数据进 LLM 的通道不止工具结果——用户输入（口述姓名）、文件/技能内容、会话历史都可能带 PII，仅网关输出脱敏（数据面）不够。
- **决策**：双层防护——第 1 层源头脱敏（MCP 网关字段白名单+映射，已设计）；第 2 层 **LLM 出口脱敏插件**（DSH 侧 TS 插件，挂 `agent/pre-step` 改写消息 / `agent/request` waterfall 拦截）：确定性模式（身份证/手机/医保/住院号）正则掩码 + 姓名按网关下发映射表替换为泛化指代（"3床患者/患者P000123"）+ 残留不明 PII 阻断告警 + 审计每请求脱敏项数。
- **原则**：映射规则由 Java 网关维护下发（遵守"规则在 Java 侧"铁律）；性能用确定性正则+字典（不做 NER）；输入侧干净 → thinking/日志/回放全链无 PII。

### 2026-08-13 AI诊断「改名后保留诊断依据」：行级绑定 + 四级显示匹配链
- **决策**：诊断依据展示从「按名称匹配」改为「行级绑定」——绑定以行的稳定标识（`d_<diagnosisId>` / `aim_<diagnosisId>` / `ai_<原始AI名归一化>`）为 key，与显示名称解耦；用户把同一诊断改成任何名称，绑定不丢。
