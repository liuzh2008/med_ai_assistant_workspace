### 2026-08-17 助手问"当前病人是谁"答不出——DSH 患者上下文链路三段断点与修复（US-N2-03 联调落地）
- 现象：工作站助手页（iframe 嵌 DSH 3080）输入"当前病人是谁"，AI 不知道当前选中的病人（答不出/反问）。

- **修复**：
  ① `medai-plugins/packages/@medai/dsh-session-sync/src/patientContextEndpoint.ts`（新增）：host 半注册 `POST /medai/patient-context`（经 `ctx.webServer.register`，`inject=['webServer']`）——工作站选中患者 fetch 直报 → `setHostPatientContext` → pre-step 注入。**绕过 client→host 通道问题**（spike 候选②"本地信任通道"的 HTTP 变体，零 DSH 内核改动）。端点含 Origin 白名单（仅 `:8080`）+ CORS 预检 + 载荷校验（null=清除）。测试 14 例；

- **验证**（RPC 直调 DSH）：`POST /medai/patient-context` 200 {ok:true}；`POST /api/session.create` + `session.prompt("当前病人是谁")` → session.history 事件 seq 出现 system 注入"当前患者：心血管一病区 3床 张*（patientId=P000123）"原文保留。
- **坑（可复用）**：
  ① **DSH_HOME 环境变量陷阱**：DSH 会话的 pwsh 环境 `DSH_HOME=C:\Users\Administrator\.dsh-dev`（开发实例）；`restart-dsh.ps1`/`start-dsh.cmd` 用 Start-Process 继承该变量 → 3080 启动加载错 profile → `listen EADDRINUSE 0.0.0.0:3081`（被 dev 实例占）。**启动 3080 必须显式 `$env:DSH_HOME='C:\Users\Administrator\.dsh'`**；watchdog 计划任务无此变量故正常。

### 2026-08-17 注入的上下文消息必须带 source 字段（否则"上下文注入"区不可见 + session.list 500 级联崩）
- 现象（第一轮修复后）：对话流"上下文注入"区只显示 AGENTS.md / dsh-system-prompt / skill-catalog，**看不到患者上下文**；随后 `session.list` 报 500 `Cannot read properties of undefined (reading 'kind')`，会话列表无法显示。
- **根因**：`injectPatientContext` append 的 system 消息**只有 {role, content}，无 source**；而 DSH 约定所有非 user 注入消息必须带 `source`（AGENTS.md=agent-instructions、system-prompt/skill-catalog=plugin）：
  ① 客户端 provenance 投影 `contextProvenance(event.data.source)`（context-provenance.ts）读不到 kind → label=null → 上下文注入区**不显示**该行；
  ② `session.list` 的投影 `applySessionListMetadata`（api-proxy.ts:514）`event.data.source.kind === 'user'` 对无 source 消息**直接崩** → 列表 500（一条坏消息崩整个列表）。
- **修复（三层）**：
  ① `patientContextInject.ts` 注入消息加 `source: {kind:'plugin', plugin:'@medai/dsh-session-sync'}`（会话文件实测：上下文注入区显示"@medai/dsh-session-sync"，source.kind 读取正常）；
  ② DSH 防御（3080 项目 deepseek-harness/packages/host/apiproxy/src/api-proxy.ts）：514 行 `event.data.source?.kind`、1344 行 `message.source?.kind` 加可选链（历史遗留无 source 消息不崩列表/队列投影）；
  ③ **历史会话文件修复**：把已写入的无 source 注入消息补 source——zstd 多帧解压（按 magic 0x28B52FFD 找帧边界逐帧解）→ JSONL 逐行改 → 重新压缩**必须保持多帧结构**（帧1=恰好一行 session header，帧2+=事件批次，每帧带 `ZSTD_c_checksumFlag:1`），否则 DSH 启动报 `corrupt Zstandard session log: first frame is not exactly one header line`（assertZstdHeaderFrame）。已验证：82 会话 7 条注入全部带 source，session.list 恢复 80 条。
- **教训（可复用）**：①任何 pre-step/上下文注入插件，注入消息**必须带 source**（kind/plugin 自证身份）——既为 UI 可辨，也避免 DSH 读取 source.kind 的路径崩溃；②DSH 会话 zstd 文件是"多帧串联"容器，第一帧必须恰为一行 header；改文件要按帧重建；③DSH 对注入消息 source 的约定是隐式强制的（多处 `event.data.source.kind` 无防御直读）。

### 2026-08-17 pre-step 注入消息 content 必须是数组——字符串 content 导致 LLM 全部 TRANSPORT
- 现象：注入修复后 LLM 调用仍全部失败（`DeepSeek API stream from https://api.deepseek.com failed` code=TRANSPORT，重试 3 次都失败）；而独立 node 脚本（fetch + parseSse + translate 同链路）完全正常——API/网络/key/模型/流式全部无问题。

- **教训（可复用）**：①**DSH 消息模型 content 恒为数组**（ContentBlock[]），任何 pre-step 注入/改写必须用数组，字符串会以 `content.some is not a function` 的形式崩在序列化层（错误表现为 TRANSPORT，极易误判为网络问题）；②TRANSPORT 的 cause 链排查方法：给 llm-deepseek adapter 258 行临时加 console.error 打印 cause（进程 stderr 可见），定位后还原；③对比"有注入/无注入"会话的 finish 状态可快速二分注入类问题；④独立 node 复现要**走 DSH 的 serialize/translate 链路**，直接拼 body 发 API 会绕过崩溃点。

### 2026-08-17 pre-step 注入消息必须满足 DSH 持久化验证（id + role=user）——缺 id 报 "lacks an identified message"
- 现象：注入修复后，打开含注入消息的会话历史报 `SessionPersistenceCorruptionError: stored session ... failed validation: session event at seq 11 lacks an identified message`。
- **根因**：DSH 持久化验证（core/session/src/index.ts `assertMessageEventShape`）对 `user/message` 事件的消息强制要求：**`id` 非空字符串** + **`role === 'user'`** + source.kind 非空 + content 数组。我们的注入消息（role='system'、无 id）不满足 → 从文件加载/读历史时验证失败。**注意**：live 会话（内存）不触发验证，重启后从文件加载才暴露。
- **修复**：`injectPatientContext` 消息结构对齐 DSH 官方 pre-step 注入（time-context 的 `createUserMessage` 契约）：`{role:'user', id: crypto.randomUUID(), content:[{type:'text',text}], source:{kind:'plugin',plugin:'@medai/dsh-session-sync'}}`——**role 用 user**（事件层 user/message 约定，官方注入 agent-instructions 等事件 role 也是 user；source 区分身份），id 必填。测试 102 全绿 + tsc 零错。
- **历史会话修复**：批量脚本给所有含注入消息的会话文件补 id + role 改 user（多帧 zstd 重写，保留 .bak2）。12 个会话文件修复；session-2505ec38 等历史加载恢复 OK。
- **验证（端到端）**：设患者 P000123 → 新会话问"当前病人是谁" → 注入消息 `{role:'user', id:'7ec3928d…', content:[{type:'text',text:'当前患者：心血管一病区 3床 张*（patientId=P000123）…'}]}`；finish fails=0 oks=4；AI 回答"当前患者为心血管一病区 3床 张*（patientId=P000123）"并尝试调工具交叉验证。
- **教训（可复用）**：①pre-step 注入消息**必须带非空 id 且 role 用 'user'**（对齐 DSH createUserMessage 契约）——role='system' 或缺 id 会在持久化验证失败（历史加载报 corruption）；②验证是否通过：重启后 RPC `session.history` 读该会话（触发 adoptStoredEvents 验证）；③修复历史会话文件流程可复用（解压多帧 → 改行 → 多帧重写：帧1 一行 header + checksum）。

### 2026-08-17 MCP 双因子落地过程中的四个坑（服务 JWT 交换方案）
- **① cordis.patch.yml 的 `!!js` 值必须是合法 JS 表达式**：`X-MedAI-Machine-Token: !!js '${process.env.X}'` 会 SyntaxError（`$` 开头非法）；必须写 `!!js 'process.env.X'`（直接表达式）或反引号模板 `!!js '`Bearer ${...}`'`（Authorization 带前缀时用模板）。

### 2026-08-14 sqlplus 批量导出脚本的三个坑（生产诊断分析数据提取）
- **PROMPT 行尾不能带 `--`**：sqlplus 把 `--` 当注释吞掉行尾换行符，导致下一行 SQL 首行被合并进注释行，报 SP2-0734（"未知的命令开头 FROM ..."）。PROMPT 行改用 `====` 或纯文本分隔。
- **NLS_LANG 不设置导致中文 LIKE 全空**：sqlplus 客户端字符集与库不一致时，`WHERE PromptTemplateName IN ('诊断分析','鉴别诊断分析')` 匹配为空、导不出数据且无报错。执行前必须 `set NLS_LANG=SIMPLIFIED CHINESE_CHINA.AL32UTF8`（已内置 run_extract.bat）。
- **ORA-64203 目标缓冲区太小**：`SUBSTR(TO_CHAR(CLOB),1,2000)` 组合报错；导出 CLOB 大字段直接用 CLOB 列 + `SET LONG 200000000 / SET LONGCHUNKSIZE 200000000 / SET LINESIZE 32767`，不要先 TO_CHAR。
- **SPOOL 单行导出需转义**：换行/制表符转义用 `\u000A`/`\u0009`（而非 `\n`/`\t`，避免与原文字面量冲突），分隔符 `|#|` 内容中出现时替换为 `¦#¦`（Python 侧 unescape 还原）。
