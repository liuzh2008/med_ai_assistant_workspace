### 2026-08-29 Docker 构建卡死根因与修复：apt universe 全量下载 + APP_VERSION 使层缓存失效
- **现象**：`docker build --build-arg APP_VERSION=0.9.283 -t med-ai-main:latest -f Dockerfile .` 卡在 `[stage-1 3/10]`（换 aliyun 源 + apt-get update）166.7s 未完成——卡在下载 `resolute/universe amd64 Packages [20.1 MB]`；且**每次构建都重新下载**（apt 层从未成功完成过，无缓存）。
- **根因①（apt 源过宽）**：`eclipse-temurin:21-jre` 基础镜像已是 Ubuntu resolute（26.04），DEB822 源（/etc/apt/sources.list.d/ubuntu.sources）含 main/restricted/universe/multiverse + deb-src 全组件 → `apt-get update` 需下载 20MB+ 索引；实测本机到 mirrors.aliyun.com 带宽仅 **~37KB/s** → 20MB 需 9 分钟+，观感即"卡死"（网络慢是主因，非镜像问题）。
- **根因②（层缓存失效，解释"每次构建都下载"）**：主 Dockerfile 中 `ARG APP_VERSION` + `LABEL version="${APP_VERSION}"` 声明在 apt 安装层**之前**（原 17-22 行 vs 30 行）→ 版本号每次变化（0.9.281→0.9.283…）→ LABEL 层内容变 → **其后所有层缓存失效**，包括 apt 层 → 每次构建从头 apt 下载。
- **修复（`med_ai_assistant_1.0_bs_backend/Dockerfile`）**：①层序重排——时区/apt 安装挪入"稳定层区"（在 ARG/LABEL 之前），版本号相关放"易变层区"最后；②apt 源收窄——sed 只保留 `Components: main`、删 deb-src（DEB822 与传统 sources.list 双格式都处理）→ update 下载量 20MB+→**3.6MB**；③加 `apt-get update -o Acquire::Retries=5 -o Acquire::http::Timeout=30` 防网络抖动无限卡死；④安装加 `--no-install-recommends`。
- **验证**：第一次构建（apt 层首跑）98.9s 完成（3.6MB，37KB/s 带宽）；第二次构建（版本改 0.9.284 模拟发版）apt 层 4 个 step 全部 **CACHED**、仅版本层重跑，**总耗时 2.7s**。执行服务器 `deploy/execution-linux/Dockerfile.execution.linux` 同步修复（同逻辑：收窄 main + 超时重试；其版本号硬编码无缓存失效问题，仅首次下载慢）。
- **教训（可复用）**：①Dockerfile 分层铁律——**易变层（ARG/LABEL/COPY 产物）放最后，稳定层（换源/装包/时区）放最前**，否则版本号一变成批缓存失效；②国内构建 apt 源只保留用到的组件（curl/netcat 都在 main，universe 20MB 纯浪费），apt-get update 卡住先看是"下载量大"还是"带宽低"（`curl -w "%{speed_download}"` 实测）；③PowerShell 跑 docker build 时 stderr 走 NativeCommandError 会显示 exit 1 误报，以日志尾部 `naming to ... done` 判断真实结果；④`Acquire::Retries`/`Acquire::http::Timeout` 是 apt 防挂死的标配。
- 关联：med-ai-main 镜像构建（0.9.283），build-and-export.sh 步骤 2。

### 2026-08-28 EMR 患者 AI 诊断过少根因：入院记录数据源被"拍板简化"断链 + 前端绕过准入校验

- **教训（可复用）**：①**数据源降级被"拍板简化"时必须评估存量场景**——"只查病历记录"只考虑了首诊流水线（医生本系统录入），漏了 EMR 同步患者（入院记录在 EMR_CONTENT）→ 诊断分析/文书缺入院记录；降级策略变更要覆盖两种数据源患者。②**前端提交路径必须与后端准入校验对齐**——后端有"无入院记录数据"跳过校验，前端 addPrompt 直接保存绕过 → 静默缺数据。③**排查"AI 输出不符合模板规则"先验证输入**（PROMPTS.OBJECTIVECONTENT 各数据块）再怀疑模板——全覆盖规则只能保证"输入什么覆盖什么"。④**关键数据源降级规则要加防误改机制**（抽方法+javadoc 硬约束+守卫测试），防止"拍板简化"再次把多级降级改回单一数据源。

### 2026-08-26 备课诊断审查"生成失败"根因：前端 axios 全局 30s 超时（+ PowerShell 响应中文长度误判）

### 2026-08-21 后台 job 启动 3080 会被回收（分离启动才是持久方案）
- **现象**：用 pwsh `run_in_background` 启动 `pnpm dsh web`（3080），验证时正常（host 端点 200），随后用户报 **100.66.1.3:3080 拒绝连接**——排查发现 3080 进程消失（`job_list` 空 = job 已结束，其子进程 pnpm/node 被连带终止）。

- **验证**：100.66.1.3:3080/medai/flow-board HTTP 200（counts + 63 患者）、client bundle 含新代码（medai-flow-badge 标记 15233 字节）。

### 2026-08-14 sqlplus 批量导出脚本的三个坑（生产诊断分析数据提取）
- **PROMPT 行尾不能带 `--`**：sqlplus 把 `--` 当注释吞掉行尾换行符，导致下一行 SQL 首行被合并进注释行，报 SP2-0734（"未知的命令开头 FROM ..."）。PROMPT 行改用 `====` 或纯文本分隔。
- **NLS_LANG 不设置导致中文 LIKE 全空**：sqlplus 客户端字符集与库不一致时，`WHERE PromptTemplateName IN ('诊断分析','鉴别诊断分析')` 匹配为空、导不出数据且无报错。执行前必须 `set NLS_LANG=SIMPLIFIED CHINESE_CHINA.AL32UTF8`（已内置 run_extract.bat）。
- **ORA-64203 目标缓冲区太小**：`SUBSTR(TO_CHAR(CLOB),1,2000)` 组合报错；导出 CLOB 大字段直接用 CLOB 列 + `SET LONG 200000000 / SET LONGCHUNKSIZE 200000000 / SET LINESIZE 32767`，不要先 TO_CHAR。
- **SPOOL 单行导出需转义**：换行/制表符转义用 `\u000A`/`\u0009`（而非 `\n`/`\t`，避免与原文字面量冲突），分隔符 `|#|` 内容中出现时替换为 `¦#¦`（Python 侧 unescape 还原）。

### 2026-08-27 生产容器版本 0.9.180 根因：Dockerfile APP_VERSION 与 pom.xml revision 双版本机制脱节
- 现象：生产 `docker exec med-ai-main cat /app/version.txt` = 0.9.180，即使代码已提交 0.9.281；曾误判"修复未上线"。
- 根因：**Maven 版本（pom.xml `<revision>`）与 Docker 构建参数（`Dockerfile ARG APP_VERSION`）是两套独立机制**。`build-and-export.bat` 的 `docker build -t med-ai-main:latest -f Dockerfile .` 从未传 `--build-arg APP_VERSION` → Dockerfile 默认值 `ARG APP_VERSION=0.9.180` 生效 → `version.txt` 与 `LABEL version` 恒为 0.9.180；而 jar 内部 `MANIFEST.MF Implementation-Version` 才是 0.9.281（来自 mvn revision），两者不一致导致版本验证混乱。
- 修复（已实施）：`build-and-export.bat` Step1 后从 pom.xml 提取 `<revision>`（`for /f "tokens=2 delims=>"` + `delims=^<` 两级解析，已验证输出 0.9.281）→ `docker build --build-arg APP_VERSION=!APP_VERSION!`；Dockerfile 默认值同步更新为 0.9.281 并加注释。验证：`docker exec med-ai-main cat /app/version.txt` 应与 jar 版本一致。
- 教训：**验证镜像版本要看 jar 内部 `MANIFEST.MF Implementation-Version` 而非仅 version.txt**（version.txt 由构建参数写入，可失真）；docker save 的 tar 可直接 `tar -xf` 解出 `blobs/sha256/*`，最大 layer 含 app.jar，用 `[System.IO.Compression.ZipFile]` 读 MANIFEST 核对版本。

### 2026-08-27 生产"已处理完但取不回"真正根因：PROMPTRESULT 缺 PROMPTID 索引 → NOT EXISTS 相关子查询卡死 → fixedDelay 轮询被阻塞
- 现象：生产新 Prompt 提交后执行服务器已完成（ENCRYPTED）但主服务器 24 分钟取不回；`SELECT COUNT(*) ... NOT EXISTS (SELECT 1 FROM PROMPTRESULT...)` 直接无响应；日志持续"数据不一致告警 - 已完成, ResultId: null"。
- 根因链（生产实证）：①`PromptRepository.findIncompleteCompleted` 用 `NOT EXISTS (SELECT 1 FROM PromptResult pr WHERE pr.promptId = p.promptId)` 相关子查询，**PROMPTRESULT 表无 PROMPTID 索引** → 对 PROMPTS 每行执行一次 PROMPTRESULT 全表扫描 → 查询卡死（几十万行×全表扫）；②该查询被 `checkDataConsistency()` 每轮调用（队列空时），且 **do-while 一次性处理全部脏数据**（当时 2127 条，每条跨库查 PromptResult+独立事务标记失败）；③`pollSubmittedPrompts` 是 `@Scheduled(fixedDelay)`——**上一轮执行不完，下一轮不启动** → 轮询线程被一致性检查占死 → 新记录永远取不回。
- 修复（已实施）：
  1. 生产：`CREATE INDEX idx_promptresult_promptid ON PROMPTRESULT(PromptId);`（查询秒回，dirty=2127）→ 循环 UPDATE 标记"执行失败"（每次 200 条 COMMIT，直到 0 行）；
  2. 代码：`findIncompleteCompleted` 由 NOT EXISTS 相关子查询改为 `LEFT JOIN PromptResult ... WHERE p.resultId IS NULL OR pr.promptId IS NULL`（+DISTINCT，防 1:N 重复）；
  3. 代码：`checkDataConsistency` 加单轮上限 `MAX_CONSISTENCY_BATCH_PER_ROUND=100`（do-while 翻页受 totalInconsistent 约束，防止数千条一次性处理拖死轮询，剩余分多轮清理）；
  4. 测试：+2 例（2.3-9 单轮处理、2.3-10 上限截断），35 例全绿。
- 教训：①**生产偶发"取不回"先查相关子查询表的索引**（NOT EXISTS/IN 子查询依赖驱动表连接列索引，缺索引=全表扫描卡死）；②`@Scheduled(fixedDelay)` 下**任何同步长任务都会阻塞后续调度**——巡检/清理类任务必须限单轮量或拆独立调度线程；③一致性/巡检查询用 LEFT JOIN+IS NULL 替代 NOT EXISTS 相关子查询是标准防卡写法。

### 2026-08-27 脏数据"清理不完"根因：ConsistencyCheckService 与 checkDataConsistency 状态横跳死循环
- 现象：生产清理"已完成但ResultId=null"脏数据后，`SELECT COUNT(*)` 不降反升（6→40→54→...→131）——**有源头在持续制造脏数据**。
- 根因（双服务打架）：`ConsistencyCheckService`（每5分钟 `@Scheduled(fixedDelay=300000)`）的 `checkSentDataWithIncompletePrompts`：执行服务器数据 SENT 但 Prompt 非"已完成"时**无条件 `transitionStatus(STATUS_COMPLETED)`，不回填 ResultId、不校验 PromptResult 是否存在**；而 `PromptStatusManager` 状态机明确允许 `执行失败 → 已完成`（STATUS_FAILED 行含 COMPLETED）。于是：
  ```
  ConsistencyCheckService: SENT+Prompt非已完成(含"执行失败") → 强制置"已完成"(无ResultId=制造脏数据)
  checkDataConsistency(轮询): "已完成"但ResultId=null无PromptResult → 标记"执行失败"
  → 下轮 ConsistencyCheckService 又把"执行失败"拉回"已完成" → 无限横跳，脏数据只增不减
  ```
- 修复（已实施）：`ConsistencyCheckService.checkSentDataWithIncompletePrompts` 三处收紧——①**尊重"执行失败"终态**（跳过不覆盖，切断横跳）；②置"已完成"前校验 PromptResult 存在：无有效 PromptResult → 标记"执行失败"（不制造脏数据）；③有有效 PromptResult → 先回填 ResultId 再置"已完成"。新增 `ConsistencyCheckServiceTest` 3 例（终态跳过/无结果标失败/有结果回填），78 例全绿。
- 教训：**状态机允许的回退路径（执行失败→已完成）必须由业务侧守住**——任何"同步置已完成"的巡检逻辑都要先校验结果数据存在并回填关联ID，否则两个修复机制互相覆盖=死循环；排查"数据越清越多"优先怀疑**两个定时/巡检服务对同一状态字段互写**。
