### 2026-08-14 科室列表 500 的根因链：ORA-28001 → 后端启动失败 → 前端代理 500
- 现象：打开 http://100.66.1.3:8080 登录页输入用户名后"获取科室列表失败: Request failed with status code 500"。
- 根因链：本机 Oracle system 账号密码过期（ORA-28001）→ 后端 Flyway 拿不到连接启动崩溃 → 8081 无监听 → 前端 dev server 代理 `/api`→`localhost:8081` 报 ECONNREFUSED 转成 500（http-proxy-middleware 的 "Proxy error: Could not proxy request ... ECONNREFUSED" 是典型信号）。
- 排查路径：curl 8080/health 返回 Express 风格 "Cannot GET /health" 说明是 Node dev server 而非 nginx；`logs/application.log` 尾部 FlywaySqlException + ORA-28001 定位。
- 修复：`ALTER USER system IDENTIFIED BY Liuzh_123 ACCOUNT UNLOCK;` + 防复发 `ALTER PROFILE DEFAULT LIMIT PASSWORD_LIFE_TIME UNLIMITED;`（开发库）。
- 注意：ORA_CIS_PROFILE=90 天、ORA_STIG_PROFILE=35 天的 profile 不覆盖 system，只改 DEFAULT 即可。

### 2026-08-14 测试库(100.66.1.4)与本机库(100.66.1.3)结构差异与 Data Pump 同步要点
- 两库同名表 205 张（全在 SYSTEM schema），本机多 12 张本地表（ALERT_RULES/DISCUSSION_SESSION/DRG_*/MTL_TEST*/PATIENT_COMPREHENSIVE_DATA/TEMP_*/TESTENTITY/TR_TEACHING_REFORM_PAPERS 等）；表结构差异在列级：本机缺 30 列（主要是 V_INP_BILL_DETAIL_INFO 视图 18 列、V_EXAM_REPORT_INFO 表 11 个中文列、TEACHING_PLANS.OBJECTIVES），本机多 266 列（含 SQL Developer 的 MGV_* 视图、新实体列 PPT_*/OBJECTIVE_TEXT 等）。
- **ID 生成机制不同**：测试库=触发器+序列（命名 `TABLE_SEQ`，如 PROMPTS_SEQ）；本机库历史=Hibernate 序列（`TABLE_COL_SEQ`，如 PROMPTS_PROMPTID_SEQ）或 IDENTITY。当前后端代码：Prompt/PromptResult/TodoItem 等实体用 `GenerationType.IDENTITY`（靠 BEFORE INSERT 触发器+序列填充，Hibernate RETURNING 取回），ConversationHistory/Diagnosis/PromptTemplate 等用显式 `@SequenceGenerator`（测试库命名）。
- 陷阱：TABLES-only 导出**不带序列**→ REPLACE 导入后触发器引用缺失序列全部 INVALID（ORA-02289）；必须补建测试库命名序列（25 个）+ `ALTER TRIGGER ... COMPILE` + 序列 RESTART 到 MAX(PK)+1。
- 陷阱：REPLACE 导入会**丢掉本机独有列**（PPT_*/OBJECTIVE_TEXT/CREATED_AT 等），导入后要用 ALTER TABLE ADD 回补。
- 陷阱：本机多数表**无 PK 约束**（测试库 schema 约束稀薄，70 表仅 43 约束），序列重同步不能用 PK 元数据驱动，要用显式 (序列→表.列) 静态映射；LABRESULTS 的 ID 列是 `ID` 不是 LABID。
- 陷阱：Data Pump parfile 路径**不能含空格**（LRM-00109 把 'D:\MedAiAssistant' 当文件）；dump 放 `D:\oracle_dump` 无空格路径，DIRECTORY 对象 DSH_DUMP 指过去。
- 陷阱：`data_default` 是 LONG 列不能 `||` 拼接（ORA-00932），列清单查询用 NVL(TO_CHAR(...),'-') 占位避免空字段错位。
- expdp 排除内部表模式：`AQ$%|LOGMNR%|LOGSTDBY%|MVIEW%|OL$%|ROLLING$%|SCHEDULER_%|SQLPLUS_PRODUCT_PROFILE|PRODUCT_PRIVS|MGV_%`（129 内部 / 76 应用表）。
- 测试库 Oracle 是 gvenzl/oracle-xe:21 容器（21.0），本机 21.3，同大版本 Data Pump 兼容无需 VERSION 参数。

### 2026-08-13 AI诊断依据匹配的前端踩坑（med_ai_assistant_1.0_bs_vue）
- **Levenshtein 模糊匹配会"张冠李戴"**：实测「高血压/低血压」相似度 0.667、「1型糖尿病/2型糖尿病」0.800，均 ≥ 0.65 阈值会误关联——向医生展示错误依据不可接受。最终方案：模糊匹配仅在显示诊断依据时启用（`allowFuzzy=true`），命中带 `__fuzzy*` 标记并在依据上方显示黄色说明；建立行级绑定时禁用。
- **名称匹配无法保证改名后保留依据**：名称可被改成任意值（如"高血压病3级 很高危"↔去空格↔无关名）。解法是行级绑定（stableRowKey 用 diagnosisId/AI 原始名，与名称解耦）。
- **编辑工具重写文件会丢 UTF-8 BOM**：write/edit 修改 .vue 文件后首行 BOM 消失，git diff 出现无意义首行变更；需用 `[System.IO.File]::WriteAllText($path, $content, (New-Object System.Text.UTF8Encoding($true)))` 恢复。
- **node --test 加载 src/utils 报 ERR_MODULE_NOT_FOUND**：node 无法解析 webpack 的 `@` 别名，且 ESM 导入必须带扩展名；utils 内跨文件导入用相对路径 + 显式 `.js`（如 `./stringSimilarity.js`），webpack 同样支持。
- **git rebase --continue 在非交互终端卡死**（打开 vim 等编辑器直到超时）：先 `git add` 解决冲突，再 `$env:GIT_EDITOR='true'; git rebase --continue`。
- **PowerShell 里 git commit -m 内嵌双引号会拆参数**（`\"` 不是转义）：提交信息整体用单引号包裹。

### 2026-08-14 sqlplus 批量导出脚本的三个坑（生产诊断分析数据提取）
- **PROMPT 行尾不能带 `--`**：sqlplus 把 `--` 当注释吞掉行尾换行符，导致下一行 SQL 首行被合并进注释行，报 SP2-0734（"未知的命令开头 FROM ..."）。PROMPT 行改用 `====` 或纯文本分隔。
- **NLS_LANG 不设置导致中文 LIKE 全空**：sqlplus 客户端字符集与库不一致时，`WHERE PromptTemplateName IN ('诊断分析','鉴别诊断分析')` 匹配为空、导不出数据且无报错。执行前必须 `set NLS_LANG=SIMPLIFIED CHINESE_CHINA.AL32UTF8`（已内置 run_extract.bat）。
- **ORA-64203 目标缓冲区太小**：`SUBSTR(TO_CHAR(CLOB),1,2000)` 组合报错；导出 CLOB 大字段直接用 CLOB 列 + `SET LONG 200000000 / SET LONGCHUNKSIZE 200000000 / SET LINESIZE 32767`，不要先 TO_CHAR。
- **SPOOL 单行导出需转义**：换行/制表符转义用 `\u000A`/`\u0009`（而非 `\n`/`\t`，避免与原文字面量冲突），分隔符 `|#|` 内容中出现时替换为 `¦#¦`（Python 侧 unescape 还原）。

### 2026-08-14 Java `Set.of()`/`Map.of()` 的 contains/get(null) 直接抛 NPE
- 现象：`ClinicalRuleInjectConfig.INJECT_TEMPLATE_NAMES = Set.of("诊断分析")`，当 `prompt.getPromptTemplateName()` 返回 null 时 `Set.of(...).contains(null)` 抛 NPE（不可变集合拒绝 null），提交链路静默失败；随后 `provide()` 返回 null 时再调 `isEmpty()` 又抛 NPE，双重叠加难定位。
- 修复：先 `templateName != null &&` 前置判空再 contains；`provide()` 返回值判空后再判空串（PromptSubmissionService:505 与 PromptExecutionController:451 同改）。
- 教训：凡「白名单/配置集合查 null 入参」一律先判 null；第三方门面方法返回值可能为 null 时，判空与判空串必须成对出现，测试须覆盖 templateName=null 与 provide()=null 两分支。

### 2026-08-14 JUnit 类级并行（parallelism=4）导致 surefire 报告交错覆盖
- 现象：同一测试类串行执行有 8 个 @Test，并行模式下 surefire 单类报告显示 Tests run: 2，XML 里混入其他测试类的 testcase，单类报告数字不可信，误判测试未跑全。
- 处理：汇总以 `mvn test -Djunit.jupiter.execution.parallel.enabled=false` 串行输出为准（单类验证可用 `-Dtest=XxxTest` 单独跑）。
- 教训：项目 pom 配置了 `junit.jupiter.execution.parallel.mode.classes.default=concurrent` 时，核对测试数量/失败数一律用串行模式汇总，不要引用并行模式下的单类报告。

### 2026-08-14 @SpringBootTest 限定 classes 时 ObjectMapper 无 Bean（诊断词典集成测试）
- 现象：@SpringBootTest(classes = {DiagnosisDictCache.class, DiagnosisDictLoader.class, ...}) 限定类轻量上下文启动失败：No qualifying bean of type 'com.fasterxml.jackson.databind.ObjectMapper' available，Loader 构造器注入 ObjectMapper 解析 JSON 资源。
- 原因：限定 classes 时不扫描主 @SpringBootApplication，Jackson 自动配置不生效，ObjectMapper 无 Bean；全量上下文则不会遇到。
- 修复：测试类内加 @TestConfiguration static class TestConfig { @Bean ObjectMapper objectMapper() { return new ObjectMapper(); } } + @Import(TestConfig.class)。
- 教训：限定类 @SpringBootTest 轻量集成测试，凡依赖自动配置提供的 Bean（ObjectMapper/DataSource 等）必须显式 @Import 或改用全量上下文；集成测试优先用限定类 + TestConfiguration 组合控制启动范围。

### 2026-08-14 双注入点功能需共享同一配置开关语义 + parseBoolean 静默关闭陷阱
- 现象：Gate 1（PatientDataController）有 DIAG_DICT_INJECT_ENABLED 开关门控，Gate 2（DiagnosisIcdProvider）漏加，同一开关在两个注入点行为不一致；代码审查发现。
- 根因：新功能跨多个注入点落地时，开关/白名单等门控条件分散在各自类中，无统一收口点校验；Boolean.parseBoolean 对 '1'/'abc' 等非字面量静默返回 false（仅空串才回退默认），导致误配时功能被静默关闭而非回退缺省。
- 修复：编排门面（Provider）直接注入 DiagnosisDictProperties 共享开关；isEnabled() 显式 equalsIgnoreCase('true'/'false') 判断，其余视为非法值回退 DEFAULT_ENABLED + warn 日志。
- 教训：①多注入点功能在 TDD 验收清单中增加'开关语义一致性'检查项；②配置解析类禁止裸用 parseBoolean/parseInt，非法值必须显式识别并回退缺省；③脚本 URL 拼接用独立 HOST/PORT 变量，禁止对已有完整 URL 做字符串替换拼端口。

### 2026-08-15 测试服务器(100.66.1.4)自动部署失效：git pull 被本地改动阻塞 + target 累积多 jar 导致 Docker COPY 失败
- 现象：8082 执行服务器两周未更新（镜像停在 7-29，版本 0.9.187）；`git-poll-deploy-cron.log` 每 10 分钟都报「11 个后端新提交 + 14 个前端新提交」但 `git pull FAILED`，永不部署。
- 根因①（git pull 阻塞）：后端仓库工作区有未提交本地改动 `deploy/execution-linux/.env.execution`（Oracle 指测试库 100.66.1.4/XE，原 172.16.11.43/freepdb1）与 `docker-compose-execution-image.yml`（加 `/medai/downloads` 挂载），与远端 11 个新提交撞车，git 报「您的本地修改将被合并操作覆盖」中止；前端 `package-lock.json` 本地改版本号（0.9.227→0.9.234）同样会卡。
- 根因②（Docker 构建失败）：`target/` 累积 13 个历史版本 jar（0.9.222~0.9.246），根 Dockerfile 第 9 行 `COPY target/*.jar ./` + 第 38 行 `COPY --from=builder /build/*.jar app.jar` 匹配多文件报 "more than one source file"。
- 修复：`git stash push -- <两个文件>` → `git pull origin main` → `git stash pop`（本地/远端改不同行可干净合并，Oracle 测试配置必须保留）；前端过时 stash 直接 drop；构建前 `rm -f target/*.jar`。
- 根因③（Flyway 校验失败，主服务器 8081 起不来）：测试库缺迁移 `0.9.189`（flyway_schema_history 只有 155/188/190，缺 189「relax legacy user department shadow columns」；其 schema 变更——USER_DEPARTMENTS 的 USERID/DEPARTMENTID 放宽为 NULL——其实早已存在于表结构，只是没登记记录）。新代码校验到 189 → `FlywayValidateException: Detected resolved migration not applied to database: 0.9.189`。
- 修复③：`spring.flyway.out-of-order=true` 对本项目 Flyway 版本**无效**（加了仍报同样错）；正确做法=直接补插 flyway_schema_history 记录（checksum 留 NULL，与既有 190 记录一致；先 UPDATE 190 的 installed_rank 3→4，再 INSERT 189 到 rank 3，使 155→188→189→190 有序）。列名都是小写引号（`system."flyway_schema_history"`）。
- 教训：测试库特有的 .env 值不应改在被跟踪的 `.env.*` 文件上（易与远端冲突、且 git pull 会被永久阻塞）；部署脚本 build_backend 应 `mvn clean package` 或先清理旧 jar，否则每次版本号 bump 都累积一个 jar，最终 COPY 炸掉；测试库 Flyway 迁移若有"缺号"，新代码部署后主服务器必挂，需在 flyway_schema_history 补登记。
- 坑中坑：`env_file`（注入原始变量）与 `--env-file`（仅做 `${VAR}` 替换）是两个独立机制，只改一个会导致容器里 `ORACLE_HOST`(raw) 与 `SPRING_DATASOURCE_URL`(替换) 不一致，entrypoint 等生产库卡死而应用配置却正确——排查时看 `docker compose config` 的 `environment` 与 `env_file` 两部分都要对。
