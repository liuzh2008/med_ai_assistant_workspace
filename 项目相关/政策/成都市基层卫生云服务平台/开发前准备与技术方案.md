## 二、P0 — 核心闭环（10 月底前必须上线）

### 2.1 数据上传与脱敏

| 子功能 | 说明 |
|--------|------|
| 病历手动录入 | 主诉、现病史、既往史、体格检查等通过表单逐项填写 |
| 多格式文件上传 | Word/PDF 病历、avi/mp4 影像视频、jpg/png 检验报告/临床照片 |
| OCR 识别 | 上传时服务端对文档/图片自动 OCR，提取文字内容用于后续 AI 分析和脱敏 |
| PII 自动脱敏 | HanLP 医疗 NER + 正则规则识别姓名/身份证号/手机号/医保号 → 打码处理 |
| 脱敏版入库 | 脱敏后内容存入 MySQL，作为平台唯一可展示版本；原始版加密存档（仅管理员可调阅） |
| 上传规范提示 | 视频上传页提示"请勿在画面中展示患者隐私信息"，引导避开床头卡、腕带等 PII 区域 |

**设计要点**：上传即脱敏，后续所有环节（AI 分析、会诊共享、归档）均使用脱敏版，无实时 OCR 处理需求。

### 2.2 视频会议（TRTC 实时音视频）

| 子功能 | 说明 |
|--------|------|
| 一键发起 | 基层医师选择专家/交由系统派单 → 一键创建 TRTC 房间 → 专家手机端实时接入 |
| 音视频通话 | 基于微信原生 `<live-pusher>` / `<live-player>` 组件，延迟 <300ms |
| 床边示教 | 基层医师后置摄像头推流，实时传输患者体征、检查操作画面 |
| 云端录制 | 查房全程自动云端录制，存入 COS，生成带教记录 |
| 关键画面截图 | REST API 触发云端截图，用于操作回溯 |
| 水印防护 | 画面叠加"请勿截图外传"半透明水印 |
| 弱网自适应 | 根据网络质量自动调整码率（标清 360p ↔ 高清 720p），3G 下保证音频通话 |
| 多端切换 | 专家可在手机小程序 ←→ PC 管理后台间无缝切换，复杂影像转 PC 端高清查看 |

### 2.3 会诊工作流

```
基层医师提交申请
    │
    ├── 填写病历 + 上传资料 → 触发脱敏 → 触发 AI 质控/诊断/诊疗计划
    │
    ▼
机构管理员审核 ──→ 驳回（附原因）→ 基层医师修改后重新提交
    │
    ▼ 通过
系统派单 / 基层指定专家
    │
    ▼
专家接单 → 预约会诊时间
    │
    ▼
开展会诊（TRTC 视频 + 会诊简报为辅助材料）
    │
    ▼
生成会诊纪要（AI 辅助总结 + 专家确认）
    │
    ▼
归档（按机构/专科/时间三维分类存储）
```

### 2.4 异步点单式请教

与实时查房并行的另一种指导模式，适用于非紧急临床疑问。

| 子功能 | 说明 |
|--------|------|
| 自主上传 | 基层医师上传病历、影像、检查报告，指定专科/专家 |
| 消息提醒 | 专家收到微信订阅消息通知，碎片化时间查看并回复 |
| 回复闭环 | 专家文字反馈 + 可选附件，基层医师收到回复通知 |
| 智能派单 | 除指定专家外，支持按专科+职称自动匹配专家池派单，避免指定专家繁忙时无人响应 |
| 服务评价 | 基层医师办结后对专家响应速度、指导实用性 1~5 星评分，结果纳入专家履职考核 |
| 全流程归档 | 每笔请教自动形成完整电子档案 |

### 2.5 消息通知

| 子功能 | 说明 |
|--------|------|
| 微信订阅消息 | 新请教通知、会诊邀请、专家回复、审核结果 |
| 站内信 | 所有消息在平台内有汇总列表，支持已读/未读 |
| 加急强提醒 | 紧急病例标记"加急"后，微信订阅消息 + 短信双通道推送 |
| 短信兜底 | 腾讯云 SMS，用于加急场景和微信通知失败时的备用通道 |

### 2.6 指导档案归档

| 子功能 | 说明 |
|--------|------|
| 三维分类 | 按**机构**（社区卫生服务中心/乡镇卫生院/村卫生室）、**专科**（内科/外科/妇产科/儿科等）、**时间**（年月）三级分类 |
| 档案内容 | 原始资料（脱敏版）+ AI 分析报告 + 专家指导意见 + 会诊纪要 + 服务评价 |
| 查询检索 | 支持按患者脱敏 ID、疾病名称、会诊时间、专家姓名等多条件组合查询 |
| 导出 | 支持单条档案打印 / 批量导出 Excel |

### 2.7 四级 RBAC 权限

| 角色 | 可见范围 |
|------|---------|
| 基层医师 | 仅本机构数据 + 本人发起的会诊/请教 |
| 上级专家 | 本人参与的会诊 + 被指定的请教 + 专家池匹配记录 |
| 机构管理员 | 本机构全部数据（含所有医师操作、评价、统计） |
| 区县卫健局 | 辖区内所有机构的聚合统计数据（不含患者个人信息明细） |

## 三、P1 — AI 增强（差异化竞争力，10 月底随核心上线）

### 3.1 会诊前 AI 指导（三大引擎）

| 引擎 | 输入 | 输出 | 来源 |
|------|------|------|------|
| **病历质控引擎** | 基层医师填写的结构化病历 + 上传资料 OCR 文本 | 质控评分（0-100）+ 缺失项清单 + 规范性建议 + 逻辑冲突检测 | 提取自 MedAiAssistant QC 模块 |
| **诊断推理引擎** | 主诉 + 现病史 + 体格检查 + 辅助检查结果 | 鉴别诊断排序清单 + 支持/不支持依据 + 建议补充检查 + 关键待确认问题 | 提取自诊断推理链（Prompt 模板 ID 405 + 断言化输出） |
| **诊疗计划引擎** | 工作诊断 + 患者上下文 + 基层资源限制 | 8 步推理草案：问题列表→治疗目标→方案生成→展开→药物互检→风险预警→患者教育→监测指标 | 提取自 8 步诊疗推理（9 个 Prompt JSON） |

**编排输出**：三引擎结果聚合为结构化《会诊简报》JSON，附入会诊请求，供专家在会诊前预览。

### 3.2 会后 AI 总结与修订（创新功能）

会诊结束后，基于专家口头指导意见，AI 自动完成以下闭环：

```
TRTC 云端录制 mp4
    │
    ├── 语音转文字（阿里云 ASR / 腾讯云语音识别）
    ├── AI 提取专家意见要点
    ├── AI 对比会诊前简报 vs 专家最终意见 → 标注差异
    │
    └── 生成《会诊后修订报告》：
         ├── 诊断修订：原 AI 诊断 A → 专家确认为 B，理由/依据
         ├── 诊疗计划修订：原方案 XX → 调整为 YY，关键修正点
         ├── 药物调整明细：新增/停用/剂量调整
         ├── 专家关键提示摘要（3~5 条核心建议）
         └── 基层医师待办事项（需执行的检查/用药/随访）
```

**价值**：背调只要求"人工撰写会诊纪要"，此功能将纪要生成自动化 + 诊断/诊疗计划的闭环修订，是区别于竞品的核心亮点。

### 3.3 专家排班与预约

| 子功能 | 说明 |
|--------|------|
| 时段设置 | 专家在系统中设置可接诊时段（如每周一三上午 9:00-11:00） |
| 基层预约 | 基层医师查看专家排班表，选择空闲时段预约查房指导 |
| 加急通道 | 紧急病例标记"加急"，系统跳过排班限制，直接通知当前在线的对应专科专家 |
| 冲突检测 | 同一专家同一时段不可被重复预约 |
| 排班提醒 | 会诊开始前 15 分钟，双方收到微信提醒 |

### 3.4 多终端无缝切换

| 场景 | 实现 |
|------|------|
| 专家在手机小程序中接听 | TRTC 微信小程序端 |
| 需要查看高清影像 | 点击"切换至 PC 端" → 同一 TRTC 房间，PC Web 端自动进入 |
| PC 端操作 | 高清视频流 + 文件查看 + DICOM 影像（远期） + 纪要编辑 |
| 回手机 | 点击"切换至移动端" → 小程序恢复通话，无缝继续 |

## 四、P2 — 运营工具（上线后迭代）

### 4.1 多维度统计报表

| 维度 | 统计指标 |
|------|---------|
| 按区（市）县 | 辖区内指导次数、培训人次、活跃机构数、平均响应时长 |
| 按医疗机构 | 该机构指导次数、请教问题类型分布、被指导科室排行、登录率 |
| 按专科 | 各专科请教量、常见问题类型、专家响应速度 |
| 按专家 | 个人指导总数、平均评分、响应时长中位数、擅长领域标签 |

**附加能力**：
- 自定义时间段导出 Excel/PDF 报表
- 月度/季度工作简报自动生成（图文混排，匹配卫健部门调度需求）

### 4.2 活跃度监测预警

| 子功能 | 说明 |
|--------|------|
| 实时看板 | 各区县/机构登录率、使用率、指导发起数可视化展示 |
| 自动预警 | 连续 30 天无登录记录 → 自动标记"低活跃"，推送预警至机构管理员和区县卫健局 |
| 督导闭环 | 预警后可生成督导函模板，卫健部门一键下发 |

### 4.3 病例研讨管理

| 子功能 | 说明 |
|--------|------|
| 脱敏上传 | 病例上传自动脱敏 |
| 范围控制 | 研讨可见范围：公开（全平台）/ 指定机构 / 指定人员 |
| 讨论区 | 文字评论 + 图片附件，支持按病例聚合讨论 |
| 教学标记 | 优秀病例可标记为"教学案例"，纳入平台培训资源库，供基层点播学习 |

### 4.4 直播培训

| 子功能 | 说明 |
|--------|------|
| 直播推流 | 专家通过 PC 端开启直播培训 |
| 签到核验 | 学员进入直播间自动签到，记录进入/离开时间 |
| 观看时长统计 | 自动累计有效观看时长（剔除短时间进出），达标后生成培训学时 |
| 资源库 | 录播课、课件按专科、层级标签分类，基层可自主点播学习 |
| 学时档案 | 每位学员的培训学时汇总，支持按时间段查询和导出 |

### 1.2 政策对标

平台严格对标以下国家政策要求，功能设计须逐项回应：

| 政策 | 对标点 |
|------|--------|
| **国家医疗卫生强基工程** | 提升基层临床服务能力 → 平台以"远程会诊、在线培训、病例研讨、远程查房"为核心，直连上级专家资源下沉 |
| **基层医疗卫生机构医疗质量改善三年行动** | 规范基层诊疗行为 → 病历质控引擎 + AI 诊断推理 + 会诊前标准化流程 |
| **互联网诊疗管理办法** | 平台定位为"业务技术指导与临床带教工具"，上级专家意见仅作临床参考，最终诊疗责任由接诊基层医师及机构承担 |
| **个人信息保护法 / 医疗数据安全** | 全链路 PII 脱敏（姓名、身份证号、手机号、医保号）；机构级数据隔离；操作审计留痕 |

### 1.4 硬件基础设施规划

需求方要求供应商提供"云服务器、安全网关、存储设备等硬件配置选型"方案。以下为推荐配置：

| 资源类型 | 推荐配置 | 数量 | 用途 |
|---------|---------|:--:|------|
| **应用服务器** | 腾讯云 CVM S5（8核16G） | ≥ 2 节点 | Spring Boot 业务服务，Nginx 反向代理 |
| **数据库服务器** | 腾讯云 CDB MySQL 8.0（8核32G，200GB SSD） | 1 主 + 1 只读 | 业务数据，读写分离 |
| **缓存服务器** | 腾讯云 Redis 7.0（4核16G，主备版） | 1 组 | 会话管理、热点缓存、分布式锁 |
| **对象存储** | 腾讯云 COS（标准存储 + 低频存储） | — | 病历、影像视频/图片文件、录播文件 |
| **搜索服务** | 腾讯云 ES（4核16G，500GB） | 1 集群 | 统计报表聚合查询 |
| **安全网关** | 腾讯云 WAF + SSL 证书 | 1 套 | Web 应用防火墙、HTTPS 终结 |
| **音视频服务** | 腾讯云 TRTC（包月套餐，基础版 625元/月含11万分钟） | — | 远程查房、会诊音视频 |
| **CDN** | 腾讯云 CDN（按流量计费） | — | 静态资源加速、培训课件分发 |
| **日志服务** | 腾讯云 CLS | — | 集中日志收集与检索 |
| **短信服务** | 腾讯云 SMS | — | 加急通知兜底 |

**成本估算（月费）**：基础配置约 9,000~13,000 元/月（含 TRTC 基础版套餐费 625元/月，不含 SMS 按量计费部分）。建议生产环境按此配置起步，根据压测结果和实际负载动态扩缩。

## 二、推荐技术选型

### 2.1 选型原则

- **团队技能延续**：优先 Java / Spring Boot / Vue 技术栈，降低学习曲线
- **微信生态兼容**：实时音视频、消息推送优先选用腾讯系 SDK

### 3.3 数据来源说明（重要）

背调文档未要求平台与各基层机构 HIS/EMR 系统对接。平台数据入口为**基层医师手动录入或自主上传**，不涉及自动化系统集成。

| 数据类型 | 来源方式 | 说明 |
|---------|---------|------|
| 病历信息 | 基层医师手动录入 | 主诉、现病史、既往史、体格检查等通过表单填写 |
| 检查报告 | 基层医师自主上传 | Word/PDF 病历、检验报告 |
| 影像资料 | 基层医师自主上传 | avi/mp4 等视频格式的影像资料（手机拍摄 CT/MRI/X 光屏幕为主）；也可上传 jpg/png 静态图片 |
| 临床照片 | 基层医师自主上传 | 床边状态、生命体征画面、现场检查操作画面 |
| 会诊请求 | 基层医师一键发起 | 选择专家或交由系统自动派单 |

> **架构影响**：由于数据不进 HIS，平台数据库即为唯一数据源，无需考虑异构系统数据同步、主数据管理、HL7/FHIR 互操作等问题，显著降低架构复杂度。

## 四、核心技术难点与应对策略

### 难点一：5,000 并发下的系统承载能力

**问题描述**：峰值 5,000 人同时在线，会诊高峰期可能集中出现在上午查房时段（9:00~11:00），瞬时压力极大。

**应对策略**：

| 层面 | 措施 |
|------|------|
| **网关层** | Nginx 反向代理 + 最小 4 核 8G × 2 节点；`limit_req_zone` 令牌桶限流（单 IP 100 QPS）；WebSocket 长连接独立端口，避免阻塞 HTTP |
| **应用层** | Spring Boot 内嵌 Undertow（比 Tomcat 高并发表现更好）；数据库连接池 HikariCP `maximumPoolSize=50`；热点数据 Redis 缓存（用户信息、机构配置、质控标准），过期策略 30min |
| **数据层** | MySQL 读写分离（主库写 + 只读副本查）；统计报表走 Elasticsearch，不直查 MySQL 大表；文件上传直传 COS，不经过应用服务器 |
| **TRTC** | 音视频流量不经过业务服务器，走腾讯 CDN 边缘节点 |

**验证目标**：JMeter 压测 — 5,000 虚拟用户并发登录 + 会诊列表查询，P99 响应 < 2s，错误率 < 0.1%。

---

### 难点二：多格式影像文件的在线查看与兼容性

**问题描述**：实际运行中，基层医师极少导出原始 DICOM 文件，更常见的操作是**用手机直接拍摄 CT/MRI/X 光屏幕或检查报告**，生成 avi/mp4 视频或 jpg/png 图片后上传。这些文件体积差异大（视频可达 200MB+），需在小程序内直接播放/查看。

**应对策略**：

1. **视频文件**：优先使用微信小程序原生 `<video>` 组件播放，支持 avi/mp4/mov 等主流格式；服务端不做转码（TRTC 云端录制本身即为 mp4）
2. **图片文件**：使用小程序原生 `<image>` 组件，支持手势缩放；大图模式下服务端生成压缩预览图（缩略图 200px宽 + 原图），列表页加载缩略图，点击查看原图
3. **文件体积控制**：超 50MB 文件上传前压缩提示；服务端后台异步生成视频首帧缩略图用于列表预览
4. **PC 端**：浏览器原生 `<video>` / `<img>` 直接渲染，支持高清查看和逐帧播放
5. **兜底方案**：极端弱网环境（3G/2G）提示"建议在 WiFi 下查看"，支持仅加载首帧预览

**与 DICOM 的关系**：背调文档提及 DICOM 格式，但基层实际极少使用。方案中将 DICOM 作为**远期锦上添花功能**（P3+），当前阶段不做 Cornerstone.js 集成和 DICOM→JPEG 转换管线。若未来需求方明确要求，再行补充。

**风险**：部分旧机型 Android WebView 对高码率视频解码性能不足。需提前用真机矩阵测试（重点测试 avi 格式兼容性，部分 Android 机型需服务端转 mp4）。

---

### 难点三：查房指导中患者隐私资料的脱敏防护

**问题描述**：查房指导过程中，基层医师可能共享病历、检查报告画面，需要自动屏蔽患者姓名、身份证号、联系方式等 PII。

**应对策略**：采用**上传即脱敏、共享即安全**的两层策略，避免实时处理。

**第一层：文档/图片 — 上传时 OCR 脱敏，指导时只显脱敏版**

```
医师上传病历/报告
    │
    ├── ① 服务端 OCR 识别文档中的文字内容
    ├── ② HanLP 医疗 NER + 正则规则 → 识别 PII（姓名/身份证号/手机号/医保号）
    ├── ③ 打码处理：姓名→"患者"，身份证号→"510************123"，手机号→"138****5678"
    ├── ④ 脱敏版存入数据库 + 原始版加密存档（仅管理员可调阅）
    │
    └── ⑤ 查房指导时，系统仅展示脱敏后的数据库记录
          → 基层医师调取、共享的任何资料都是已脱敏版本
          → 无需在指导过程中做实时 OCR 处理
```

**第二层：音视频画面 — 上传规范约束，不依赖技术拦截**

- 平台在上传页明确提示："请勿在视频中展示患者姓名、身份证号等隐私信息"
- 基层医师拍摄床边画面时，引导对准体征/操作区域，避开床头卡、腕带等含 PII 的区域
- 不追求实时视频流 OCR 脱敏（延迟高、误判大、成本不可控）

**配套措施**：

- TRTC 云端录制文件标注"可能含患者信息"标签，设定自动过期策略（如 7 天）
- 视频画面叠加半透明水印"请勿截图外传"，TRTC SDK 支持混流水印注入
- 所有资料调阅操作记录审计日志（谁、何时、查看了什么）

**优势**：相比"共享前实时脱敏"方案，上传即脱敏消除了指导过程中的处理延迟和 OCR 失败风险，用户体验更流畅。

---

### 难点四：四级 RBAC 的数据隔离与可见性控制

**问题描述**：

| 角色 | 可见范围 |
|------|---------|
| 基层医师 | 仅本机构数据 + 本人发起的会诊/请教 |
| 上级专家 | 本人参与的会诊 + 被指定的请教 |
| 机构管理员 | 本机构全部数据（含所有医师） |
| 区县卫健局 | 辖区内所有机构的统计数据（不含患者明细） |

**应对策略**：

1. **机构级数据隔离**：每张业务表加 `institution_id` 字段；所有查询 Service 层统一注入机构过滤条件（基于 JWT token 中的 `institution_id`）
2. **角色权限矩阵**：Spring Security `@PreAuthorize` 注解 + 自定义 `PermissionEvaluator`；权限规则配置在数据库，支持运行时调整
3. **卫健局统计隔离**：统计数据经聚合后对外暴露，原始患者明细不返回（API 层拦截，仅返回 count/sum/avg）

**测试重点**：越权测试 — 基层医师是否能查看到其他机构数据？区县卫健局能否获取患者个人信息？——这是安全审计的必过项。

---

### 难点五：3.5 个月工期下的功能取舍

**问题描述**：需求文档功能范围大（远程查房、异步请教、直播培训、会诊流程、病例研讨、统计报表、活跃度监测），3.5 个月不可能全部交付。

**MVP 分阶段策略**：

| 阶段 | 时间 | 交付内容 |
|------|:--:|------|
| **P0 — 核心闭环** | 第 1~6 周 | 微信登录 + RBAC；异步点单式请教（上传→派单→回复→评价→归档）；远程会诊流程（申请→审核→接单→纪要）；TRTC 基础音视频（1v1） |
| **P1 — 增强功能** | 第 7~10 周 | 远程教学查房（TRTC 多端 + 一键发起 + 截图录屏）；影像文件在线查看（视频播放+图片缩放）；会诊前 AI 指导集成（病历质控+诊断推理+诊疗计划）；专家智能匹配（专科+职称自动派单）；消息推送（含加急强提醒） |
| **P2 — 运营工具** | 第 11~14 周 | 直播培训 + 签到核验 + 学时统计 + 点播学习；病例研讨管理（脱敏+范围控制+教学标记）；统计报表基础版；排班预约（专家时段+加急机制） |
| **P3 — 延后上线** | 上线后 | 活跃度监测预警（自动标记低活跃机构）；统计报表高级版（月度/季度工作简报自动生成）；服务评价纳入专家履职考核看板 |

**核心原则**：P0 必须保证"基层能发起请教（含自动派单）、专家能回复反馈并归档、会诊流程全链路走通"这一最小闭环在 10 月底上线。P1 实现远程查房+AI指导+智能匹配等核心差异化功能，与 P0 共同构成 10 月底试运行版本。P2 运营工具类和 P3 简报自动生成等可上线后迭代。

---

### 难点六：微信小程序包体积限制

**问题描述**：微信小程序主包限制 2MB，分包总限制 20MB。功能模块多，容易超限。

**应对策略**：

| 措施 | 说明 |
|------|------|
| **分包加载** | 按功能域拆分：主包（登录+首页+消息）→ 分包（会诊/培训/研讨/影像/统计） |
| **图片/CDN** | 所有静态资源（图标、培训课件封面）放腾讯云 COS + CDN，不打包 |
| **组件库按需引入** | uni-app 的 uni-ui 组件按需引入，不用全量导入 |
| **代码压缩** | uni-app 编译自带 tree-shaking + 代码压缩；关闭 sourcemap |

---

### 难点七：多机构多格式文件管理

**问题描述**：支持 Word/PDF 病历、avi/mp4 影像视频、jpg/png 检验报告图片、临床照片等多种格式上传；文件需在线预览，按机构安全隔离。

**应对策略**：

1. **文件分类存储**：COS Bucket 按 `{institution_id}/{type}/{yyyy-MM}/` 路径隔离
2. **上传安全**：后端校验文件类型（Magic Number 校验，非扩展名）；文件大小限制（视频 200MB，其他 50MB）；病毒扫描（腾讯云 CSS）
3. **预览转换**：
   - Word/PDF → 服务端 LibreOffice 转 PDF → 小程序端 PDF.js 预览
   - 视频（avi/mp4/mov）→ 小程序原生 `<video>` 组件直接播放；服务端异步生成首帧缩略图
   - 图片 → 原图 + 缩略图双存储
4. **下载控制**：默认在线预览，下载需记录日志（谁、何时、下载了什么）

---

### 难点八：MedAiAssistant AI 能力的提取与直接集成

**策略变更**：不再将 MedAiAssistant 作为外部服务通过 API 远程调用，而是将核心 AI 能力**提取为独立 Java 模块**，直接嵌入云平台代码库中，作为平台原生功能。

**提取范围**：

| 模块 | 来源 | 提取内容 |
|------|------|---------|
| `platform-ai-qc` | MedAiAssistant QC 引擎 | 病种质控标准 JSON（qc-standards/） + 完整性检查 + 规范性检查 + 逻辑一致性检查的规则逻辑 |
| `platform-ai-diagnosis` | 诊断推理链（Prompt 模板 ID 405 + LogicalDiagnosisPanel 后端） | 6 步推理链 Prompt 模板 + 断言化输出解析器 |
| `platform-ai-treatment` | 8 步诊疗推理（9 个 Prompt JSON） | 问题列表→治疗目标→方案生成→展开→药物互检→风险预警→患者教育→监测指标 的完整推理链 |
| `platform-ai-brief` | 新建 | 纯规则编排器：从三个 AI 模块输出中提取关键字段聚合为会诊简报 JSON |

**直接集成的优势**：

| 对比 | 远程 API 调用（旧方案） | 直接集成（新方案） |
|------|----------------------|-------------------|
| 网络依赖 | 依赖 MedAiAssistant 服务器在线 | 无，仅 LLM 为外部调用 |
| 延迟 | HTTP 往返 + 序列化开销 | 进程内调用，零额外延迟 |
| 部署复杂度 | 两个系统独立部署+运维 | 一个系统，统一部署 |
| 数据一致性 | 两套数据库，需同步 | 共享 MySQL，天然一致 |
| 容错 | MedAiAssistant 宕机→AI 全部不可用 | 仅 LLM 不可用时降级（概率远低于服务器宕机） |
| 开发效率 | 跨系统联调，接口对齐成本高 | 同代码库，无联调成本 |

**需要适配的工作**：

1. **数据库迁移**：MedAiAssistant 使用 Oracle，云平台使用 MySQL。Prompt 模板和质控标准 JSON 需从 Oracle 导出，转为 MySQL 表或直接文件存储
2. **LLM 配置**：DeepSeek / 通义千问的 API Key 和调用逻辑可直接复用 MedAiAssistant 的 AiService 层
3. **脱敏引擎**：HanLP 医疗 NER + 正则规则可直接复制，无需改造
4. **Prompt 模板管理**：从 MedAiAssistant 的模板管理系统简化为文件加载或 MySQL 存储（云平台不需要版本同步/UPSERT 等高级功能）

**工作量变化**：原方案需新建 consultation API 模块 + 跨系统联调。新方案改为提取现有代码 + 适配数据库，总工作量基本持平（约 2~3 周），但长期维护成本大幅降低。

### 难点九：服务评价体系与专家履职考核

**问题描述**：需求明确要求"基层医师办结请教后，可对专家响应速度、指导实用性进行评价，结果纳入专家履职考核数据"。这意味着评价不仅是一个简单的打分功能，还需对接卫健局的管理考核体系。

**应对策略**：

1. **评价维度**：响应速度（系统自动记录从派单到首次回复时间）+ 指导实用性（医师主观评分 1~5 星）+ 可选文字反馈
2. **防刷机制**：同一次请教仅允许评价一次；评价后不可修改；匿名评价（专家看不到评价者身份）
3. **考核看板**：按专家、专科、时间段生成评价汇总报表（平均分、响应时长中位数、好评率）
4. **低分预警**：连续 3 次低于 3 星自动标记，推送提醒至机构管理员
5. **数据隔离**：评价数据归属卫健局管理端可见，基层医师仅能看到自己对专家的评价
